3.1  INTRODUCTION
================================================================================

Memory management is one of the most critical functions of an operating system.
The memory management subsystem is responsible for allocating and deallocating
memory to processes, keeping track of which parts of memory are in use, and
managing the transfer of data between main memory and secondary storage (disk).

────────────────────────────────────────────────────
3.1.1  Storage Organization
────────────────────────────────────────────────────

Computer memory is organized in a hierarchy based on speed, cost, and capacity.
The basic unit of memory is the byte (8 bits). Memory addresses on a modern
64-bit system are 64 bits wide, theoretically allowing addressing of $2^{64}$
bytes (16 exabytes), though practical implementations use only 48 or 57 bits.

Storage can be categorized by volatility:
  - Volatile: Loses content when power is removed (registers, cache, RAM).
  - Non-volatile: Retains content (SSD, HDD, flash memory, ROM).

The processor can only directly execute instructions and access data that
reside in main memory (RAM) or CPU registers. Any program or data not in main
memory must be moved there before the CPU can operate on it.

    Micro-topic: The Memory Controller and DRAM Architecture
    ─────────────────────────────────────────────────────────
    Modern systems use DDR (Double Data Rate) SDRAM. The memory controller
    (integrated into the CPU on modern processors like AMD Ryzen and Intel
    Core) manages access to DRAM chips. A DRAM chip is organized into:
      - Banks: Independent arrays that can be accessed in parallel.
      - Rows: A row must be "activated" (copied into the row buffer) before
        any column in it can be read.
      - Columns: Individual memory locations within an active row.

    A memory access involves: Precharge → Row Activate → Column Read/Write.
    If the requested row is already active (row buffer hit), access is fast
    (~15ns). If a different row must be activated (row buffer miss), it takes
    longer (~30-50ns). This is why sequential memory access patterns
    (locality) are much faster than random access.

        Deeper: NUMA (Non-Uniform Memory Access)
        ─────────────────────────────────────────
        In multi-socket systems, each CPU socket has its own local memory.
        Accessing local memory is faster than accessing memory attached to
        another socket (remote memory). This is NUMA. The Linux kernel is
        NUMA-aware: the memory allocator (the buddy system and slab
        allocator) prefers to allocate memory from the NUMA node closest to
        the CPU where the requesting process is running. Tools like numactl
        and numastat on Arch Linux allow inspecting and controlling NUMA
        behavior.

────────────────────────────────────────────────────
3.1.2  Memory Hierarchy
────────────────────────────────────────────────────

The memory hierarchy exploits the principle of locality of reference to provide
the illusion of a large, fast memory by combining small-fast and large-slow
storage technologies.

  ┌──────────────────────────────────────────────────────────────────┐
  │  Level          │ Typical Size  │ Access Time  │ Cost/GB         │
  ├──────────────────────────────────────────────────────────────────┤
  │  CPU Registers  │ ~1 KB         │ ~0.3 ns      │ —               │
  │  L1 Cache       │ 32-64 KB      │ ~1 ns        │ Very high       │
  │  L2 Cache       │ 256 KB-1 MB   │ ~4-7 ns      │ High            │
  │  L3 Cache       │ 4-64 MB       │ ~10-20 ns    │ Moderate-high   │
  │  Main Memory    │ 4-256 GB      │ ~50-100 ns   │ ~$3-5           │
  │  SSD (NVMe)     │ 256 GB-4 TB   │ ~25-100 μs   │ ~$0.10-0.20     │
  │  HDD            │ 1-20 TB       │ ~5-10 ms     │ ~$0.02-0.03     │
  │  Tape/Archive   │ Unlimited     │ Seconds-Min  │ ~$0.01          │
  └──────────────────────────────────────────────────────────────────┘

Principle of Locality:
  - Temporal Locality: If a memory location is accessed, it is likely to be
    accessed again in the near future (loops, frequently-used variables).
  - Spatial Locality: If a memory location is accessed, nearby locations are
    likely to be accessed soon (arrays, sequential code execution).

Cache lines (typically 64 bytes on x86-64) exploit spatial locality: when one
byte is accessed, the entire 64-byte cache line is loaded.

    Micro-topic: Cache Architecture (Associativity and Replacement)
    ───────────────────────────────────────────────────────────────
    Caches are organized by associativity:
      - Direct-mapped: Each memory block maps to exactly one cache line.
        Fast lookup but high conflict misses.
      - N-way Set-Associative: Each memory block can map to any of N lines
        in a set. A set is selected by address bits. Common: 4-way, 8-way,
        16-way.
      - Fully Associative: A block can go anywhere in the cache. Best hit
        rate but expensive to search.

    Cache replacement policies (when a set is full):
      - LRU (Least Recently Used): Evict the least recently accessed line.
      - Pseudo-LRU: Approximation of LRU using a tree of bits.
      - Random: Surprisingly effective and simpler to implement.

        Deeper: Cache Coherency Protocols (MESI/MOESI)
        ───────────────────────────────────────────────
        In multiprocessor systems, each core has its own L1/L2 cache. When
        one core modifies a cached memory location, other cores' caches may
        have stale copies. Cache coherency protocols ensure consistency:

        MESI Protocol (Intel):
          M (Modified): Line is dirty, only in this cache.
          E (Exclusive): Line is clean, only in this cache.
          S (Shared): Line is clean, may be in other caches.
          I (Invalid): Line is not valid.

        When Core 0 writes to a Shared line, it sends an invalidation
        message to all other cores, transitioning their copies to Invalid
        and its own to Modified. This is called "write-invalidate."


================================================================================
3.2  STORAGE ALLOCATION
================================================================================

────────────────────────────────────────────────────
3.2.1  Contiguous vs. Non-Contiguous Allocation
────────────────────────────────────────────────────

CONTIGUOUS ALLOCATION: Each process is loaded into a single contiguous block
of memory. Simple addressing (base + offset) but suffers from external
fragmentation—free memory is split into small, unusable holes.

NON-CONTIGUOUS ALLOCATION: A process can be loaded into non-adjacent memory
blocks. More complex addressing (requires page tables or segment tables) but
eliminates external fragmentation. Paging is the most common non-contiguous
allocation scheme.

────────────────────────────────────────────────────
3.2.2  Logical and Physical Memory
────────────────────────────────────────────────────

LOGICAL ADDRESS (Virtual Address): The address generated by the CPU during
program execution. Every memory reference a program makes is a logical
address. The logical address space is the set of all logical addresses
generated by a program.

PHYSICAL ADDRESS: The actual address in the main memory hardware (the address
that appears on the memory bus). The physical address space is the set of all
physical addresses corresponding to the logical addresses.

The mapping from logical to physical addresses is performed by hardware called
the Memory Management Unit (MMU). In the simplest case (base-and-limit
registers), the MMU adds the base register value to the logical address:

$$PA = BR + LA$$

The limit register ensures that the logical address does not exceed the
process's allocated memory:

$$LA \geq LR \Rightarrow \operatorname{trap}$$

    Micro-topic: Address Space Layout Randomization (ASLR)
    ──────────────────────────────────────────────────────
    Modern operating systems randomize the placement of the stack, heap,
    shared libraries, and other memory regions within the virtual address
    space. This makes it harder for attackers to predict the location of
    code or data for exploitation (buffer overflow attacks). On Linux, ASLR
    is controlled by /proc/sys/kernel/randomize_va_space:
      0 = disabled
      1 = randomize mmap, stack, vdso
      2 = full (also randomize heap via brk)

────────────────────────────────────────────────────
3.2.3  Fragmentation
────────────────────────────────────────────────────

EXTERNAL FRAGMENTATION: Free memory is broken into small, non-contiguous
pieces. There may be enough total free memory to satisfy a request, but no
single contiguous block is large enough.

INTERNAL FRAGMENTATION: Memory allocated to a process may be slightly larger
than needed (because allocation is in fixed-size blocks). The unused space
within the allocated block is wasted.

Example of internal fragmentation: If memory is allocated in 4 KB pages and
a process needs 4097 bytes, it gets two pages (8 KB), wasting 4095 bytes.

────────────────────────────────────────────────────
3.2.4  Fixed Partition and Variable Partition
────────────────────────────────────────────────────

FIXED PARTITIONING:
Memory is divided into fixed-size partitions at boot time. Each partition can
hold exactly one process. Partition sizes may be equal or unequal.

  Memory:  |  Part 1 (2 MB)  |  Part 2 (4 MB)  |  Part 3 (8 MB)  |

Problems:
  - Internal fragmentation: If a process is smaller than its partition.
  - Limited multiprogramming: Number of processes ≤ number of partitions.
  - Large processes may not fit in any partition.

VARIABLE (DYNAMIC) PARTITIONING:
Partitions are created dynamically to fit each process exactly. No internal
fragmentation, but external fragmentation develops as processes are loaded
and removed.

Allocation strategies for variable partitions:
  - First Fit: Allocate the first hole that is big enough. Fast.
  - Best Fit: Allocate the smallest hole that is big enough. Minimizes
    wasted space but leaves many tiny useless holes.
  - Worst Fit: Allocate the largest hole. Leaves the largest remainder
    (hopefully usable). Generally performs poorly.
  - Next Fit: Like First Fit, but starts searching from where the last
    allocation was made.

    Micro-topic: Buddy System Allocator
    ────────────────────────────────────
    The Linux kernel uses the buddy system for physical page allocation.
    Memory is divided into blocks of sizes that are powers of 2 (in units
    of pages: 1, 2, 4, 8, ..., 1024 pages). When a block of $2^k$ pages
    is requested:
      1. If a block of size $2^k$ is available, allocate it.
      2. Otherwise, find a block of size $2^{k+1}$, split it into two
         "buddies" of size $2^k$, allocate one, and put the other on the
         free list.
      3. When both buddies are freed, they are coalesced back into a
         $2^{k+1}$ block.

    The buddy allocator is fast (O(log n)) and reduces external
    fragmentation. You can view the buddy system state on Arch Linux:
      $ cat /proc/buddyinfo

        Deeper: The Slab Allocator (SLUB)
        ──────────────────────────────────
        The buddy system allocates entire pages (4 KB minimum), which is
        wasteful for small kernel objects (e.g., a 64-byte task_struct
        pointer, a 128-byte inode). The slab allocator sits on top of the
        buddy allocator and provides efficient allocation of small,
        frequently-used objects.

        Linux uses SLUB (the unqueued slab allocator, default since 2.6.23):
          - Maintains caches for different object sizes.
          - Each cache consists of slabs (one or more contiguous pages).
          - Each slab is divided into fixed-size slots for objects.
          - Freed objects are returned to the slab, not to the buddy system.

        View slab statistics:
          $ sudo cat /proc/slabinfo | head -20
          $ sudo slabtop   # Real-time slab monitoring

3.3  RELOCATION AND PROTECTION
================================================================================

RELOCATION refers to the ability to load a process at any location in physical
memory, not just at a fixed address. Since multiple processes share memory,
the OS must be able to place them wherever free space exists.

Types of relocation:
  - Static Relocation: Addresses are fixed at compile/link time or at load
    time. Once loaded, the process cannot be moved.
  - Dynamic Relocation: Address translation is done at runtime by the MMU.
    The process can be moved in memory (swapped out and back in at a
    different location) without modifying the code.

Dynamic relocation uses base and limit registers:
  - Base register: Contains the starting physical address of the process.
  - Limit register: Contains the size of the logical address space.

Every logical address is checked: if logical_address < limit, then
physical_address = base + logical_address. Otherwise, a trap is generated.

PROTECTION ensures that a process cannot access memory belonging to another
process or to the operating system. Protection is achieved through:
  1. Base-and-limit registers (hardware-enforced bounds checking).
  2. Page-level protection bits (read, write, execute permissions per page).
  3. Privilege levels (Ring 0 for kernel, Ring 3 for user on x86).

    Micro-topic: NX Bit (No-Execute) and W^X Policy
    ─────────────────────────────────────────────────
    Modern CPUs provide an NX (No-Execute) bit in page table entries. When
    set, the page cannot be executed, preventing code injection attacks
    (even if an attacker writes shellcode to the stack, the CPU refuses to
    execute it). The W^X (Write XOR Execute) policy ensures that no page
    is simultaneously writable AND executable:
      - Code pages: readable + executable (not writable)
      - Data/stack pages: readable + writable (not executable)


================================================================================
3.4  MEMORY MANAGEMENT WITH SWAPPING
================================================================================

Swapping is a technique where the OS moves entire processes between main
memory and a backing store (swap partition or swap file on disk) to free up
memory for other processes.

The process is swapped out to the backing store and later swapped back in to
continue execution. With dynamic relocation (base register), the process can
be swapped back into a different memory location.

Swap Time = Transfer Time = (Process Size / Disk Transfer Rate)

For example, if process size = 100 MB and disk transfer rate = 100 MB/s:
$$T_{swap} = \frac{100\,\mathrm{MB}}{100\,\mathrm{MB/s}} = 1\,\mathrm{s}$$

Total swap (out + in) = 2 seconds. This is expensive!

────────────────────────────────────────────────────
3.4.1  Memory Management with Bitmaps
────────────────────────────────────────────────────

Memory is divided into allocation units (e.g., 4 bytes to several KB). A
bitmap has one bit per allocation unit: 0 = free, 1 = allocated (or vice
versa).

  Memory:     |A A A|F F|B B B B|F|C C|
  Bitmap:      1 1 1 0 0 1 1 1 1 0 1 1

Advantages: Simple, fixed-size overhead.
Disadvantage: Finding a run of consecutive free units for a large process
requires scanning the bitmap, which is slow for large memories.

Size of bitmap: If memory = M bytes and allocation unit = U bytes:
$$B = \frac{M}{U}\,\mathrm{bits} = \frac{M}{8U}\,\mathrm{bytes}$$

────────────────────────────────────────────────────
3.4.2  Memory Management with Linked Lists
────────────────────────────────────────────────────

A linked list of allocated and free memory segments. Each node contains:
  - Process ID (or "H" for hole/free)
  - Start address
  - Length
  - Pointer to next segment

  [P1: 0-5K] → [H: 5K-8K] → [P2: 8K-14K] → [H: 14K-16K] → ...

When a process terminates, its segment is marked as a hole. Adjacent holes
are merged (coalesced). The First Fit, Best Fit, and Worst Fit algorithms
operate on this list.

────────────────────────────────────────────────────
3.4.3  Memory Management Without Swapping
────────────────────────────────────────────────────

In simple systems (embedded, early PCs), only one process runs at a time, and
it occupies all of memory (above the OS). No swapping is needed. When a new
program is loaded, the old one is completely replaced.

Modern systems use virtual memory (Section 3.7) instead of whole-process
swapping, bringing in only the needed pages on demand.


================================================================================
3.5  CONTIGUOUS MEMORY ALLOCATION
================================================================================

In contiguous memory allocation, each process occupies a single contiguous
section of memory.

Memory Protection: Base and limit registers prevent processes from accessing
each other's memory. The CPU hardware checks every memory reference:

    if (logical_address >= limit)
        trap("segmentation fault");
    physical_address = base + logical_address;

Memory Allocation: When a process arrives and needs memory of size S:
  - Search the list of free holes for one of size ≥ S.
  - Allocate S bytes from the hole.
  - If the hole is larger, split it: the remaining part becomes a new hole.

FRAGMENTATION:

Internal Fragmentation: The allocated block is larger than requested. Wasted
space is inside the allocated region.

$$F_{\mathrm{internal}} = S_{\mathrm{allocated}} - S_{\mathrm{requested}}$$

External Fragmentation: Free memory exists but is not contiguous. The total
free memory may be large, but no single hole is big enough.

The 50% Rule (Knuth): After a system has been running for a while, on
average, for every N allocated blocks, there will be approximately N/2 holes.
That is, roughly 1/3 of memory is wasted in holes.


================================================================================
3.6  PAGING
================================================================================

Paging is a memory management scheme that eliminates external fragmentation
by dividing both physical memory and logical memory into fixed-size blocks.

  - Page: A fixed-size block of a process's logical (virtual) address space.
  - Frame: A fixed-size block of physical memory.
  - Page size = Frame size (typically 4 KB on x86-64, though 2 MB and 1 GB
    "huge pages" are also supported).

The address translation mechanism:
  A logical address is divided into two parts:
    - Page Number (p): Used as an index into the page table.
    - Page Offset (d): Combined with the frame number to get the physical
      address.

  If the logical address space is $2^m$ and the page size is $2^n$:
    - Page number bits: m - n
    - Offset bits: n
    - Number of pages: $2^{m-n}$

  $$PA = FN \times PS + d$$

  Or equivalently:
  $$PA = (PT[p] \cdot 2^n) + d$$

Example: 32-bit logical address, 4 KB (4096 = $2^{12}$) page size:
  - Offset bits: 12
  - Page number bits: 32 - 12 = 20
  - Number of pages per process: $2^{20}$ = 1,048,576 (~1 million pages)
  - Page table size: $2^{20}$ entries × 4 bytes/entry = 4 MB per process!

This page table size problem motivates multi-level page tables.

    Micro-topic: Page Table Entry (PTE) Structure
    ──────────────────────────────────────────────
    Each page table entry contains:
      - Frame number: Physical frame where the page resides.
      - Present/Valid bit: 1 if the page is in memory, 0 if on disk.
      - Protection bits: Read (R), Write (W), Execute (X) permissions.
      - Dirty bit (Modified): Set if the page has been written to.
      - Accessed/Referenced bit: Set if the page has been read or written.
      - Caching control bits: Write-through, cache-disable.
      - User/Supervisor bit: Accessible from user mode or kernel mode only.

    On x86-64, a PTE is 8 bytes (64 bits):
      Bits 0: Present
      Bits 1: Read/Write
      Bits 2: User/Supervisor
      Bits 3: Write-Through
      Bits 4: Cache Disable
      Bits 5: Accessed
      Bits 6: Dirty
      Bits 7: Page Size (for huge pages at PDE level)
      Bits 12-51: Physical frame number (40 bits → 1 TB physical address)
      Bits 63: NX (No-Execute)

────────────────────────────────────────────────────
3.6.1  Structure of Page Table
────────────────────────────────────────────────────

HIERARCHICAL (MULTI-LEVEL) PAGE TABLE:

To avoid having a single enormous page table, it is broken into multiple
levels. On x86-64, Linux uses a 4-level (or 5-level with LA57) page table:

  Level 4: PGD (Page Global Directory) — 512 entries
  Level 3: PUD (Page Upper Directory) — 512 entries per PGD entry
  Level 2: PMD (Page Middle Directory) — 512 entries per PUD entry
  Level 1: PTE (Page Table Entry) — 512 entries per PMD entry

A 48-bit virtual address is decomposed:
  Bits 47-39: PGD index (9 bits → 512 entries)
  Bits 38-30: PUD index (9 bits)
  Bits 29-21: PMD index (9 bits)
  Bits 20-12: PTE index (9 bits)
  Bits 11-0:  Offset (12 bits → 4 KB page)

Total addressable: $2^{48}$ = 256 TB virtual address space.

Advantage: Only the page table levels that are actually needed are allocated.
A process using only 100 MB of virtual address space doesn't need page table
entries for the other 255.9+ TB.

HASHED PAGE TABLE:

Used for address spaces larger than 32 bits. The virtual page number is
hashed into a hash table. Each entry in the hash table contains a linked list
of elements that hash to the same location. Each element stores:
  (virtual page number, frame number, pointer to next element)

Lookup: Hash the virtual page number, search the chain for a matching VPN.

INVERTED PAGE TABLE:

Instead of one entry per virtual page (per process), the inverted page table
has one entry per physical frame. Each entry stores:
  (process ID, virtual page number)

Lookup: Search the table for (pid, vpn). Since the table is indexed by
physical frame, the frame number is implicit (it's the index).

Size: Fixed at one entry per physical frame, regardless of virtual address
space size. For a system with 4 GB RAM and 4 KB frames: 1,048,576 entries.

Problem: Linear search is slow. Solution: Use a hash table on top of the
inverted page table for O(1) average lookup.

Real-World: PowerPC and IA-64 (Itanium) architectures used inverted page
tables.

SHARED PAGE TABLE:

Multiple processes can share the same physical pages (and their page table
entries) for read-only code. For example, if 100 users run the same editor
(vi), the code pages are shared—only one copy in physical memory. Each
process has its own data and stack pages.

    Micro-topic: Copy-on-Write (CoW) Pages
    ────────────────────────────────────────
    After fork(), the parent and child share all pages (marked read-only).
    When either process writes to a shared page:
      1. A page fault occurs (write to read-only page).
      2. The kernel allocates a new physical frame.
      3. The content of the old frame is copied to the new frame.
      4. The writing process's page table entry is updated to point to the
         new frame (with write permission).
      5. The other process retains the original frame.

    This is much faster than copying the entire address space at fork() time,
    especially when the child immediately calls exec() (which discards the
    address space anyway).


================================================================================
3.7  VIRTUAL MEMORY
================================================================================

Virtual memory is a technique that allows the execution of processes that are
not completely in memory. The main advantage is that programs can be larger
than physical memory. Virtual memory abstracts main memory into an extremely
large, uniform array of storage, separating logical memory as viewed by the
programmer from physical memory.

Benefits:
  - Programs are not constrained by the amount of physical memory.
  - Each process has its own virtual address space, providing isolation.
  - More programs can be in memory simultaneously (only their working sets
    need to be resident), improving CPU utilization and throughput.
  - Less I/O needed to load or swap processes.

────────────────────────────────────────────────────
3.7.1  Demand Paging
────────────────────────────────────────────────────

Demand paging is the most common implementation of virtual memory. Pages are
loaded into memory only when they are needed (on demand), not at process
start time.

  - Lazy Swapper (Pager): Never brings a page into memory until it is needed.
  - When a process references a page that is not in memory, a page fault
    occurs.

PAGE FAULT HANDLING:

  1. The CPU generates a logical address and consults the page table.
  2. The valid/present bit in the PTE is 0 → PAGE FAULT TRAP.
  3. The OS checks: Is this a valid reference? (Is the address within the
     process's virtual address space?)
     - If invalid: Terminate the process (segmentation fault).
     - If valid but page not in memory: Continue to step 4.
  4. Find a free frame in physical memory.
     - If no free frame: Invoke the page replacement algorithm to select
       a victim frame.
  5. Read the desired page from disk (swap space or file) into the free frame.
  6. Update the page table: set the frame number and set the present bit to 1.
  7. Restart the instruction that caused the page fault.

EFFECTIVE ACCESS TIME WITH DEMAND PAGING:

Let:
  $p$ = page fault rate (probability of a page fault, $0 \leq p \leq 1$)
  $t_m$ = memory access time (~100 ns)
  $t_{pf}$ = page fault service time (~10 ms = 10,000,000 ns)

$$EAT = (1 - p)\,t_m + p\,t_{pf}$$

Example: If $p$ = 1/1000 (one page fault per 1000 accesses):
$$EAT = (1 - 0.001)\cdot 100 + 0.001\cdot 10{,}000{,}000$$
$$= 99.9 + 10{,}000 = 10{,}099.9\,\mathrm{ns}$$

That's a 100x slowdown! This shows that even a small page fault rate
dramatically affects performance.

────────────────────────────────────────────────────
3.7.2  Page Table (TLB Acceleration)
────────────────────────────────────────────────────

Every memory reference requires consulting the page table, which is itself
stored in memory. This means every data/instruction access requires TWO
memory accesses: one to the page table and one to the actual data. This
doubles the effective memory access time.

Solution: Translation Lookaside Buffer (TLB)

The TLB is a small, fast, fully-associative cache in the MMU that stores
recent virtual-to-physical page translations. Modern TLBs have:
  - L1 dTLB (data): ~64 entries, ~0.5 ns access
  - L1 iTLB (instruction): ~64 entries
  - L2 TLB (unified): ~1024-2048 entries, ~5-7 ns access

TLB LOOKUP PROCESS:
  1. CPU generates virtual address → extract page number.
  2. Search TLB for the page number (parallel/associative search).
  3. TLB Hit: Get frame number from TLB → form physical address → access
     memory (1 memory access total).
  4. TLB Miss: Access page table in memory → get frame number → load entry
     into TLB → access memory (2 memory accesses).
  5. If page table lookup finds present bit = 0 → page fault.

EFFECTIVE ACCESS TIME WITH TLB:

Let:
  $h$ = TLB hit ratio
  $t_{tlb}$ = TLB access time (~1 ns, often overlapped with cache access)
  $t_m$ = memory access time (~100 ns)

$$EAT = h\,(t_{\mathrm{TLB}} + t_m) + (1-h)\,(t_{\mathrm{TLB}} + 2t_m)$$

If TLB access is overlapped with cache access (common):
$$EAT = h\,t_m + (1-h)\,2t_m = (1 + (1-h))\,t_m$$
$$= (2-h)\,t_m$$

Example: h = 0.99, $t_m$ = 100 ns:
$$EAT = (2-0.99)\cdot 100 = 1.01\cdot 100 = 101\,\mathrm{ns}$$

Only 1% overhead! This is why high TLB hit rates are crucial.

────────────────────────────────────────────────────
3.7.3  Block Mapping and Direct Mapping
────────────────────────────────────────────────────

BLOCK MAPPING: The entire virtual address space is divided into fixed-size
blocks. A mapping table translates block numbers to physical locations. This
is the generalized concept behind both paging (block = page) and segmentation
(block = segment).

DIRECT MAPPING: A simplified address translation where the virtual address
directly indexes into a single-level page table without any intermediate
levels. This is only practical for small address spaces.

────────────────────────────────────────────────────
3.7.4  Thrashing
────────────────────────────────────────────────────

Thrashing occurs when a system spends more time paging (swapping pages in and
out) than executing useful work. It happens when the total memory demand of
all active processes exceeds the available physical memory.

Symptoms:
  - Extremely high page fault rate.
  - CPU utilization drops dramatically (CPU is idle waiting for pages to be
    read from disk).
  - Disk I/O is at 100%.
  - System becomes unresponsive.

Cause: Too many processes competing for too little memory. Each process has
fewer frames than its working set requires, so every page it needs causes a
fault, evicting a page that another process needs.

The WORKING SET MODEL:
  The working set $W(t, \Delta)$ of a process at time $t$ is the set of pages
  referenced in the most recent $\Delta$ time units (the working-set window).
  The working set size (WSS) varies over time.

  $$D = \sum_{i} WSS_i$$

  Where $D$ = total demand for frames. If $D >$ total available frames $m$,
  then thrashing occurs.

  Prevention: The OS should admit a new process only if:
  $$\sum_{i} WSS_i + WSS_{new} \leq m$$

    Micro-topic: The OOM Killer in Linux
    ─────────────────────────────────────
    When Linux runs critically low on memory and swap, the Out-of-Memory
    (OOM) Killer is invoked. It selects a process to kill based on a
    heuristic score (oom_score) that considers memory usage, nice value, and
    other factors. Each process's score is visible at:
      /proc/<pid>/oom_score

    You can adjust the likelihood of a process being killed:
      /proc/<pid>/oom_score_adj  (range: -1000 to 1000)
    Setting -1000 makes it exempt from the OOM killer (use with caution).


================================================================================
3.8  PAGE REPLACEMENT ALGORITHMS
================================================================================

When a page fault occurs and there are no free frames, the OS must choose a
victim page to evict. The goal is to minimize the number of page faults.

OPTIMAL UPPER BOUND (Bélády's Theorem):
No algorithm can produce fewer page faults than the optimal algorithm, which
replaces the page that will not be used for the longest period in the future.
This is theoretical (requires future knowledge) but serves as a benchmark.

Bélády's Anomaly: For some algorithms (notably FIFO), increasing the number
of frames can actually INCREASE the number of page faults! This counter-
intuitive behavior is called Bélády's anomaly. Stack-based algorithms (LRU,
Optimal) are immune to this anomaly.

═══════════════════════════════════════════════════
ALGORITHM 1: FIRST-IN-FIRST-OUT (FIFO)
═══════════════════════════════════════════════════

FIFO replaces the page that has been in memory the longest (the "oldest" page).
Implemented with a simple queue: when a page is loaded, it's added to the tail;
when a replacement is needed, the page at the head is evicted.

Simple to implement but poor performance because the oldest page might be
frequently used.

═══════════════════════════════════════════════════
ALGORITHM 3: LEAST RECENTLY USED (LRU)
═══════════════════════════════════════════════════

LRU replaces the page that has not been used for the longest period of time.
It is based on the principle of temporal locality: if a page hasn't been used
recently, it's unlikely to be used in the near future.

LRU is a good approximation of the optimal algorithm (looking backward
instead of forward). It does not suffer from Bélády's anomaly.

Implementation approaches:
  - Counter-based: Each page has a "last used" timestamp. On every memory
    reference, update the counter. Replace the page with the smallest
    counter value. Requires searching all pages on replacement.
  - Stack-based: Maintain a stack of page numbers. On every reference, move
    the referenced page to the top. The bottom of the stack is the LRU page.
    O(1) replacement but O(n) update (doubly-linked list with hash table
    can achieve O(1) for both).

═══════════════════════════════════════════════════
ALGORITHM 4: NOT RECENTLY USED (NRU)
═══════════════════════════════════════════════════

NRU uses the Referenced (R) and Modified (M) bits (maintained by hardware)
to classify pages into four categories:

  Class 0: Not referenced, not modified  (R=0, M=0)
  Class 1: Not referenced, modified      (R=0, M=1)
  Class 2: Referenced, not modified       (R=1, M=0)
  Class 3: Referenced, modified           (R=1, M=1)

Periodically (e.g., every clock tick), the R bit is cleared for all pages
(to distinguish recently referenced from long-ago referenced). The M bit is
NOT cleared (needed to know if the page must be written to disk).

On a page fault, NRU removes a random page from the lowest non-empty class.
This favors removing unmodified pages (no write-back needed) over modified
pages, and unreferenced over referenced.


═══════════════════════════════════════════════════
ALGORITHM 5: SECOND CHANCE (CLOCK) PAGE REPLACEMENT
═══════════════════════════════════════════════════

Second Chance is a modification of FIFO that gives pages a "second chance"
before eviction by checking the Referenced bit.

Algorithm:
  1. Examine the oldest page (head of FIFO queue).
  2. If its R bit is 0: Evict it.
  3. If its R bit is 1: Clear the R bit, move the page to the tail of the
     queue (give it a second chance), and repeat with the next oldest page.

If all pages have R=1, the algorithm degenerates to FIFO (after clearing all
R bits, it evicts the original oldest page).

CLOCK PAGE REPLACEMENT is an efficient implementation of Second Chance using
a circular list (clock) with a "clock hand" pointer instead of physically
moving pages in a queue.

────────────────────────────

═══════════════════════════════════════════════════
ALGORITHM 6: WORKING SET PAGE REPLACEMENT
═══════════════════════════════════════════════════

Based on the working set model. The working set at time $t$ with window
$\Delta$ is the set of pages referenced in the last $\Delta$ time units.

On a page fault, evict a page that is NOT in the working set (i.e., has not
been referenced in the last $\Delta$ time units). If all pages are in the
working set, evict the one with the oldest reference time.

This algorithm adapts to the process's locality and resists thrashing.


═══════════════════════════════════════════════════
ALGORITHM 7: WSCLOCK PAGE REPLACEMENT
═══════════════════════════════════════════════════

WSClock combines the Working Set and Clock algorithms. It uses a circular
list (like Clock) but considers the working set window $\Delta$ when deciding
whether to evict a page:

  1. If the page has R=1: Clear R, advance the hand.
  2. If R=0 and age > $\Delta$ (not in working set):
     a. If not dirty: Evict it.
     b. If dirty: Schedule a write-back, advance the hand.
  3. If R=0 and age ≤ $\Delta$: The page is in the working set; skip it.

WSClock is widely used in practice because it is efficient (O(1) amortized)
and adapts to the process's working set.


================================================================================
3.9  SEGMENTATION
================================================================================

Segmentation is a memory management scheme that supports the programmer's view
of memory. Instead of a single linear address space, a program's memory is
divided into logical segments:
  - Code segment
  - Data segment (global variables)
  - Stack segment
  - Heap segment
  - Shared library segments

Each segment has a name (or number), a base address, and a length. A logical
address consists of a pair: <segment-number, offset>.

The Segment Table maps segment numbers to physical addresses:
  ┌─────────────┬──────────┬───────────┐
  │ Segment No. │   Base   │   Limit   │
  ├─────────────┼──────────┼───────────┤
  │      0      │  0x1000  │   0x400   │
  │      1      │  0x4000  │   0x800   │
  │      2      │  0x8000  │   0x200   │
  └─────────────┴──────────┴───────────┘

Address translation:
  If offset < limit[segment]:
      physical_address = base[segment] + offset
  Else:
      SEGMENTATION FAULT

Advantages:
  - Natural protection between segments (each has its own permissions).
  - Segments can grow/shrink independently.
  - Sharing is natural (share a code segment between processes).

Disadvantage:
  - External fragmentation (segments are variable-sized).

────────────────────────────────────────────────────
3.9.1  Segmentation with Paging
────────────────────────────────────────────────────

To combine the benefits of segmentation (logical division, protection) with
the benefits of paging (no external fragmentation), some systems use
segmentation with paging:

  1. The logical address is first divided into segment + offset.
  2. The segment table entry points to a page table for that segment.
  3. The offset is further divided into page number + page offset.
  4. The page table gives the physical frame number.

This was used in Intel 80386 (x86-32) with its GDT/LDT segments and paging.
However, modern x86-64 (long mode) effectively uses flat segmentation (all
segment bases = 0, limits = max) and relies purely on paging for memory
management. Segmentation is largely vestigial on x86-64.

    Micro-topic: Intel x86 Segmentation — History and Legacy
    ─────────────────────────────────────────────────────────
    The Intel 8086 (1978) used segmentation as its primary memory management
    mechanism (16-bit segments shifted left 4 bits + 16-bit offset = 20-bit
    physical address). The 80286 added protected-mode segmentation with
    privilege levels. The 80386 added paging on top of segmentation.

    Modern x86-64 (AMD64) simplifies this:
      - In long mode (64-bit), segment bases for CS, DS, ES, SS are forced
        to 0, and segment limits are ignored.
      - Only FS and GS segment registers retain their base addresses (used
        for Thread-Local Storage).
      - Paging is the sole memory management mechanism.


================================================================================
3.10  COALESCING AND COMPACTION
================================================================================

COALESCING is the process of merging adjacent free memory blocks into a single
larger block. When a process releases memory, the memory manager checks whether
the neighboring blocks are also free. If so, they are combined.

  Before coalescing:  |USED|FREE|FREE|USED|FREE|
  After coalescing:   |USED|  FREE   |USED|FREE|

Coalescing is done automatically in the buddy system (merging buddies) and
in the malloc() implementation's free list management.

COMPACTION is the process of rearranging memory contents to place all free
memory together in one large block, eliminating external fragmentation.

  Before compaction:  |P1|FREE|P2|FREE|P3|FREE|
  After compaction:   |P1|P2|P3|       FREE      |

Compaction is expensive:
  - Requires copying processes in memory.
  - All address references must be updated (or use dynamic relocation).
  - The system must be paused during compaction (stop-the-world).

Modern systems avoid compaction through paging (which eliminates external
fragmentation entirely). However, compaction is still relevant in:
  - Garbage collectors (e.g., Java GC's compaction phase).
  - Linux's memory compaction for huge pages (compaction daemon).

    Micro-topic: Linux Memory Compaction for Huge Pages
    ───────────────────────────────────────────────────
    Linux can use 2 MB or 1 GB "huge pages" (via Transparent Huge Pages or
    hugetlbfs) to reduce TLB misses. However, allocating a contiguous 2 MB
    block may fail due to fragmentation. The kernel's kcompactd daemon
    performs memory compaction: it migrates pages to consolidate free memory
    into contiguous blocks, making huge page allocation possible.
