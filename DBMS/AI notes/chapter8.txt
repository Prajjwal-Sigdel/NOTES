8.1  TRANSACTION CONCEPTS
================================================================================

■ FORMAL DEFINITION
────────────────────
A **Transaction** is a logical unit of work that consists of one or more
database operations (reads, writes, insertions, deletions) that must be
executed as a SINGLE, INDIVISIBLE unit. Either ALL operations in the
transaction complete successfully, or NONE of them take effect.

■ IN-DEPTH EXPLANATION
───────────────────────
A transaction represents a real-world event that transforms the database
from one **consistent state** to another consistent state.

Example — Bank Transfer of ₹5000 from Account A to Account B:

  Transaction T₁:
    1. read(A)          -- Read balance of A
    2. A := A - 5000    -- Deduct ₹5000 from A
    3. write(A)         -- Write updated A back to DB
    4. read(B)          -- Read balance of B
    5. B := B + 5000    -- Add ₹5000 to B
    6. write(B)         -- Write updated B back to DB

If the system crashes after step 3 but before step 6, ₹5000 disappears!
The transaction mechanism PREVENTS this by ensuring either all 6 steps
complete, or none take effect.

■ TRANSACTION OPERATIONS
─────────────────────────
  • **BEGIN TRANSACTION** — Marks the start of a transaction.
  • **COMMIT** — Makes all changes permanent. Signals successful end.
  • **ROLLBACK (ABORT)** — Undoes all changes. Signals failure.
  • **SAVEPOINT** — Creates intermediate checkpoint within a transaction.

■ SQL SYNTAX
─────────────
  BEGIN TRANSACTION;
    UPDATE account SET balance = balance - 5000 WHERE acc_id = 'A';
    UPDATE account SET balance = balance + 5000 WHERE acc_id = 'B';
  COMMIT;

  -- If error occurs:
  ROLLBACK;

================================================================================

A transaction goes through the following states:

    Aborted --> [*]

  │   │ FAILED │                     │ COMMITTED │ │ FAILED │     │
  │   └───┬────┘                     └───────────┘ └───┬────┘     │
  │       │                                            │           │
  │       │ rollback complete                          │           │
  │       ▼                                            ▼           │
  │   ┌─────────┐                              ┌─────────┐       │

■ STATE DESCRIPTIONS
─────────────────────
  ┌─────────────────────┬─────────────────────────────────────────────┐
  │ State               │ Description                                 │
  ├─────────────────────┼─────────────────────────────────────────────┤
  │ Active              │ Initial state. Transaction is executing     │
  │                     │ its operations normally.                    │
  │ Partially Committed │ After the last statement has executed.      │
  │                     │ Changes are in buffer, not yet on disk.     │
  │ Committed           │ Changes are permanently written to disk.    │
  │                     │ Transaction completed successfully.         │
  │ Failed              │ Normal execution can no longer proceed      │
  │                     │ (error, constraint violation, crash).       │
  │ Aborted             │ Transaction has been rolled back. All       │
  │                     │ changes undone. DB restored to prior state. │
  └─────────────────────┴─────────────────────────────────────────────┘

After ABORT, the system can either:
  1. **Restart** the transaction (if failure was due to hardware/software).
  2. **Kill** the transaction (if failure was due to logical error).

8.3  ACID PROPERTIES
================================================================================

■ FORMAL DEFINITION
────────────────────
The **ACID properties** are four fundamental properties that guarantee
database transactions are processed reliably:

  ┌──────────────────────────────────────────────────────────────────────┐
  │                        A C I D                                      │
  │                                                                      │
  │  A = Atomicity          "All or Nothing"                             │
  │  C = Consistency        "Correct state to correct state"             │
  │  I = Isolation          "As if running alone"                        │
  │  D = Durability         "Once committed, forever"                    │
  └──────────────────────────────────────────────────────────────────────┘

■ DETAILED EXPLANATION OF EACH PROPERTY
─────────────────────────────────────────

**1. ATOMICITY** — "All or Nothing"
  Either ALL operations of the transaction execute, or NONE do.
  If a transaction fails midway, all changes are rolled back.

  Ensured by: **Recovery System** (undo logs).

  Example: In the bank transfer, if the system crashes after debiting A
  but before crediting B, atomicity ensures the debit is rolled back.

**2. CONSISTENCY** — "Preserves correctness"
  A transaction transforms the database from one CONSISTENT state to
  another. All integrity constraints are satisfied before and after.

  Ensured by: **Application logic** + **Integrity constraints**.

  Example: If total money in the system = ₹100,000 before the transfer,
  it must still be ₹100,000 after. (A + B remains constant.)

**3. ISOLATION** — "Concurrent transactions don't interfere"
  Each transaction executes as if it were the ONLY transaction in the
  system. Intermediate states of one transaction are invisible to others.

  Ensured by: **Concurrency Control System** (locks, timestamps, MVCC).

  Example: While T₁ is transferring money, T₂ reading the balance
  should see either the state BEFORE T₁ or AFTER T₁, never a partial
  state (A debited but B not yet credited).

**4. DURABILITY** — "Committed changes survive crashes"
  Once a transaction is committed, its changes persist permanently,
  even if the system crashes immediately after.

  Ensured by: **Recovery System** (redo logs, write-ahead logging).

  Example: If the system acknowledges "Transfer complete" and then
  crashes, the transfer must still be reflected after recovery.

■ ACID PROPERTY ↔ SYSTEM COMPONENT MAPPING
────────────────────────────────────────────
  ┌───────────────┬────────────────────────────────────────┐
  │ Property      │ Ensured By                             │
  ├───────────────┼────────────────────────────────────────┤
  │ Atomicity     │ Recovery System (undo operations)      │
  │ Consistency   │ Application + Integrity Constraints    │
  │ Isolation     │ Concurrency Control System             │
  │ Durability    │ Recovery System (redo operations)      │
  └───────────────┴────────────────────────────────────────┘

8.4  SERIALIZABILITY
================================================================================

■ FORMAL DEFINITION
────────────────────
A **schedule** (or history) is an interleaved sequence of operations
from multiple concurrent transactions. A schedule is **serializable**
if its effect is equivalent to SOME serial schedule (one transaction at
a time, no interleaving).

■ SERIAL vs NON-SERIAL SCHEDULES
──────────────────────────────────
  **Serial Schedule**: Transactions execute one after another, no
  interleaving. Always correct, but poor performance (no concurrency).

  **Non-Serial Schedule**: Operations from different transactions are
  interleaved. Better performance, but may produce incorrect results
  if not properly controlled.

  Example with T₁ and T₂:

  Serial Schedule (T₁ before T₂):    Non-Serial Schedule:
    T₁: read(A)                         T₁: read(A)
    T₁: write(A)                        T₂: read(A)    ← interleaved
    T₁: read(B)                         T₁: write(A)
    T₁: write(B)                        T₂: write(A)   ← interleaved
    T₂: read(A)                         T₁: read(B)
    T₂: write(A)                        T₁: write(B)
                                         T₂: read(B)
                                         T₂: write(B)

■ CONFLICTING OPERATIONS
──────────────────────────
Two operations CONFLICT if:
  1. They belong to DIFFERENT transactions.
  2. They access the SAME data item.
  3. At least one of them is a WRITE operation.

  Types of conflicts:
  • **Read-Write (RW)** conflict: T₁ reads X, T₂ writes X.
  • **Write-Read (WR)** conflict: T₁ writes X, T₂ reads X.
  • **Write-Write (WW)** conflict: T₁ writes X, T₂ writes X.

  Non-conflicting: Two reads, or operations on different data items.

────────────────────────────────────────────────
8.4.1  CONFLICT SERIALIZABILITY
────────────────────────────────────────────────

■ DEFINITION
─────────────
A schedule S is **conflict serializable** if it can be transformed into
a serial schedule by swapping CONSECUTIVE NON-CONFLICTING operations.

■ TESTING: PRECEDENCE GRAPH (SERIALIZATION GRAPH)
───────────────────────────────────────────────────
  1. Create a node for each transaction.
  2. Add a directed edge Tᵢ → Tⱼ if:
     - Tᵢ and Tⱼ have conflicting operations, AND
     - Tᵢ's conflicting operation comes BEFORE Tⱼ's.
  3. The schedule is conflict serializable if and only if the
     precedence graph has **NO CYCLE**.

■ EXAMPLE
──────────
  Schedule S:
    T₁: read(A)
    T₂: read(A)
    T₁: write(A)
    T₂: write(A)
    T₁: read(B)
    T₂: read(B)
    T₁: write(B)
    T₂: write(B)

  Conflicts:
    T₁.read(A) — T₂.write(A) → T₁ before T₂ → edge T₁→T₂
    T₂.read(A) — T₁.write(A) → T₂ before T₁ → edge T₂→T₁
    T₁.read(B) — T₂.write(B) → T₁ before T₂ → edge T₁→T₂
    T₂.read(B) — T₁.write(B) → T₂ before T₁ → edge T₂→T₁

  Precedence Graph:
    T₁ ⇄ T₂  (cycle exists!)

  ∴ NOT conflict serializable.

■ ANOTHER EXAMPLE
──────────────────
  Schedule S':
    T₁: read(A)
    T₁: write(A)
    T₂: read(A)
    T₂: write(A)
    T₁: read(B)
    T₁: write(B)
    T₂: read(B)
    T₂: write(B)

  Conflicts: All point T₁ → T₂ (T₁ always comes first).
  Precedence Graph: T₁ → T₂ (no cycle).
  ∴ Conflict serializable. Equivalent to serial schedule T₁, T₂.

────────────────────────────────────────────────
8.4.2  VIEW SERIALIZABILITY
────────────────────────────────────────────────

■ DEFINITION
─────────────
A schedule S is **view serializable** if it is **view equivalent** to
some serial schedule. Two schedules S and S' are view equivalent if:

  1. **Initial Read**: If Tᵢ reads the initial value of data item Q in
     S, then Tᵢ must also read the initial value of Q in S'.
  2. **Updated Read**: If Tᵢ reads a value of Q written by Tⱼ in S,
     then Tᵢ must also read the value of Q written by Tⱼ in S'.
  3. **Final Write**: If Tᵢ performs the final write on Q in S, then
     Tᵢ must also perform the final write on Q in S'.

■ RELATIONSHIP BETWEEN SERIALIZABILITY TYPES
──────────────────────────────────────────────

  ┌──────────────────────────────────────────────────────────┐
  │              All Schedules                                │
  │  ┌────────────────────────────────────────────────────┐   │
  │  │         View Serializable                          │   │
  │  │  ┌──────────────────────────────────────────────┐  │   │
  │  │  │       Conflict Serializable                  │  │   │
  │  │  │  ┌────────────────────────────────────────┐  │  │   │
  │  │  │  │        Serial Schedules               │  │  │   │
  │  │  │  └────────────────────────────────────────┘  │  │   │
  │  │  └──────────────────────────────────────────────┘  │   │
  │  └────────────────────────────────────────────────────┘   │
  └──────────────────────────────────────────────────────────┘

  • Every conflict serializable schedule is view serializable.
  • View serializable ⊃ Conflict serializable ⊃ Serial.
  • Testing conflict serializability: Polynomial time (precedence graph).
  • Testing view serializability: NP-complete!
  • Practical systems use conflict serializability.

8.5  SQL ISOLATION LEVELS
================================================================================

■ FORMAL DEFINITION
────────────────────
SQL defines four **isolation levels** that control the degree to which
concurrent transactions can see each other's uncommitted changes. Higher
levels provide more isolation but reduce concurrency.

■ CONCURRENCY PROBLEMS (ANOMALIES)
─────────────────────────────────────

  1. **Dirty Read**: Transaction T₂ reads a value written by T₁ that
     has NOT yet been committed. If T₁ aborts, T₂ has read "dirty"
     (invalid) data.

     T₁: write(A=100)          -- not committed
     T₂: read(A) → 100         -- dirty read!
     T₁: ROLLBACK              -- A reverts to original value

  2. **Non-Repeatable Read (Fuzzy Read)**: Transaction T₂ reads A twice,
     and gets DIFFERENT values because T₁ modified and committed A
     between the two reads.

     T₂: read(A) → 100
     T₁: write(A=200); COMMIT
     T₂: read(A) → 200         -- different value!

  3. **Phantom Read**: Transaction T₂ executes a query twice, and gets
     a DIFFERENT SET of rows because T₁ inserted/deleted rows between
     the two executions.

     T₂: SELECT * FROM emp WHERE dept='CS' → {Alice, Bob}
     T₁: INSERT INTO emp ('Charlie','CS'); COMMIT
     T₂: SELECT * FROM emp WHERE dept='CS' → {Alice, Bob, Charlie}
         -- phantom row appeared!

■ ISOLATION LEVELS TABLE
──────────────────────────

  ┌──────────────────────┬──────────┬────────────────┬──────────────┐
  │ Isolation Level      │ Dirty    │ Non-Repeatable │ Phantom      │
  │                      │ Read     │ Read           │ Read         │
  ├──────────────────────┼──────────┼────────────────┼──────────────┤
  │ READ UNCOMMITTED     │ Possible │ Possible       │ Possible     │
  │ READ COMMITTED       │ Prevented│ Possible       │ Possible     │
  │ REPEATABLE READ      │ Prevented│ Prevented      │ Possible     │
  │ SERIALIZABLE         │ Prevented│ Prevented      │ Prevented    │
  └──────────────────────┴──────────┴────────────────┴──────────────┘

  ↑ Increasing isolation (and decreasing concurrency/performance)

■ SQL SYNTAX
─────────────
  SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
  SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

■ REAL-WORLD DEFAULTS
───────────────────────
  • PostgreSQL: READ COMMITTED (default)
  • MySQL InnoDB: REPEATABLE READ (default)
  • Oracle: READ COMMITTED (default)
  • SQL Server: READ COMMITTED (default)

8.6  CONCURRENCY CONTROL
================================================================================

■ WHY CONCURRENCY CONTROL?
───────────────────────────
Without concurrency control, concurrent transactions can lead to:
  1. **Lost Update**: Two transactions update the same item; one update
     is lost.
  2. **Dirty Read**: Reading uncommitted data.
  3. **Inconsistent Analysis**: Reading partial results of another
     transaction.
  4. **Non-Repeatable Read / Phantom Read**.

Concurrency control ensures that the concurrent execution is equivalent
to SOME serial execution (serializability).

────────────────────────────────────────────────
8.6.1  LOCK-BASED PROTOCOLS
────────────────────────────────────────────────

■ FORMAL DEFINITION
────────────────────
In **lock-based protocols**, a transaction must acquire a **lock** on a
data item before accessing it. The lock controls concurrent access.

■ LOCK TYPES
──────────────
  ┌────────────────────┬───────────────────────────────────────────────┐
  │ Lock Type          │ Description                                   │
  ├────────────────────┼───────────────────────────────────────────────┤
  │ Shared Lock (S)    │ Acquired for READ operations.                 │
  │                    │ Multiple transactions can hold S locks on the │
  │                    │ same item simultaneously.                     │
  │ Exclusive Lock (X) │ Acquired for WRITE operations.                │
  │                    │ Only ONE transaction can hold an X lock.       │
  │                    │ No other lock (S or X) can coexist.           │
  └────────────────────┴───────────────────────────────────────────────┘

■ LOCK COMPATIBILITY MATRIX
─────────────────────────────
                     Existing Lock
                  ┌──────────┬──────────┐
                  │    S     │    X     │
    ┌─────────────┼──────────┼──────────┤
    │ Request S   │   YES    │   NO     │
    │ Request X   │   NO     │   NO     │
    └─────────────┴──────────┴──────────┘

  • S + S = Compatible (both can read simultaneously).
  • S + X = NOT Compatible (reader must wait for writer, or vice versa).
  • X + X = NOT Compatible (writers must be serialized).

■ LOCK OPERATIONS
──────────────────
  • lock-S(Q): Request shared lock on data item Q.
  • lock-X(Q): Request exclusive lock on data item Q.
  • unlock(Q): Release the lock on data item Q.

  A transaction must wait (block) if it requests a lock that conflicts
  with an existing lock held by another transaction.

■ LOCK UPGRADE AND DOWNGRADE
──────────────────────────────
  • **Upgrade**: S lock → X lock (when a transaction that was reading
    now wants to write). Possible only if no other transaction holds S.
  • **Downgrade**: X lock → S lock (after writing, allow others to read).

■ PROBLEMS WITH SIMPLE LOCKING
────────────────────────────────
  Simple "lock before access, unlock after use" is NOT sufficient to
  guarantee serializability.

  Example (incorrect):
    T₁: lock-X(A), write(A), unlock(A), lock-X(B), write(B), unlock(B)
    T₂: lock-X(A), write(A), unlock(A), lock-X(B), write(B), unlock(B)

  If T₂ acquires lock on A after T₁ releases it but before T₁ locks B,
  T₂ sees T₁'s update to A but not B → inconsistent state!

  SOLUTION: Two-Phase Locking (2PL).

────────────────────────────────────────────────
8.6.2  TWO-PHASE LOCKING (2PL) PROTOCOL
────────────────────────────────────────────────

■ FORMAL DEFINITION
────────────────────
The **Two-Phase Locking (2PL)** protocol requires that each transaction
acquires and releases locks in TWO DISTINCT PHASES:

  **Phase 1 — Growing Phase**: Transaction may acquire (lock) new locks
  but may NOT release any locks.

  **Phase 2 — Shrinking Phase**: Transaction may release (unlock) locks
  but may NOT acquire any new locks.

  ┌──────────────────────────────────────────────────────────────────┐
  │                                                                  │
  │   Number of     ╱╲                                               │
  │   Locks held   ╱  ╲                                              │
  │               ╱    ╲                                             │
  │              ╱      ╲                                            │
  │             ╱        ╲                                           │
  │            ╱          ╲                                          │
  │    ───────╱────────────╲───────────                              │
  │          Growing     Shrinking                                   │
  │          Phase       Phase                                       │
  │                 ↑                                                 │
  │            Lock Point                                            │
  │     (point where all locks acquired)                             │
  │                                                                  │
  └──────────────────────────────────────────────────────────────────┘

■ 2PL GUARANTEES CONFLICT SERIALIZABILITY
───────────────────────────────────────────
  **Theorem**: If all transactions follow 2PL, then all resulting
  schedules are conflict serializable.

  The serialization order corresponds to the order of lock points.

■ VARIANTS OF 2PL
───────────────────

  ┌───────────────────┬──────────────────────────────────────────────────┐
  │ Variant           │ Description                                      │
  ├───────────────────┼──────────────────────────────────────────────────┤
  │ Basic 2PL         │ Locks released in shrinking phase (as described).│
  │                   │ Guarantees serializability.                       │
  │                   │ BUT may cause CASCADING ROLLBACKS.               │
  │                   │                                                  │
  │ Strict 2PL        │ All EXCLUSIVE (X) locks held until COMMIT/ABORT.│
  │                   │ Prevents cascading rollbacks.                     │
  │                   │ Most commonly used in practice.                  │
  │                   │                                                  │
  │ Rigorous 2PL      │ ALL locks (S and X) held until COMMIT/ABORT.    │
  │                   │ Most restrictive. Simplest to implement.         │
  │                   │ Serialization order = commit order.              │
  └───────────────────┴──────────────────────────────────────────────────┘

■ WHY STRICT 2PL?
───────────────────
  Basic 2PL can cause **cascading rollbacks**:
    T₁ releases a lock, T₂ reads the unlocked item.
    If T₁ later aborts, T₂ must also abort (read dirty data),
    and any transaction that read T₂'s data must also abort, etc.

  Strict 2PL avoids this by holding X locks until commit.

■ EXAMPLE OF 2PL
──────────────────
  Correct 2PL schedule for T₁ (transfer):
    T₁: lock-X(A)      -- Growing phase
    T₁: read(A)
    T₁: A := A - 5000
    T₁: write(A)
    T₁: lock-X(B)      -- Still growing phase
    T₁: read(B)
    T₁: B := B + 5000
    T₁: write(B)
    T₁: unlock(A)      -- Shrinking phase begins
    T₁: unlock(B)

  In Strict 2PL: unlock(A) and unlock(B) happen ONLY at COMMIT.

────────────────────────────────────────────────
8.6.3  GRAPH-BASED PROTOCOLS (TREE PROTOCOL)
────────────────────────────────────────────────

■ FORMAL DEFINITION
────────────────────
**Graph-Based Protocols** impose an ordering on data items and require
transactions to lock items according to this ordering. The most common
is the **Tree Protocol** where data items form a tree (hierarchy).

■ TREE PROTOCOL RULES
───────────────────────
  Assume data items are organized in a tree (e.g., database indices):

  1. Only **exclusive (X)** locks are used.
  2. The FIRST lock can be on ANY data item.
  3. Subsequently, a data item Q can be locked only if the PARENT of Q
     is CURRENTLY locked by the same transaction.
  4. Data items may be UNLOCKED at any time (no two-phase restriction).
  5. A data item that has been locked and unlocked CANNOT be locked
     again by the same transaction.

■ EXAMPLE
──────────

  Data item tree:
            A
           / \
          B   C
         / \
        D   E

  Valid lock sequence: lock(A), lock(B), lock(D), unlock(A), lock(E)
    ✓ B's parent A was locked when B was locked.
    ✓ D's parent B was locked when D was locked.
    ✓ E's parent B was locked when E was locked.

  Invalid: lock(D) first (D is not a root, and its parent B is not
  locked). Also invalid: lock(C), lock(B) (B's parent A not locked).

■ ADVANTAGES AND DISADVANTAGES
────────────────────────────────
  ✓ Ensures conflict serializability.
  ✓ DEADLOCK-FREE (no cycles possible in lock acquisition).
  ✓ Earlier unlock than 2PL → potentially better concurrency.

  ✗ Does NOT guarantee recoverability or cascade-freedom.
  ✗ May lock items unnecessarily (must lock parent to lock child).
  ✗ Requires knowledge of the data item tree structure in advance.


================================================================================
8.7  DEADLOCK HANDLING
================================================================================

■ FORMAL DEFINITION
────────────────────
A **Deadlock** occurs when two or more transactions are waiting for
each other to release locks, creating a CIRCULAR WAIT where none can
proceed.

■ EXAMPLE
──────────
  T₁: lock-X(A)         -- T₁ holds lock on A
  T₂: lock-X(B)         -- T₂ holds lock on B
  T₁: lock-X(B)         -- T₁ WAITS for T₂ to release B
  T₂: lock-X(A)         -- T₂ WAITS for T₁ to release A

  DEADLOCK! T₁ waits for T₂, T₂ waits for T₁.

■ DEADLOCK HANDLING APPROACHES
────────────────────────────────

**Approach 1: DEADLOCK PREVENTION**
  Prevent deadlocks from ever occurring using one of:

  a) **Wait-Die** (Non-preemptive):
     Based on timestamps (older = higher priority).
     • If Tᵢ is OLDER than Tⱼ: Tᵢ WAITS for Tⱼ's lock.
     • If Tᵢ is YOUNGER than Tⱼ: Tᵢ DIES (aborts and restarts).

  b) **Wound-Wait** (Preemptive):
     • If Tᵢ is OLDER than Tⱼ: Tᵢ WOUNDS Tⱼ (forces Tⱼ to abort).
     • If Tᵢ is YOUNGER than Tⱼ: Tᵢ WAITS for Tⱼ's lock.

  ┌──────────────────┬────────────────────┬────────────────────┐
  │ Scheme           │ Older requests     │ Younger requests   │
  │                  │ lock held by       │ lock held by       │
  │                  │ younger            │ older              │
  ├──────────────────┼────────────────────┼────────────────────┤
  │ Wait-Die         │ Older WAITS        │ Younger DIES       │
  │ Wound-Wait       │ Older WOUNDS       │ Younger WAITS      │
  │                  │ (kills younger)    │                    │
  └──────────────────┴────────────────────┴────────────────────┘

  Both guarantee: older transactions are never aborted in favor of
  younger ones → no starvation (a transaction eventually becomes the
  oldest).

  c) **Timeout-Based**: If a transaction waits for a lock longer than a
     threshold, assume deadlock and abort it. Simple but may cause
     unnecessary aborts.

  d) **Lock Ordering**: All transactions lock items in a predefined
     global order → prevents circular wait.

**Approach 2: DEADLOCK DETECTION & RECOVERY**
  Allow deadlocks to occur, then detect and resolve them.

  Detection: Build a **Wait-For Graph**.
    • Node for each transaction.
    • Edge Tᵢ → Tⱼ if Tᵢ is waiting for a lock held by Tⱼ.
    • Deadlock exists if and only if the graph has a **CYCLE**.

  ┌────────────────────────────────────────────┐
  │ Wait-For Graph:                             │
  │     T₁ → T₂ → T₃ → T₁   ← CYCLE!        │
  │                                             │
  │ Deadlock detected!                          │
  └────────────────────────────────────────────┘

  Recovery: Choose a **victim** transaction to abort.
    Selection criteria:
    • Choose the youngest transaction (least work lost).
    • Choose the one holding fewest locks.
    • Choose the one closest to completion (to minimize wasted work).
    • Avoid starving any transaction (limit rollback count).

■ STARVATION
─────────────
A transaction may be repeatedly chosen as the deadlock victim → it
never completes. Solution: include the number of rollbacks as a factor
in victim selection. If a transaction has been rolled back too many
times, give it priority.

■ INTERVIEW ESSENTIALS
───────────────────────
  Q: What is 2PL? Does it prevent deadlocks?
  A: 2PL requires all locks to be acquired before any are released
     (growing then shrinking phase). It guarantees conflict
     serializability but does NOT prevent deadlocks. Deadlocks can
     still occur when two transactions each hold locks the other needs.

  Q: Difference between Wait-Die and Wound-Wait?
  A: Wait-Die: older waits, younger aborts. Wound-Wait: older kills
     younger, younger waits. Both prevent deadlocks by ordering
     transactions by timestamp. Wound-Wait tends to do fewer rollbacks.

  Q: What is the difference between Strict 2PL and Rigorous 2PL?
  A: Strict 2PL holds all exclusive locks until commit/abort (prevents
     cascading rollbacks). Rigorous 2PL holds ALL locks (shared and
     exclusive) until commit/abort (serialization order = commit order).
