5.1  INTRODUCTION
================================================================================

Input/Output (I/O) management is one of the most complex and diverse areas of
operating system design. The OS must manage a staggeringly wide variety of
devices — from keyboards and mice to high-speed NVMe SSDs, GPUs, network
interfaces, sensors, and USB peripherals — each with different speeds, data
formats, control protocols, and error conditions. The range of I/O device
speeds spans many orders of magnitude: a keyboard generates perhaps 10 bytes
per second, while a modern NVMe SSD can transfer 7 GB/s, and a PCIe 5.0 x16
GPU link can sustain 64 GB/s.

The I/O subsystem of the OS has several key goals:
  1. DEVICE INDEPENDENCE: Application programs should not need to know the
     specific details of the hardware. A program should be able to read from
     a file the same way whether it's stored on an HDD, SSD, USB drive, or
     network share.
  2. UNIFORM NAMING: Devices should be accessible through a consistent naming
     convention (on UNIX: /dev/sda, /dev/nvme0n1, /dev/ttyUSB0).
  3. ERROR HANDLING: Errors should be handled as close to the hardware as
     possible. The device controller handles electrical errors; the driver
     handles protocol errors; the OS handles higher-level errors.
  4. SYNCHRONOUS vs. ASYNCHRONOUS: Most physical I/O is asynchronous
     (interrupt-driven), but application programs find it easier to work with
     synchronous (blocking) I/O. The OS bridges this gap.
  5. BUFFERING: Data often cannot be stored directly at its final destination;
     buffering (single, double, circular) smooths the mismatch between device
     and process speeds.
  6. SHARING vs. DEDICATED: Some devices can be shared (disk drives) while
     others must be dedicated (printers via spooling, tape drives).

    Micro-topic: The I/O Software Layers
    ─────────────────────────────────────
    I/O software is organized into four hierarchical layers:

      ┌───────────────────────────────┐
      │   User-Level I/O Software     │  ← printf(), fread(), etc.
      ├───────────────────────────────┤
      │   Device-Independent OS       │  ← Naming, caching, buffering,
      │   Software                    │     block allocation, protection
      ├───────────────────────────────┤
      │   Device Drivers              │  ← Device-specific control code
      ├───────────────────────────────┤
      │   Interrupt Handlers          │  ← Hardware interrupt processing
      └───────────────────────────────┘

    Each layer hides complexity from the layer above. A user calling
    fread() doesn't know whether the data comes from an NVMe SSD or a
    network socket — the layers abstract it all away.

        Deeper: Everything is a File — The UNIX I/O Philosophy
        ──────────────────────────────────────────────────────
        UNIX (and Linux) implements a powerful abstraction: nearly every
        I/O resource is represented as a file descriptor. This means the
        same system calls (open, read, write, close, ioctl) work on:
          - Regular files (/home/user/data.txt)
          - Devices (/dev/sda, /dev/ttyS0)
          - Pipes (created by pipe())
          - Sockets (network connections)
          - /proc and /sys pseudo-filesystems
          - signalfd, timerfd, eventfd (Linux extensions)

        This unification is achieved through the Virtual File System (VFS)
        layer, which provides a common interface and dispatches operations
        to the appropriate driver or subsystem.

5.2  INTERRUPT HANDLERS
================================================================================

An interrupt is a signal to the CPU that an event requiring attention has
occurred. Interrupts allow the CPU to respond to external events (hardware
interrupts) or exceptional conditions (exceptions/software interrupts)
without continuously polling devices.

TYPES OF INTERRUPTS:

  1. HARDWARE INTERRUPTS (External Interrupts):
     Generated by hardware devices to signal events.
     - Maskable: Can be temporarily disabled by the CPU (e.g., disk
       completion, network packet arrival, keyboard press). Signaled
       through the APIC (Advanced Programmable Interrupt Controller).
     - Non-Maskable (NMI): Cannot be disabled; reserved for critical
       events (memory parity error, hardware watchdog timeout, machine
       check exception).

  2. SOFTWARE INTERRUPTS (Exceptions/Traps):
     Generated by the CPU itself due to:
     - Faults: Recoverable errors (page fault #PF, general protection
       fault #GP, divide-by-zero #DE). The saved RIP points to the
       faulting instruction, allowing retry.
     - Traps: Intentional exceptions (INT 0x80 for system calls on
       32-bit Linux, breakpoint INT 3 for debuggers). The saved RIP
       points to the next instruction.
     - Aborts: Unrecoverable errors (double fault #DF, machine check
       #MC). Recovery is usually impossible.

INTERRUPT HANDLING SEQUENCE:

  1. Device asserts interrupt line → signal reaches the interrupt
     controller (APIC on modern x86).
  2. APIC signals the CPU on its INTR pin.
  3. CPU finishes the current instruction.
  4. CPU acknowledges the interrupt.
  5. CPU saves current state (RFLAGS, CS, RIP, and possibly SS, RSP if
     crossing privilege levels) onto the kernel stack.
  6. CPU disables further interrupts (clears IF flag).
  7. CPU looks up the interrupt vector in the IDT (Interrupt Descriptor
     Table) to find the handler address.
  8. CPU jumps to the interrupt handler (in kernel space).
  9. Handler saves additional registers (pushes them onto the kernel
     stack).
  10. Handler processes the interrupt (reads device status, transfers
      data, acknowledges device).
  11. Handler restores registers and executes IRET to return to the
      interrupted code.

    Micro-topic: Top Half and Bottom Half Processing
    ─────────────────────────────────────────────────
    Interrupt handlers must execute quickly because interrupts are disabled
    (or the interrupt line is masked) during handler execution. Long-running
    work in an interrupt handler would delay other interrupts and increase
    latency. Linux solves this with a two-part approach:

    TOP HALF (Hardirq): The actual interrupt handler registered with
    request_irq(). It runs with interrupts disabled (on that CPU), must be
    very fast, and typically:
      - Acknowledges the interrupt to the hardware.
      - Reads essential data from the device.
      - Schedules bottom-half processing.
      - Returns IRQ_HANDLED.

    BOTTOM HALF: Deferred processing for longer work. Three mechanisms:

      a. Softirqs: Statically defined (at compile time), high-performance.
         Used for networking (NET_TX_SOFTIRQ, NET_RX_SOFTIRQ), block I/O,
         timers, and RCU. Run on ksoftirqd threads when load is high.

      b. Tasklets: Built on softirqs, dynamically allocatable. Simpler
         API. A given tasklet runs on only one CPU at a time. Being phased
         out in favor of threaded IRQs.

      c. Workqueues (most common): Run in kernel thread context (kworker).
         Can sleep, use mutexes. Most flexible. Example: a USB driver's
         interrupt handler copies a few bytes from the device, then
         schedules a workqueue item to process the data.

        Deeper: Threaded Interrupts
        ───────────────────────────
        Modern Linux supports "threaded interrupts" (request_threaded_irq),
        where the top half is a thin "primary" handler and the main work
        runs in a dedicated kernel thread. This allows the handler to:
          - Sleep and use mutexes.
          - Be scheduled by the real-time scheduler (important for PREEMPT_RT).
        The PREEMPT_RT patch converts almost all interrupt handlers to
        threaded interrupts for deterministic latency.

5.3  PRINCIPLES OF I/O HARDWARE
================================================================================

────────────────────────────────────────────────────
5.3.1  I/O Devices
────────────────────────────────────────────────────

I/O devices can be classified along several axes:

BY DATA TRANSFER MODE:
  - Block devices: Transfer data in fixed-size blocks (512 bytes, 4 KB).
    Each block has an address and can be read/written independently.
    Examples: Hard disks, SSDs, USB flash drives, CD/DVD drives.
    In Linux: /dev/sda, /dev/nvme0n1p1.

  - Character devices: Transfer data one character (byte) at a time, in a
    stream, without addressable blocks. Data cannot be seeked.
    Examples: Keyboards, mice, serial ports, terminals, audio devices.
    In Linux: /dev/ttyS0, /dev/input/mice, /dev/random.

  - Network devices: Neither pure block nor character; they produce and
    consume packets. Linux handles them through a separate network
    interface abstraction (not via /dev entries, but via socket API and
    interface names like eth0, wlan0).

BY SPEED:
  ┌──────────────────┬──────────────────────┐
  │ Device           │ Approximate Speed    │
  ├──────────────────┼──────────────────────┤
  │ Keyboard         │ 10 B/s               │
  │ Mouse            │ 100 B/s              │
  │ Serial port      │ 115 KB/s             │
  │ Laser printer    │ 100 KB/s             │
  │ USB 2.0          │ 60 MB/s              │
  │ Gigabit Ethernet │ 125 MB/s             │
  │ USB 3.2 Gen 2    │ 1.25 GB/s            │
  │ SATA III SSD     │ 600 MB/s             │
  │ NVMe SSD (PCIe4) │ 7 GB/s              │
  │ PCIe 5.0 x16 GPU │ 64 GB/s             │
  │ DDR5 RAM         │ 50+ GB/s             │
  └──────────────────┴──────────────────────┘

    Micro-topic: Block Size and Sector Size
    ────────────────────────────────────────
    Traditional HDDs use 512-byte sectors. Modern drives (both HDD and SSD)
    increasingly use 4096-byte (4K) sectors — called "Advanced Format."
    Some drives emulate 512-byte sectors for compatibility (512e) while
    internally using 4K (4Kn = 4K native). Linux file systems typically
    use 4 KB blocks regardless. The relationship:

      Physical sector → Logical sector → FS block → Page
      (4 KB, drive)     (512B, driver)   (4 KB)     (4 KB, VM)

────────────────────────────────────────────────────
5.3.2  Device Controllers
────────────────────────────────────────────────────

A device controller is the electronic component (hardware) that acts as an
intermediary between the CPU/bus and the physical device. The controller:

  1. Converts serial bit streams from the device to blocks of bytes.
  2. Performs error detection/correction (ECC for disks, CRC for networks).
  3. Provides a set of registers (control, status, data) that the CPU
     accesses to communicate with the device.
  4. Contains a buffer to store data temporarily during transfer.

Example — Disk Controller (AHCI for SATA):
  - The CPU writes a command to the controller's command register (e.g.,
    "read sector 12345").
  - The controller activates the disk head, waits for the sector to rotate
    under the head, reads the bits, assembles them into bytes, performs ECC,
    and places the data in its internal buffer.
  - The controller asserts an interrupt to tell the CPU the data is ready.
  - The CPU (or DMA engine) reads the data from the controller's buffer.

Controller registers are accessed by the CPU either via:
  - I/O Ports (Port-Mapped I/O) — special IN/OUT instructions, or
  - Memory-Mapped I/O — reading/writing specific memory addresses.

    Micro-topic: NVMe — A Modern Controller Architecture
    ─────────────────────────────────────────────────────
    NVMe (Non-Volatile Memory Express) is a modern storage controller
    protocol designed specifically for SSDs connected via PCIe. Unlike
    AHCI (designed for spinning disks with a single command queue), NVMe
    supports:
      - Up to 65,535 I/O queues, each with up to 65,536 commands.
      - Direct PCIe connection (no SATA bottleneck).
      - Doorbell registers for queue submission/completion.
      - MSI-X interrupts for per-queue completion notifications.
    Result: NVMe SSDs achieve ~7 GB/s sequential and 1M+ IOPS random.

────────────────────────────────────────────────────
5.3.3  Memory-Mapped I/O
────────────────────────────────────────────────────

There are two methods for the CPU to communicate with device controllers:

METHOD 1: PORT-MAPPED I/O (Isolated I/O):
  - Uses a separate I/O address space (distinct from memory addresses).
  - Accessed via special CPU instructions: IN and OUT (x86).
  - Example: IN AL, 0x60 reads a byte from keyboard controller port 0x60.
  - Address space is small (65,536 ports on x86).
  - Advantage: Cannot accidentally access a device by dereferencing a bad
    pointer (separate address space).
  - Disadvantage: Requires special instructions; cannot use regular memory
    instructions (MOV, etc.) on device registers.

METHOD 2: MEMORY-MAPPED I/O (MMIO):
  - Device registers are mapped into the regular memory address space.
  - The CPU reads/writes device registers using ordinary load/store
    instructions (MOV on x86).
  - Example: A GPU's frame buffer is mapped to a range of physical memory
    addresses. Writing to those addresses changes the displayed image.
  - Advantages:
    * No special instructions needed — any instruction that can reference
      memory can access device registers.
    * Can use the full repertoire of memory instructions (useful for
      driver development in C: struct pointer dereference works directly).
    * Protection via page tables: the OS can control which processes have
      access to MMIO regions.
    * The compiler can optimize memory-mapped device access (though
      volatile must be used to prevent incorrect optimization).
  - Disadvantages:
    * MMIO regions must be marked as uncacheable (otherwise the CPU cache
      might serve stale data instead of reading from the device). This
      is done via page table entries (PAT/MTRR on x86).
    * Consumes address space (less of a concern with 64-bit addressing).

MODERN SYSTEMS: Most modern systems use a combination. x86 PCs still use
port I/O for legacy devices (keyboard 0x60, serial ports 0x3F8) but use
MMIO for modern devices (GPU, NVMe, network cards, USB controllers). PCIe
devices use MMIO exclusively via BAR (Base Address Register) mappings.

    Micro-topic: BAR (Base Address Registers) in PCIe
    ──────────────────────────────────────────────────
    Each PCIe device has up to 6 BARs in its configuration space. A BAR
    tells the system how much memory-mapped address space the device needs.
    During boot, the BIOS/UEFI (or the OS) assigns physical address
    ranges to each BAR. The device's registers and memory then appear at
    those physical addresses.

    On Linux:
      $ lspci -vv | grep "Memory at"
      #  Memory at fe000000 (64-bit, non-prefetchable) [size=16M]

────────────────────────────────────────────────────
5.3.4  Direct Memory Access (DMA)
────────────────────────────────────────────────────

Without DMA, the CPU must personally transfer every byte between a device
controller and memory (called Programmed I/O or PIO). For high-speed devices,
this wastes enormous CPU time.

DMA (Direct Memory Access) allows the device controller (or a separate DMA
controller chip) to transfer data directly between the device and memory
without CPU involvement for each byte.

DMA TRANSFER PROCESS:
  1. The CPU programs the DMA controller with:
     - Source address (device buffer or memory address)
     - Destination address (memory address or device buffer)
     - Number of bytes to transfer
     - Direction (read from device / write to device)
  2. The CPU initiates the transfer and continues other work.
  3. The DMA controller takes over the bus and performs the transfer
     (one bus cycle per word/byte, stealing cycles from the CPU — this
     is called "cycle stealing").
  4. When the transfer is complete, the DMA controller asserts an
     interrupt to notify the CPU.

DMA MODES:
  - Burst mode: The DMA controller takes over the bus for the entire
    transfer. Fast, but the CPU is locked out of the bus.
  - Cycle stealing: The DMA controller transfers one word at a time, then
    returns the bus to the CPU. Slower but allows CPU bus access.
  - Transparent mode: DMA only uses the bus when the CPU isn't using it.
    No performance impact on CPU but slowest transfer.

MODERN DMA (Bus Mastering):
  On modern PCI/PCIe systems, DMA is done through "bus mastering": the device
  itself (not a separate DMA controller) directly reads/writes system memory.
  The device is a "bus master" and initiates memory transactions on the PCIe
  bus. This is how NVMe SSDs, GPUs, and network cards achieve their high
  throughput.

    Micro-topic: IOMMU and DMA Security
    ────────────────────────────────────
    A malicious or buggy device with DMA access could read/write any memory
    location — a massive security risk. The IOMMU (I/O Memory Management
    Unit) provides address translation and access control for DMA:

      - Intel VT-d (Virtualization Technology for Directed I/O)
      - AMD-Vi (AMD I/O Virtualization)

    The IOMMU translates device-visible addresses (IOVA — I/O Virtual
    Addresses) to physical addresses through I/O page tables. The OS
    configures these tables to restrict each device to only the memory
    regions it should access.

    On Linux, the IOMMU is essential for:
      - VFIO (Virtual Function I/O) — passing PCIe devices to VMs.
      - DMA protection against DMA attacks (e.g., Thunderbolt/FireWire).

        Deeper: Bounce Buffers
        ──────────────────────
        Some older DMA controllers can only address the lower 16 MB of
        memory (ISA DMA). If the data buffer is above 16 MB, the kernel
        uses a "bounce buffer": it allocates a temporary buffer in low
        memory, performs the DMA transfer there, then copies the data to
        the actual high-memory buffer. Modern PCIe devices address full
        64-bit memory, so bounce buffers are rarely needed.

5.4  PRINCIPLES OF I/O SOFTWARE
================================================================================

────────────────────────────────────────────────────
5.4.1  Goals of I/O Software
────────────────────────────────────────────────────

The primary goals of the I/O software subsystem are:

  1. DEVICE INDEPENDENCE: Programs should work with any I/O device without
     modification. A program that reads from a file should work whether the
     file is on a local SSD, a USB drive, or a remote NFS server.

  2. UNIFORM NAMING: The name of a file or device should be a string or
     integer that does not depend on the device type. On UNIX, /dev/sda1
     and /dev/nvme0n1p1 can both be mounted at /home — applications don't
     know the difference.

  3. ERROR HANDLING: Errors should be handled as close to the hardware as
     possible. The controller retries on CRC errors; the driver retries on
     timeout; the file system handles bad blocks; user programs handle
     file-not-found.

  4. SYNCHRONOUS vs. ASYNCHRONOUS TRANSFER: Physical I/O is asynchronous
     (DMA/interrupt-based), but most user programs expect blocking I/O
     (read() blocks until data is available). The OS converts asynchronous
     hardware operations to synchronous programming abstractions. For
     applications that want async: Linux provides io_uring, aio, epoll.

  5. BUFFERING: The OS must buffer data for several reasons:
     - Speed mismatch: If a process reads one byte at a time from disk,
       the OS reads a full block and buffers the rest.
     - Device-process timing mismatch: Network packets arrive asynchronously
       and must be buffered until the process reads them.

  6. SHARABLE vs. DEDICATED DEVICES: Disks are shared (multiple processes
     access simultaneously); printers are dedicated (one job at a time,
     managed by spooling).

    Micro-topic: Buffering Strategies
    ──────────────────────────────────
    - No buffering: Data goes directly from device to user's buffer.
      Problem: user must be ready when data arrives.

    - Single buffering: OS provides one buffer. While the user processes
      data from the buffer, the device fills a new buffer (but must wait
      if the user hasn't finished).

    - Double buffering: Two buffers. While the user processes buffer A,
      the device fills buffer B, and vice versa. Overlaps processing
      and I/O for better throughput.

    - Circular buffering: N buffers arranged in a ring (producer-consumer
      pattern). Used when the device and process have highly variable
      speeds.

────────────────────────────────────────────────────
5.4.2  Polled I/O vs. Interrupt-Driven I/O
────────────────────────────────────────────────────

POLLED I/O (Programmed I/O):
  The CPU continuously checks (polls) the device's status register in a
  tight loop, waiting for the device to become ready. Also called "busy
  waiting."

  Algorithm:
    while (device_status_register & BUSY_BIT)
        ; // spin — CPU does nothing useful
    read data from device data register;

  Advantages:
    - Simple implementation.
    - Low latency for very fast devices (no interrupt overhead).
    - Predictable (no interrupt jitter).

  Disadvantages:
    - Wastes CPU cycles. The CPU cannot do anything else while waiting.
    - For slow devices (disk, network), this is catastrophically wasteful.

INTERRUPT-DRIVEN I/O:
  The CPU initiates an I/O operation and then continues executing other tasks.
  When the device completes, it asserts an interrupt, causing the CPU to
  invoke the interrupt handler to process the result.

  Algorithm:
    write command to device command register;
    // CPU does other work...
    // Later, when device interrupts:
    interrupt_handler() {
        read data from device data register;
        wake up waiting process;
    }

  Advantages:
    - CPU is free to do useful work while waiting.
    - Essential for multitasking systems.

  Disadvantages:
    - Interrupt overhead (save/restore registers, context switch).
    - For very high-speed devices generating many interrupts per second
      (e.g., 10 Gbps network), interrupts can overwhelm the CPU
      ("interrupt livelock" or "receive livelock").

HYBRID APPROACH (Modern Linux Networking — NAPI):
  Linux uses NAPI (New API) for high-speed networking:
    1. First packet arrives → hardware interrupt fires.
    2. Interrupt handler disables further interrupts for this device.
    3. The driver switches to polling mode: a soft-interrupt handler polls
       the device for more packets.
    4. When no more packets are available, re-enable interrupts.
  This avoids both the waste of pure polling and the overhead of per-packet
  interrupts.

    Micro-topic: io_uring — Modern Asynchronous I/O on Linux
    ─────────────────────────────────────────────────────────
    io_uring (Linux 5.1+) is a high-performance async I/O framework:
      - Two ring buffers shared between user space and kernel:
        Submission Queue (SQ) and Completion Queue (CQ).
      - User space adds I/O requests to SQ; kernel processes them
        asynchronously and posts results to CQ.
      - No system call overhead per I/O (after initial setup) — the
        kernel polls the SQ.
      - Supports: file I/O, network I/O, timers, even process creation.
    io_uring achieves millions of IOPS for NVMe storage.

────────────────────────────────────────────────────
5.4.3  Character User Interface and Graphical User Interface
────────────────────────────────────────────────────

CHARACTER USER INTERFACE (CLI / Terminal):
  A text-based interface where the user interacts by typing commands and
  reading text output. The fundamental I/O devices are the keyboard (input)
  and the display/terminal (output).

  On Linux, terminals are represented as TTY devices:
    - /dev/tty1 through /dev/tty6: Virtual consoles (Ctrl+Alt+F1-F6).
    - /dev/pts/0, /dev/pts/1, ...: Pseudo-terminals (used by terminal
      emulators like Alacritty, kitty, xterm, and SSH sessions).

  The TTY subsystem in the kernel handles:
    - Line discipline: Echoing characters, handling backspace, Ctrl+C
      (SIGINT), Ctrl+Z (SIGTSTP), Ctrl+D (EOF), etc.
    - Terminal modes: Canonical (line-buffered) vs. Raw (unbuffered).
    - Job control: Foreground/background process groups.

GRAPHICAL USER INTERFACE (GUI):
  A visual interface with windows, icons, menus, and pointer interactions.
  On Linux, the display stack involves:

    ┌──────────────────────────────────────────┐
    │  Applications (Firefox, KDE, GNOME)      │
    ├──────────────────────────────────────────┤
    │  Toolkit (Qt, GTK)                       │
    ├──────────────────────────────────────────┤
    │  Windowing Protocol                      │
    │  (Wayland / X11)                         │
    ├──────────────────────────────────────────┤
    │  Compositor / Display Server             │
    │  (Sway, KWin, Mutter / Xorg)             │
    ├──────────────────────────────────────────┤
    │  DRM/KMS (Direct Rendering Manager /     │
    │   Kernel Mode Setting)                   │
    ├──────────────────────────────────────────┤
    │  GPU Driver (i915, amdgpu, nouveau)      │
    ├──────────────────────────────────────────┤
    │  GPU Hardware                            │
    └──────────────────────────────────────────┘

  Wayland is the modern replacement for the X11 (X Window System) protocol.
  Arch Linux uses Wayland by default in GNOME and KDE Plasma 6.

────────────────────────────────────────────────────
5.4.4  Device Drivers
────────────────────────────────────────────────────

A device driver is a kernel module (or compiled-in code) that knows how to
communicate with a specific hardware device. The driver translates abstract
OS requests (e.g., "read block 42") into device-specific register
manipulations, DMA setup, and interrupt handling.

DRIVER RESPONSIBILITIES:
  - Initialize the device on startup or module load.
  - Translate OS-level requests into hardware commands.
  - Set up DMA transfers.
  - Handle interrupts from the device.
  - Manage device power states (suspend, resume).
  - Report errors to the OS.

LINUX DRIVER MODEL:

  In Linux, drivers register with a bus subsystem (PCI, USB, platform)
  and provide callback functions:

  struct file_operations (for character devices):
    .open     = my_open,
    .read     = my_read,
    .write    = my_write,
    .ioctl    = my_ioctl,
    .release  = my_release,

  struct block_device_operations (for block devices):
    .open     = my_open,
    .submit_bio = my_submit_bio,  // (newer interface)

  Drivers interact with hardware through:
    - ioread32() / iowrite32() — for MMIO access.
    - inb() / outb() — for port I/O access.
    - dma_alloc_coherent() — for DMA buffer allocation.
    - request_irq() / request_threaded_irq() — for interrupt registration.

    Micro-topic: Loadable Kernel Modules (LKMs)
    ─────────────────────────────────────────────
    Most Linux drivers are compiled as Loadable Kernel Modules (.ko files)
    rather than built into the kernel image. Modules can be loaded and
    unloaded at runtime:

      $ sudo modprobe nvidia       # Load nvidia driver
      $ sudo rmmod nvidia          # Unload nvidia driver
      $ lsmod                      # List loaded modules
      $ modinfo ext4               # Show info about a module

    Module files on Arch Linux are stored at:
      /usr/lib/modules/$(uname -r)/kernel/drivers/

    The module system uses dependency tracking (modules.dep) and automatic
    loading via udev rules. When hardware is detected at boot, udev
    triggers modprobe with the appropriate module alias.

        Deeper: Driver Development Frameworks
        ──────────────────────────────────────
        - DriverKit (macOS): User-space driver framework.
        - WDF (Windows Driver Framework): KMDF (kernel) and UMDF (user).
        - VFIO (Linux): User-space driver framework for PCIe passthrough.
        - DPDK (Data Plane Development Kit): User-space network drivers
          for high-performance packet processing (bypasses kernel stack).
        - SPDK (Storage Performance Development Kit): User-space NVMe
          drivers for extreme IOPS.

────────────────────────────────────────────────────
5.4.5  Device-Independent I/O Software
────────────────────────────────────────────────────

Device-independent I/O software performs functions common to all devices,
providing a uniform interface above the driver layer:

  1. UNIFORM INTERFACE FOR DRIVERS: The OS defines standard interfaces
     (struct file_operations, struct block_device_operations) that all
     drivers must implement. New drivers plug into the existing framework.

  2. NAMING AND PROTECTION:
     - Devices are identified by major and minor numbers.
       Major number → identifies the driver.
       Minor number → identifies the specific device instance.
     - Example: major 8 = SCSI disk driver; minor 0 = /dev/sda, minor 1 =
       /dev/sda1.
     - Protection uses the standard UNIX permission model (rwx) on device
       files in /dev/.

  3. BUFFERING: The buffer cache (page cache in Linux) buffers disk blocks
     in memory, dramatically reducing disk I/O.

  4. ERROR REPORTING: The OS provides a standard error reporting mechanism.
     Drivers return error codes (e.g., -EIO, -ENOMEM, -ENODEV) which are
     propagated to user space via errno.

  5. ALLOCATING AND RELEASING DEDICATED DEVICES: The OS manages exclusive
     access to devices like tape drives and printers.

  6. DEVICE-INDEPENDENT BLOCK SIZE: File systems use a standard block size
     (4 KB) regardless of the underlying device's sector size.

────────────────────────────────────────────────────
5.4.6  User-Space I/O Software
────────────────────────────────────────────────────

Most I/O visible to application programmers is through library functions,
not direct system calls:

  - C Standard Library (stdio.h):
    printf(), scanf(), fread(), fwrite(), fopen(), fclose()
    These use internal buffering (user-space buffers) and invoke the
    underlying system calls (write(), read()) as needed.

  - Spooling: For dedicated devices like printers, a spooling system (e.g.,
    CUPS — Common UNIX Printing System) queues print jobs. User programs
    submit to the spooler (user-space daemon), which manages access to the
    physical printer.

  - User-space drivers: Some modern approaches move drivers to user space:
    - FUSE (Filesystem in Userspace): Implement file systems without
      kernel code (e.g., sshfs, rclone mount).
    - libusb: Access USB devices from user space.
    - DPDK/SPDK: High-performance user-space network/storage drivers.


================================================================================
5.5  SYSTEM RESOURCES AND DEADLOCKS
================================================================================

────────────────────────────────────────────────────
5.5.1  Preemptable and Non-Preemptable Resources
────────────────────────────────────────────────────

A RESOURCE is anything a process needs to proceed: CPU time, memory, disk
space, I/O devices, mutexes, semaphores, database records, etc.

PREEMPTABLE RESOURCES: Can be taken away from a process without ill effects.
The process can be given the resource back later and will continue normally.
  Examples:
    - CPU (time-slicing / preemptive scheduling).
    - Memory (pages can be swapped out and brought back).

NON-PREEMPTABLE RESOURCES: Cannot be taken away without causing the process
to fail or lose work. The process must voluntarily release the resource.
  Examples:
    - Printer (cannot take a half-printed job and give the printer to
      another process).
    - CD/DVD recorder (cannot pause mid-burn).
    - Tape drive (positioning is sequential).
    - Mutexes/locks (taking a lock from a process would violate mutual
      exclusion and corrupt data).

DEADLOCKS primarily involve NON-PREEMPTABLE resources. If resource A can be
preempted and given to another process, circular wait (and hence deadlock)
can be broken.

RESOURCE USAGE SEQUENCE:
  1. Request: Process requests the resource. If not available, the process
     blocks (waits).
  2. Use: Process uses the resource.
  3. Release: Process releases the resource.

────────────────────────────────────────────────────
5.5.2  Deadlock — Definition and Conditions
────────────────────────────────────────────────────

DEADLOCK: A set of processes is deadlocked when each process in the set is
waiting for a resource held by another process in the set. No process can
proceed because each is waiting for the other.

Classic example: Two processes, two resources.
  Process A holds Resource 1, wants Resource 2.
  Process B holds Resource 2, wants Resource 1.
  Neither can proceed.

COFFMAN CONDITIONS (Necessary and Sufficient):
All four conditions must hold simultaneously for deadlock to occur:

  1. MUTUAL EXCLUSION: At least one resource must be held in a non-sharable
     mode. Only one process can use the resource at a time.

  2. HOLD AND WAIT: A process must be holding at least one resource and
     waiting to acquire additional resources held by other processes.

  3. NO PREEMPTION: Resources cannot be forcibly taken from a process; they
     must be released voluntarily.

  4. CIRCULAR WAIT: There must be a circular chain of two or more processes,
     each waiting for a resource held by the next process in the chain.
     P1 → P2 → P3 → ... → Pn → P1.

If any one of these conditions is prevented, deadlock cannot occur.

    Micro-topic: Livelock and Starvation
    ─────────────────────────────────────
    LIVELOCK: Processes are not blocked; they actively change state in
    response to each other, but no progress is made. Example: two people
    in a hallway, both stepping aside in the same direction repeatedly.
    In computing: two processes detect potential deadlock, release their
    resources, retry, and collide again — infinitely.

    STARVATION: A process waits indefinitely because other processes keep
    getting the resource first. The process is not deadlocked (no circular
    wait), but it never gets served. Example: a low-priority process in
    a priority scheduling system that is perpetually preempted.

    DEADLOCK ≠ STARVATION:
    Deadlock: all involved processes are blocked (no progress for any).
    Starvation: one process is indefinitely postponed (others progress).

────────────────────────────────────────────────────
5.5.3  Methods of Handling Deadlocks
────────────────────────────────────────────────────

Four approaches:

  1. DEADLOCK PREVENTION: Design the system so that at least one of the
     four Coffman conditions can never hold.

  2. DEADLOCK AVOIDANCE: Allow all four conditions to potentially hold, but
     make careful resource allocation decisions to ensure the system never
     enters a deadlocked state (Banker's Algorithm).

  3. DEADLOCK DETECTION AND RECOVERY: Allow deadlocks to occur, but detect
     them and take corrective action.

  4. OSTRICH ALGORITHM (Ignore): Pretend deadlocks don't happen. If one
     occurs, reboot. Used in many real systems (including UNIX/Linux for
     some resources) when deadlocks are very rare and the cost of
     prevention/avoidance outweighs the cost of occasional reboots.

────────────────────────────────────────────────────
5.5.3.1  Deadlock Prevention
────────────────────────────────────────────────────

Attack each Coffman condition:

ATTACKING MUTUAL EXCLUSION:
  Make resources sharable. However, many resources (printers, locks) are
  inherently non-sharable. Spooling can help: instead of granting direct
  printer access, processes write to a spool file (sharable), and the
  spooler daemon is the only process that directly accesses the printer.
  Problem: not all resources can be spooled (e.g., process table entries,
  mutexes).

ATTACKING HOLD AND WAIT:
  Strategy 1: Require processes to request ALL needed resources at once
  (before starting). Only grant if all are available.
    Problem: Process may not know all needed resources in advance.
    Problem: Low resource utilization — resources held but unused.
  Strategy 2: Require a process to release all currently held resources
  before requesting new ones.
    Problem: May lead to starvation or inconsistency.

ATTACKING NO PREEMPTION:
  If a process holding resources requests another that's unavailable,
  forcibly release (preempt) all its current resources. The process
  restarts when all needed resources are available.
  Works for: CPU, memory (pages can be swapped).
  Does NOT work for: printers, database locks, tape drives.

ATTACKING CIRCULAR WAIT:
  Impose a total ordering on all resource types and require processes
  to request resources in strictly increasing order.
  Example: Assign each resource a number: R1=1, R2=2, R3=3.
  A process holding R2 can only request R3 (not R1).
  This prevents cycles in the wait graph.
  Problem: May be impractical with many resource types; program logic
  may not naturally follow the ordering.

────────────────────────────────────────────────────
5.5.4  Deadlock Avoidance: Banker's Algorithm
────────────────────────────────────────────────────

The Banker's Algorithm, devised by Edsger Dijkstra (1965), is a deadlock
avoidance algorithm. It models the system as a banker with a fixed amount
of capital (resources), lending to customers (processes). The banker
never allocates resources in a way that could lead to deadlock.

CONCEPT: Before granting a resource request, the algorithm checks if
granting it would leave the system in a "safe state." If yes, the
request is granted; if no (the system would be "unsafe"), the request
is deferred.

SAFE STATE: A state in which there exists at least one sequence
(called a "safe sequence") in which all processes can finish.
Formally, a sequence <P1, P2, ..., Pn> is safe if for each Pi, the
resources that Pi can still request can be satisfied by the currently
available resources plus the resources held by all Pj (j < i) that
finish before Pi.

UNSAFE STATE ≠ DEADLOCK. An unsafe state means deadlock is possible
(not certain). A safe state guarantees deadlock cannot occur.

DATA STRUCTURES:
  Let n = number of processes, m = number of resource types.

  - Available[m]: Vector of currently available resources of each type.
  - Max[n][m]: Maximum demand of each process.
  - Allocation[n][m]: Currently allocated resources for each process.
  - Need[n][m]: Remaining need of each process.
    Need[i][j] = Max[i][j] - Allocation[i][j]

SAFETY ALGORITHM:
  1. Let Work[m] = Available[m], Finish[n] = {false, ..., false}.
  2. Find a process Pi such that:
       Finish[i] == false AND Need[i] <= Work
     (i.e., Pi's remaining need can be satisfied with available resources.)
  3. If found:
       Work = Work + Allocation[i]    (simulate Pi finishing and releasing)
       Finish[i] = true
       Go to step 2.
  4. If all Finish[i] == true → system is in a SAFE state.
     Otherwise → UNSAFE state.

RESOURCE REQUEST ALGORITHM:
  When process Pi requests resources Request[i]:
  1. If Request[i] > Need[i] → ERROR (process exceeded max claim).
  2. If Request[i] > Available → Process must WAIT.
  3. Pretend to allocate:
       Available = Available - Request[i]
       Allocation[i] = Allocation[i] + Request[i]
       Need[i] = Need[i] - Request[i]
  4. Run Safety Algorithm.
     If SAFE → grant the request.
     If UNSAFE → revert the pretend allocation, process waits.

────────────────────────────────────────────────────
5.5.5  Deadlock Detection: Resource Allocation Graph
────────────────────────────────────────────────────

Instead of preventing or avoiding deadlock, we can allow deadlocks to happen
and then detect them.

RESOURCE ALLOCATION GRAPH (RAG):

A directed graph with two types of nodes:
  - Process nodes (circles): P1, P2, ...
  - Resource nodes (rectangles with dots for instances): R1, R2, ...

Two types of edges:
  - REQUEST EDGE: Pi → Rj (process Pi is waiting for resource Rj)
  - ASSIGNMENT EDGE: Rj → Pi (resource Rj is allocated to process Pi)

DEADLOCK DETECTION:
  - SINGLE INSTANCE per resource type: Deadlock ↔ cycle in the RAG.
    If there is a cycle, the processes in the cycle are deadlocked.

  - MULTIPLE INSTANCES per resource type: A cycle is necessary but NOT
    sufficient for deadlock. Use the detection algorithm (similar to
    Banker's safety algorithm but without Max — uses only Allocation,
    Request, and Available).

DETECTION ALGORITHM (Multiple Instances):
    1. Work = Available, Finish[i] = false (if Allocation[i] ≠ 0),
       Finish[i] = true (if Allocation[i] = 0).
    2. Find Pi such that Finish[i] = false AND Request[i] <= Work.
    3. If found: Work = Work + Allocation[i], Finish[i] = true, goto 2.
    4. If any Finish[i] = false → Pi is DEADLOCKED.

Example RAG with cycle (single instance):

       P1 ──request──→ R1 ──assign──→ P2
       ↑                               │
       │                               │
    R2 ──assign── P1              request
       ↑                               │
       │                               ▼
       └──────── request ── P2 ← assign ── R2

  Wait, let me draw this more clearly:

       P1 requests R1 (P1 → R1)
       R1 is held by P2 (R1 → P2)
       P2 requests R2 (P2 → R2)
       R2 is held by P1 (R2 → P1)

       Cycle: P1 → R1 → P2 → R2 → P1
       DEADLOCK!

WHEN TO RUN DETECTION:
  - On every resource request (expensive but catches deadlocks immediately).
  - Periodically (e.g., every 5 minutes).
  - When CPU utilization drops below a threshold (possible symptom of
    deadlock).

    Micro-topic: Wait-For Graph
    ───────────────────────────
    For single-instance resources, the RAG can be simplified to a
    Wait-For Graph: only process nodes, with an edge Pi → Pj meaning
    "Pi is waiting for a resource held by Pj." Deadlock detection
    reduces to finding a cycle in this simpler graph. Cycle detection
    can be done with DFS in O(V+E) time.

────────────────────────────────────────────────────
5.5.6  Recovery from Deadlock
────────────────────────────────────────────────────

Once a deadlock is detected, the system must break it:

METHOD 1: PROCESS TERMINATION
  a. Abort ALL deadlocked processes. Drastic but simple.
  b. Abort ONE process at a time until the deadlock is broken. After each
     termination, re-run the detection algorithm. The selection criteria
     for which process to abort:
       - Priority of the process (abort lowest priority first).
       - How long the process has been running (abort newest first).
       - Resources used by the process (abort one using few resources).
       - How many more resources the process needs.
       - How many processes will need to be terminated.
       - Whether the process is interactive or batch.

METHOD 2: RESOURCE PREEMPTION
  Forcibly take resources from some processes and give them to others:
  a. Select a victim: Choose the process whose resources to preempt
     (minimize cost — consider priority, progress, etc.).
  b. Rollback: The victim must be rolled back to a safe state (this
     requires checkpointing, which is not always feasible).
  c. Starvation: Ensure the same process is not always chosen as victim.
     Limit the number of rollbacks per process.

METHOD 3: CHECKPOINT AND RESTART
  Periodically save process state. On deadlock, roll back one or more
  processes to a previous checkpoint and retry.

In practice, many operating systems use a combination of prevention (e.g.,
ordering of lock acquisition in the kernel) and detection with recovery
(e.g., database systems use timeout-based deadlock detection).

5.6  RAID (REDUNDANT ARRAY OF INEXPENSIVE DISKS)
================================================================================

RAID is a technique of combining multiple physical disk drives into a single
logical unit for improved performance, redundancy, or both. It was introduced
by Patterson, Gibson, and Katz at UC Berkeley in 1988. The original paper
defined 5 RAID levels; RAID 6 was added later.

MOTIVATION:
  - Single large disks are expensive and have limited I/O performance.
  - Using many small, inexpensive disks in parallel can increase both
    capacity and throughput.
  - Redundancy (data duplication or parity) can improve reliability.

RAID LEVELS:

  RAID 0 (Striping):
    - Data is striped (split into blocks) across N disks.
    - No redundancy (no mirror, no parity).
    - Performance: N× read and write throughput.
    - Capacity: 100% of total disk space.
    - Risk: If ANY disk fails, ALL data is lost.
    - Use case: Temporary data, scratch space, speed-critical non-critical data.

  RAID 1 (Mirroring):
    - Data is written identically to two (or more) disks.
    - Full redundancy: can survive failure of N-1 disks (in N-disk mirror).
    - Read performance: Up to N× (reads can be distributed).
    - Write performance: Same as single disk (all mirrors must be written).
    - Capacity: 50% of total disk space (for 2-disk mirror).
    - Use case: OS partition, critical databases.

  RAID 2 (Bit-level striping with Hamming code):
    - Data is striped at the bit level across disks.
    - Dedicated disks for Hamming error-correcting codes.
    - Obsolete: modern disk controllers handle error correction internally.

  RAID 3 (Byte-level striping with dedicated parity):
    - Data is striped at the byte level; one dedicated parity disk.
    - Can recover from single disk failure using parity.
    - Rarely used: every I/O operation involves all disks (no independent
      access).

  RAID 4 (Block-level striping with dedicated parity):
    - Data is striped at the block level; one dedicated parity disk.
    - Independent reads (different blocks on different disks).
    - Writes require updating the parity disk → parity disk becomes a
      bottleneck (the "write penalty").
    - Can recover from single disk failure.

  RAID 5 (Block-level striping with distributed parity):
    - Like RAID 4, but parity is distributed across all disks (rotates).
    - Eliminates the parity disk bottleneck.
    - Can recover from single disk failure.
    - Minimum 3 disks.
    - Capacity: (N-1)/N of total disk space.
    - The most common RAID level for servers.

    RAID 5 Parity calculation:
    $$ P = D_1 \oplus D_2 \oplus D_3 \oplus \ldots \oplus D_{n-1} $$
    (XOR of all data blocks)

    If disk k fails, its data is recovered:
    $$ D_k = D_1 \oplus \ldots \oplus D_{k-1} \oplus D_{k+1} \oplus \ldots \oplus P $$

  RAID 6 (Block-level striping with double distributed parity):
    - Two parity blocks per stripe (using two different parity algorithms:
      XOR and Reed-Solomon / Galois Field).
    - Can survive TWO simultaneous disk failures.
    - Minimum 4 disks.
    - Capacity: (N-2)/N of total disk space.
    - Increasingly common as disk sizes grow (larger disks → longer rebuild
      times → higher chance of second failure during rebuild).

  COMMON NESTED LEVELS:
    RAID 10 (1+0): Stripe of mirrors. Mirrors for redundancy, stripe for
    speed. Minimum 4 disks. Best performance with redundancy.
    RAID 01 (0+1): Mirror of stripes. Less resilient than RAID 10.

  ┌─────────┬────────┬──────────┬───────────┬──────────┬────────────┐
  │ Level   │ Min    │ Capacity │ Fault     │ Read     │ Write      │
  │         │ Disks  │          │ Tolerance │ Speed    │ Speed      │
  ├─────────┼────────┼──────────┼───────────┼──────────┼────────────┤
  │ RAID 0  │ 2      │ N        │ 0 disks   │ N×       │ N×         │
  │ RAID 1  │ 2      │ N/2      │ N-1 disks │ N×       │ 1×         │
  │ RAID 5  │ 3      │ N-1      │ 1 disk    │ (N-1)×   │ <(N-1)×   │
  │ RAID 6  │ 4      │ N-2      │ 2 disks   │ (N-2)×   │ <(N-2)×   │
  │ RAID 10 │ 4      │ N/2      │ 1 per mir │ N×       │ (N/2)×    │
  └─────────┴────────┴──────────┴───────────┴──────────┴────────────┘

    Micro-topic: Software RAID vs. Hardware RAID
    ─────────────────────────────────────────────
    Hardware RAID: A dedicated RAID controller card with its own CPU and
    cache. The OS sees a single logical disk. Pros: offloads parity
    computation, battery-backed write cache. Cons: expensive, vendor
    lock-in, controller failure risks data loss.

    Software RAID: The OS manages RAID using CPU and regular disks.
    Linux: mdadm (MD = Multiple Devices) creates software RAID arrays.
    Modern CPUs are so fast that software RAID performance is comparable
    to (or exceeds) all but the most expensive hardware RAID controllers.

    ZFS and Btrfs have built-in RAID functionality (RAIDZ/RAIDZ2 for ZFS,
    RAID 1/5/6 for Btrfs) that integrates RAID with the file system for
    better data integrity (checksums, self-healing).

5.7  RAM DISKS
================================================================================

A RAM disk (or ramdisk) is a block device that uses a portion of the system's
RAM as a virtual disk drive. Data stored on a RAM disk is accessed at memory
speed, which is orders of magnitude faster than any SSD or HDD.

CHARACTERISTICS:
  - Speed: ~10-50 GB/s (vs. ~7 GB/s for NVMe SSD, ~200 MB/s for HDD).
  - Latency: ~100 ns (vs. ~10 μs for NVMe, ~10 ms for HDD).
  - Volatile: All data is lost on reboot (unless backed by persistent
    storage).
  - Capacity: Limited by available RAM.

USES:
  - Temporary files and build artifacts.
  - Databases with extreme performance requirements.
  - Testing: simulating fast storage.
  - Embedded systems: storing the root filesystem in RAM.

LINUX IMPLEMENTATIONS:

  1. tmpfs (Most common):
     A virtual filesystem that uses RAM and swap. It is dynamic — it only
     uses RAM for files that actually exist (no pre-allocated size).
     Automatically shrinks as files are deleted.
       $ mount -t tmpfs -o size=2G tmpfs /mnt/ramdisk
     By default, /tmp on Arch Linux is a tmpfs.

  2. ramfs:
     An older, simpler RAM filesystem. Does NOT have a size limit (can grow
     to consume all available RAM and crash the system). Does NOT use swap.
     tmpfs is almost always preferred over ramfs.
       $ mount -t ramfs ramfs /mnt/ramfs

  3. /dev/ram* (Block RAM Disk):
     Traditional block device RAM disks. A fixed amount of RAM is reserved
     and presented as a block device. A filesystem must be created on it:
       $ modprobe brd rd_size=1048576    # 1 GB RAM disk
       $ mkfs.ext4 /dev/ram0
       $ mount /dev/ram0 /mnt/ramdisk
     Less flexible than tmpfs; wastes RAM even when empty.

  4. initramfs / initrd:
     The initial RAM filesystem loaded during boot (covered in Chapter 4)
     is essentially a RAM disk used to bootstrap the system.

    Micro-topic: tmpfs and the Linux Page Cache
    ─────────────────────────────────────────────
    tmpfs integrates with the kernel's page cache and swap subsystem:
      - Files in tmpfs are stored as anonymous pages in RAM.
      - Under memory pressure, tmpfs pages can be swapped out to disk
        (unlike ramfs, which never swaps).
      - tmpfs is used internally for several kernel facilities:
        * Shared memory (POSIX shm_open, SysV shmget)
        * /dev/shm — the shared memory mount point
        * /run — runtime data (PID files, sockets)
        * /tmp — temporary files (on Arch Linux)

        Deeper: ZRAM — Compressed RAM Disks
        ────────────────────────────────────
        zram creates compressed block devices in RAM. Data written to a
        zram device is compressed before being stored in RAM, effectively
        multiplying the available storage. Common uses:
          - Swap on zram: Compressed RAM swap is much faster than disk
            swap and can significantly improve responsiveness on systems
            with limited RAM.
          - /tmp on zram: Faster than disk-backed tmpfs.

        On Arch Linux:
          $ sudo modprobe zram
          $ echo lz4 | sudo tee /sys/block/zram0/comp_algorithm
          $ echo 4G | sudo tee /sys/block/zram0/disksize
          $ sudo mkswap /dev/zram0
          $ sudo swapon /dev/zram0

        systemd-zram-setup or zram-generator can automate this.

    $ sudo umount /mnt/raid
    $ sudo mdadm --stop /dev/md0
    $ for i in 0 1 2; do sudo losetup -d /dev/loop$i; rm /tmp/disk$i.img; done
