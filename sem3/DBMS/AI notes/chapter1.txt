1.1  DATABASE MANAGEMENT SYSTEM: PURPOSE AND APPLICATIONS
================================================================================

■ FORMAL DEFINITION
────────────────────
A **Database Management System (DBMS)** is a software system that enables
users to define, create, maintain, and control access to a database. It
serves as an intermediary between end-users (or application programs) and
the database, providing a systematic, organized mechanism for managing
collections of interrelated data.

More precisely, a **database** is a logically coherent collection of data
with some inherent meaning, representing some aspect of the real world
(sometimes called the "mini-world" or "Universe of Discourse").

■ IN-DEPTH EXPLANATION
───────────────────────
WHY do we need a DBMS?

Before DBMS, data was stored in flat files on disk. This approach worked
for trivially small datasets, but as organizations grew, severe problems
emerged: data redundancy, inconsistency, difficulty in accessing data,
lack of concurrent access, and absence of security. DBMS was designed to
solve ALL of these problems.

HOW does a DBMS work?

At its core, a DBMS does the following:
  1. **Data Definition**: Allows defining the structure (schema) of data
     using a Data Definition Language (DDL).
  2. **Data Manipulation**: Allows inserting, updating, deleting, and
     querying data using a Data Manipulation Language (DML).
  3. **Data Security & Integrity**: Enforces access controls, constraints,
     and rules that keep data consistent and secure.
  4. **Concurrency Control**: Manages simultaneous access by multiple users
     without conflicts.
  5. **Recovery**: Restores data to a consistent state after failures.

■ PURPOSE OF DBMS
──────────────────
  • **Data Redundancy Control**: Centralizes data, minimizing duplication.
  • **Data Consistency**: Ensures that the same data item has the same
    value across the entire system.
  • **Data Sharing**: Multiple users can access data concurrently.
  • **Data Integrity**: Enforces integrity constraints (e.g., primary keys,
    foreign keys, check constraints).
  • **Data Security**: Implements access control mechanisms to protect
    sensitive data.
  • **Backup and Recovery**: Provides automated backup and crash recovery.
  • **Data Independence**: Changes to data storage do not affect
    application programs.

■ APPLICATIONS OF DBMS
───────────────────────
  ┌─────────────────────────┬──────────────────────────────────────────┐
  │ Domain                  │ Application Example                      │
  ├─────────────────────────┼──────────────────────────────────────────┤
  │ Banking & Finance       │ Account management, transactions, loans  │
  │ Airlines                │ Reservations, flight scheduling          │
  │ Universities            │ Student records, enrollment, grades      │
  │ Telecommunications      │ Call records, billing, subscriber mgmt   │
  │ E-Commerce              │ Product catalog, orders, payments        │
  │ Healthcare              │ Patient records, prescriptions, billing  │
  │ Social Media            │ User profiles, posts, relationships      │
  │ Government              │ Citizen records, tax, census data        │
  │ Manufacturing           │ Inventory, supply chain, production      │
  └─────────────────────────┴──────────────────────────────────────────┘

■ EVOLUTION OF DBMS
────────────────────
  Flat Files → Hierarchical DBMS (1960s, IBM IMS)
    → Network DBMS (1970s, CODASYL)
      → Relational DBMS (1970s–present, E.F. Codd's model)
        → Object-Oriented DBMS (1990s)
          → NoSQL & NewSQL (2010s–present)

■ REAL-WORLD SCENARIO
──────────────────────
Consider **Amazon**: millions of products, billions of orders, hundreds of
millions of customers. Amazon uses a combination of relational databases
(Aurora/PostgreSQL for transactional data) and NoSQL databases (DynamoDB
for cart/session data). Without a DBMS, managing this volume of data with
consistency, high availability, and security would be impossible.

■ INTERVIEW ESSENTIALS
───────────────────────
  Q: What is a DBMS?
  A: A DBMS is software that provides an interface between the database
     and its users/applications, offering data definition, manipulation,
     security, concurrency control, and recovery capabilities.

  Q: Name 5 advantages of DBMS.
  A: Data independence, reduced redundancy, data integrity, concurrent
     access, and backup/recovery.

1.2  DATABASE SYSTEMS vs FILE SYSTEMS
================================================================================

■ FORMAL DEFINITION
────────────────────
A **File System** is an OS-level mechanism for storing and retrieving
individual files on disk. Data is organized as flat files with no
inherent relationship management between them.

A **Database System** is a unified system of software, hardware, data,
users, and procedures that manages structured collections of interrelated
data with built-in redundancy control, integrity, security, and
concurrency.

■ IN-DEPTH COMPARISON
──────────────────────

  ┌──────────────────────┬────────────────────────┬──────────────────────────┐
  │ Criteria             │ File System            │ Database System          │
  ├──────────────────────┼────────────────────────┼──────────────────────────┤
  │ Data Redundancy      │ High (duplicate data   │ Low (centralized,        │
  │                      │   across files)        │   normalization)         │
  │ Data Consistency     │ Difficult to maintain  │ Enforced by constraints  │
  │ Data Isolation       │ Data scattered in      │ Data logically           │
  │                      │   different files/fmts │   organized in tables    │
  │ Concurrent Access    │ No built-in support    │ Full concurrency control │
  │ Security             │ OS-level file perms    │ Fine-grained (row/col)   │
  │ Data Integrity       │ App-level enforcement  │ DBMS-enforced constraints│
  │ Crash Recovery       │ Manual/limited         │ Automatic (WAL, logs)    │
  │ Data Independence    │ None                   │ Physical + Logical       │
  │ Query Language       │ No standard query lang │ SQL (standardized)       │
  │ Relationships        │ Not supported          │ FK, joins, constraints   │
  │ Atomicity            │ Not guaranteed         │ Transaction-based (ACID) │
  │ Scalability          │ Limited                │ Designed for scale       │
  └──────────────────────┴────────────────────────┴──────────────────────────┘

■ PROBLEMS WITH FILE SYSTEMS
─────────────────────────────
  1. **Data Redundancy & Inconsistency**: Same data stored in multiple
     files in different formats leads to wasted storage and inconsistency.
  2. **Difficulty in Accessing Data**: No standard query language; requires
     writing new programs for each query.
  3. **Data Isolation**: Data scattered across multiple files and formats.
  4. **Integrity Problems**: Constraints (e.g., "balance >= 0") must be
     hard-coded in programs; adding new constraints requires code changes.
  5. **Atomicity Problems**: Partial updates during failures can leave data
     in an inconsistent state.
  6. **Concurrent Access Anomalies**: Uncontrolled simultaneous access
     leads to lost updates and dirty reads.
  7. **Security Problems**: Only coarse-grained file-level permissions.

■ REAL-WORLD SCENARIO
──────────────────────
Imagine a small college initially storing student records in Excel files:
  - "students.csv" in the admission office
  - "grades.csv" in the examination department
  - "fees.csv" in the accounts department

If a student changes their address, it must be updated in ALL files
manually — leading to inconsistency. A DBMS centralizes this data so a
single update propagates everywhere.

■ WHEN IS A FILE SYSTEM STILL APPROPRIATE?
───────────────────────────────────────────
  • Very small datasets with a single user
  • Simple logging (e.g., web server access logs)
  • Multimedia storage where relational structure is not needed
  • Embedded systems with extreme resource constraints

■ INTERVIEW ESSENTIALS
───────────────────────
  Q: Why is DBMS preferred over file systems?
  A: DBMS eliminates data redundancy, ensures consistency through
     constraints, supports concurrent access, provides crash recovery,
     and offers data independence — all of which file systems lack.

1.3  VIEW OF DATA
================================================================================

────────────────────────────────────────────────
1.3.1  DATA ABSTRACTION
────────────────────────────────────────────────

■ FORMAL DEFINITION
────────────────────
**Data Abstraction** is the process of hiding the complexity of how data
is physically stored and presenting only the essential information to
different categories of users. A DBMS provides three levels of abstraction:
Physical, Logical, and View.

■ THE THREE LEVELS OF DATA ABSTRACTION
───────────────────────────────────────

  ┌─────────────────────────────────────────────────────────────────┐
  │                      VIEW LEVEL (External)                      │
  │   [View 1]    [View 2]    [View 3]    ...    [View n]           │
  │   (Cashier)   (Manager)   (HR)               (Customer App)     │
  ├─────────────────────────────────────────────────────────────────┤
  │                    LOGICAL LEVEL (Conceptual)                   │
  │                                                                 │
  │   Full logical structure of the entire database                 │
  │   Tables, relationships, constraints, types                     │
  │   e.g., CREATE TABLE employee(id INT, name VARCHAR, ...)        │
  ├─────────────────────────────────────────────────────────────────┤
  │                    PHYSICAL LEVEL (Internal)                    │
  │                                                                 │
  │   How data is actually stored on disk                           │
  │   File structures, indexing, compression, block layout          │
  │   e.g., B⁺ tree index on employee.id, heap file for records     │
  └─────────────────────────────────────────────────────────────────┘

**1. Physical Level (Internal Level):**
   - The LOWEST level of abstraction.
   - Describes HOW data is physically stored on disk.
   - Deals with: file structures, storage allocation, indexing methods
     (B⁺ trees, hash), record placement, compression, encryption at rest.
   - Users and most application programmers do NOT interact at this level.
   - Managed by: Database Administrator (DBA) and the DBMS storage engine.

   Example: "The employee table is stored as a heap file with a clustered
   B⁺ tree index on the emp_id column, using 8KB pages."

**2. Logical Level (Conceptual Level):**
   - Describes WHAT data is stored and the relationships among them.
   - Defines: tables, columns, data types, constraints (PK, FK, CHECK),
     relationships, and views.
   - This is where the database schema lives.
   - Managed by: Database Administrators and Database Designers.

   Example:
     CREATE TABLE employee (
       emp_id    INT PRIMARY KEY,
       name      VARCHAR(100),
       dept_id   INT REFERENCES department(dept_id),
       salary    DECIMAL(10,2) CHECK (salary > 0)
     );

**3. View Level (External Level):**
   - The HIGHEST level of abstraction.
   - Describes only a PART of the entire database relevant to a
     particular user.
   - Different users see different views (subsets) of the same data.
   - Provides SECURITY: users see only what they are authorized to see.
   - Provides SIMPLICITY: users see only what they need.

   Example: The HR department sees employee names, departments, and
   salaries, but NOT the internal storage details or other unrelated
   tables like product inventory.

■ MERMAID FLOWCHART: THREE LEVELS OF ABSTRACTION

```mermaid
graph TD
    A[End Users & Applications] --> B[View Level]
    B --> B1[View 1: HR Staff]
    B --> B2[View 2: Manager]
    B --> B3[View 3: Customer App]
    B1 --> C[Logical Level]
    B2 --> C
    B3 --> C
    C --> C1[Tables, Relationships, Constraints]
    C1 --> D[Physical Level]
    D --> D1[Files, Indices, Disk Blocks]
```

────────────────────────────────────────────────
1.3.2  DATA INDEPENDENCE
────────────────────────────────────────────────

■ FORMAL DEFINITION
────────────────────
**Data Independence** is the ability to modify the schema at one level of
a database system without requiring changes to the schema at the next
higher level. It is a key benefit of the three-level architecture.

■ TWO TYPES OF DATA INDEPENDENCE
─────────────────────────────────

**1. Physical Data Independence:**
   - The ability to modify the PHYSICAL schema (how data is stored)
     without changing the LOGICAL schema.
   - This is RELATIVELY EASY to achieve.

   Examples of physical changes that should NOT affect logical schema:
     • Changing from heap file to sequential file organization
     • Adding or removing an index (e.g., creating a B⁺ tree on a column)
     • Moving the database to a faster disk or SSD
     • Changing compression or encryption methods
     • Reorganizing storage blocks

   WHY is it easier? Because the logical schema is an abstraction over
   the physical schema. The mapping between them is maintained by the
   DBMS internal mappings.

**2. Logical Data Independence:**
   - The ability to modify the LOGICAL schema without changing the
     EXTERNAL schema (views) or application programs.
   - This is MORE DIFFICULT to achieve.

   Examples of logical changes:
     • Adding a new column to a table
     • Adding a new table to the database
     • Splitting a table into two (decomposition)
     • Renaming a column

   WHY is it harder? Application programs and views are often tightly
   coupled to the logical schema. If a table is split, existing queries
   that reference the old table must be rewritten (or views must be
   created to maintain backward compatibility).

■ COMPARISON TABLE
──────────────────
  ┌──────────────────────────┬──────────────────────┬─────────────────────┐
  │ Aspect                   │ Physical Independence│ Logical Independence│
  ├──────────────────────────┼──────────────────────┼─────────────────────┤
  │ Modifies which level?    │ Physical (Internal)  │ Logical (Conceptual)│
  │ Which level unaffected?  │ Logical + View       │ View (External)     │
  │ Difficulty               │ Easier               │ Harder              │
  │ Example                  │ Add index on column  │ Add new column      │
  │ Managed by mapping       │ Internal ↔ Conceptual│ Conceptual ↔ Extern │
  └──────────────────────────┴──────────────────────┴─────────────────────┘

■ REAL-WORLD SCENARIO
──────────────────────
Consider **Instagram's database**:
  - **Physical Independence**: Instagram migrated from one storage engine
    to another (e.g., from MySQL InnoDB to RocksDB for certain workloads).
    The application code didn't change because the logical schema (tables,
    columns) remained the same.
  - **Logical Independence**: When Instagram added "Reels" as a feature,
    new tables were added to the logical schema. Existing features like
    "Stories" and "Posts" continued to work because their views/queries
    didn't reference the new tables.

■ INTERVIEW ESSENTIALS
───────────────────────
  Q: What is data independence?
  A: The ability to modify the schema at one level without affecting the
     schema at the next higher level.

  Q: Why is logical data independence harder than physical?
  A: Because applications and views are tightly coupled to the logical
     schema (table structures, column names), whereas the physical
     schema is an internal detail hidden by the DBMS.

1.4  INSTANCES AND SCHEMAS
================================================================================

■ FORMAL DEFINITION
────────────────────
• **Schema**: The overall design/structure of a database. It is the
  "blueprint" that describes how data is organized. The schema does NOT
  change frequently (it is relatively static).

• **Instance** (or **State**): The actual content of the database at a
  particular point in time. The instance changes every time data is
  inserted, updated, or deleted.

■ IN-DEPTH EXPLANATION
───────────────────────
Think of a schema like the STRUCTURE of an Excel spreadsheet (column
headers: Name, Age, City) and the instance as the ROWS of data currently
in the spreadsheet.

**Schema Types:**
  1. **Physical Schema**: Describes how data is stored at the physical
     level (file organization, index structures).
  2. **Logical Schema**: Describes the logical structure — tables, columns,
     data types, constraints, relationships. This is the MOST IMPORTANT
     schema from a database design perspective.
  3. **Subschema (View/External Schema)**: Describes different views of the
     database for different users.

**Key Difference:**
  - Schema = TYPE (structure)
  - Instance = VALUE (data at a moment)

■ EXAMPLE
──────────
Schema:
  student(roll_no: INT, name: VARCHAR(50), dept: VARCHAR(20), cgpa: FLOAT)

Instance (at time T₁):
  ┌─────────┬────────┬──────┬──────┐
  │ roll_no │ name   │ dept │ cgpa │
  ├─────────┼────────┼──────┼──────┤
  │ 101     │ Aarav  │ CS   │ 3.8  │
  │ 102     │ Bipana │ IT   │ 3.5  │
  │ 103     │ Chetan │ CS   │ 3.9  │
  └─────────┴────────┴──────┴──────┘

Instance (at time T₂ — after INSERT):
  ┌─────────┬────────┬──────┬──────┐
  │ roll_no │ name   │ dept │ cgpa │
  ├─────────┼────────┼──────┼──────┤
  │ 101     │ Aarav  │ CS   │ 3.8  │
  │ 102     │ Bipana │ IT   │ 3.5  │
  │ 103     │ Chetan │ CS   │ 3.9  │
  │ 104     │ Deepa  │ EE   │ 3.7  │    ← NEW ROW
  └─────────┴────────┴──────┴──────┘

The SCHEMA hasn't changed — only the INSTANCE has.

■ ANALOGY
──────────
  Schema → Class definition in OOP (e.g., class Student { int id; ... })
  Instance → Object/instance of that class (e.g., Student s1 = new Student())

■ INTERVIEW ESSENTIALS
───────────────────────
  Q: How is schema different from instance?
  A: Schema is the structural description (metadata) of the database —
     tables, columns, types, constraints. Instance is the actual data
     stored at a given moment. Schema rarely changes; instances change
     with every DML operation.

1.5  DATABASE LANGUAGES
================================================================================

A DBMS provides specialized languages for different operations on the
database. These are broadly categorized into DDL, DML, and DCL.

────────────────────────────────────────────────
1.5.1  DDL — DATA DEFINITION LANGUAGE
────────────────────────────────────────────────

■ FORMAL DEFINITION
────────────────────
**DDL (Data Definition Language)** is a set of SQL commands used to
define, modify, and delete database structures (schemas). DDL commands
operate on the METADATA (structure) of the database, NOT the data itself.

■ KEY DDL COMMANDS
───────────────────
  ┌──────────────┬──────────────────────────────────────────────────────┐
  │ Command      │ Purpose                                              │
  ├──────────────┼──────────────────────────────────────────────────────┤
  │ CREATE       │ Create a new table, database, view, index, etc.      │
  │ ALTER        │ Modify the structure of an existing table            │
  │ DROP         │ Delete a table, database, view, or index entirely    │
  │ TRUNCATE     │ Remove all rows from a table (structure remains)     │
  │ RENAME       │ Rename a table or column                             │
  └──────────────┴──────────────────────────────────────────────────────┘

■ EXAMPLES
───────────
  CREATE TABLE employee (
    emp_id   INT PRIMARY KEY,
    name     VARCHAR(100) NOT NULL,
    salary   DECIMAL(10,2),
    dept_id  INT REFERENCES department(dept_id)
  );

  ALTER TABLE employee ADD COLUMN email VARCHAR(100);

  DROP TABLE employee;

  TRUNCATE TABLE employee;  -- deletes all data, keeps structure

■ DATA DICTIONARY
──────────────────
When a DDL statement is executed, the DBMS stores the schema metadata in
a special set of tables called the **Data Dictionary** (or **System
Catalog**). The data dictionary contains:
  • Table names, column names, data types
  • Constraints (PK, FK, UNIQUE, CHECK, NOT NULL)
  • Index definitions
  • View definitions
  • User privileges

────────────────────────────────────────────────
1.5.2  DML — DATA MANIPULATION LANGUAGE
────────────────────────────────────────────────

■ FORMAL DEFINITION
────────────────────
**DML (Data Manipulation Language)** is a set of SQL commands used to
retrieve, insert, update, and delete DATA within the database tables.

■ TWO TYPES OF DML
────────────────────
  1. **Procedural DML**: The user specifies WHAT data is needed AND HOW to
     get it (step-by-step). Example: Relational Algebra.
  2. **Declarative (Non-Procedural) DML**: The user specifies WHAT data is
     needed but NOT how to get it. The DBMS optimizer decides the best
     strategy. Example: SQL.

■ KEY DML COMMANDS
───────────────────
  ┌──────────────┬──────────────────────────────────────────────────────┐
  │ Command      │ Purpose                                              │
  ├──────────────┼──────────────────────────────────────────────────────┤
  │ SELECT       │ Retrieve data from one or more tables                │
  │ INSERT       │ Add new rows to a table                              │
  │ UPDATE       │ Modify existing rows in a table                      │
  │ DELETE       │ Remove rows from a table                             │
  └──────────────┴──────────────────────────────────────────────────────┘

■ EXAMPLES
───────────
  SELECT name, salary FROM employee WHERE dept_id = 5;

  INSERT INTO employee (emp_id, name, salary, dept_id)
  VALUES (1001, 'Hari', 55000.00, 3);

  UPDATE employee SET salary = salary * 1.10 WHERE dept_id = 5;

  DELETE FROM employee WHERE emp_id = 1001;

────────────────────────────────────────────────
1.5.3  DCL — DATA CONTROL LANGUAGE
────────────────────────────────────────────────

■ FORMAL DEFINITION
────────────────────
**DCL (Data Control Language)** is a set of SQL commands used to control
access and permissions on database objects. It manages WHO can do WHAT
on which database objects.

■ KEY DCL COMMANDS
───────────────────
  ┌──────────────┬──────────────────────────────────────────────────────┐
  │ Command      │ Purpose                                              │
  ├──────────────┼──────────────────────────────────────────────────────┤
  │ GRANT        │ Give specific privileges to a user or role           │
  │ REVOKE       │ Remove previously granted privileges                 │
  └──────────────┴──────────────────────────────────────────────────────┘

■ EXAMPLES
───────────
  GRANT SELECT, INSERT ON employee TO user_hr;
  GRANT ALL PRIVILEGES ON employee TO admin;
  REVOKE INSERT ON employee FROM user_hr;

■ ADDITIONAL: TCL — TRANSACTION CONTROL LANGUAGE
──────────────────────────────────────────────────
(Sometimes grouped separately from DML)
  • COMMIT: Save all changes made during a transaction.
  • ROLLBACK: Undo all changes since the last COMMIT.
  • SAVEPOINT: Set a point within a transaction to which you can rollback.

■ SUMMARY TABLE
────────────────
  ┌──────┬──────────────────────┬──────────────────────────────────┐
  │ Type │ Commands             │ Operates On                      │
  ├──────┼──────────────────────┼──────────────────────────────────┤
  │ DDL  │ CREATE, ALTER, DROP  │ Schema / Structure (metadata)    │
  │      │ TRUNCATE, RENAME     │                                  │
  │ DML  │ SELECT, INSERT,      │ Data (rows/records)              │
  │      │ UPDATE, DELETE       │                                  │
  │ DCL  │ GRANT, REVOKE        │ Permissions / Access Control     │
  │ TCL  │ COMMIT, ROLLBACK,    │ Transactions                     │
  │      │ SAVEPOINT            │                                  │
  └──────┴──────────────────────┴──────────────────────────────────┘

■ INTERVIEW ESSENTIALS
───────────────────────
  Q: Differentiate between DDL and DML.
  A: DDL defines/modifies the structure (CREATE, ALTER, DROP) while DML
     manipulates the data (SELECT, INSERT, UPDATE, DELETE). DDL is
     auto-committed; DML can be rolled back before COMMIT.

  Q: What role does DCL play?
  A: DCL manages user permissions and access control through GRANT and
     REVOKE commands, ensuring database security.

1.6  DATABASE AND APPLICATION ARCHITECTURE
================================================================================

────────────────────────────────────────────────
1.6.1  DATABASE SYSTEM ARCHITECTURE
────────────────────────────────────────────────

■ FORMAL DEFINITION
────────────────────
The **Database System Architecture** describes the internal components of
a DBMS and how they interact to process queries, manage storage, enforce
security, and handle transactions.

■ COMPONENTS OF DATABASE SYSTEM ARCHITECTURE

  ┌─────────────────────────────────────────────────────────────────┐
  │                       DATABASE USERS                            │
  │  [Naive Users] [App Programmers] [Sophisticated Users] [DBA]    │
  ├─────────────────────────────────────────────────────────────────┤
  │                     APPLICATION PROGRAMS                        │
  │                     & QUERY INTERFACES                          │
  ├─────────────────────────────────────────────────────────────────┤
  │                     QUERY PROCESSOR                             │
  │  ┌───────────────┐  ┌───────────────┐  ┌──────────────────┐     │
  │  │ DDL Compiler  │  │ DML Compiler  │  │ Query Optimizer  │     │
  │  │ (Interpreter) │  │ & Parser      │  │ & Evaluation Eng │     │
  │  └───────────────┘  └───────────────┘  └──────────────────┘     │
  ├─────────────────────────────────────────────────────────────────┤
  │                     STORAGE MANAGER                             │
  │  ┌────────────────┐ ┌────────────────┐ ┌────────────────────┐   │
  │  │ Authorization  │ │ Transaction    │ │ File Manager       │   │
  │  │ & Integrity Mgr│ │ Manager        │ │ & Buffer Manager   │   │
  │  └────────────────┘ └────────────────┘ └────────────────────┘   │
  ├─────────────────────────────────────────────────────────────────┤
  │                     DISK STORAGE                                │
  │  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────────┐     │
  │  │Data Files│  │ Data Dict│  │ Indices  │  │ Statistical  │     │
  │  │          │  │ (Catalog)│  │          │  │ Data         │     │
  │  └──────────┘  └──────────┘  └──────────┘  └──────────────┘     │
  └─────────────────────────────────────────────────────────────────┘

■ KEY COMPONENTS EXPLAINED
───────────────────────────

**1. Query Processor:**
  • **DDL Interpreter**: Processes DDL statements and records schema
    definitions in the data dictionary.
  • **DML Compiler/Parser**: Translates DML statements into low-level
    instructions (query evaluation plans).
  • **Query Optimizer**: Chooses the most efficient evaluation plan by
    considering available indices, table statistics, and join strategies.
  • **Query Evaluation Engine**: Executes the chosen plan and returns
    results.

**2. Storage Manager:**
  • **Authorization & Integrity Manager**: Checks user permissions and
    enforces integrity constraints.
  • **Transaction Manager**: Ensures ACID properties, manages concurrent
    access, handles recovery.
  • **File Manager**: Manages allocation of disk space and data structures
    used to store information.
  • **Buffer Manager**: Manages the transfer of data between disk and
    main memory (buffer pool).

**3. Disk Storage:**
  • **Data Files**: Actual data stored in tables.
  • **Data Dictionary**: Metadata about schema, constraints, users.
  • **Indices**: B⁺ trees, hash indices for fast data access.
  • **Statistical Data**: Table sizes, value distributions for the
    query optimizer.

■ TYPES OF DATABASE USERS
──────────────────────────
  1. **Naive Users**: End-users who interact via pre-built application
     interfaces (e.g., ATM users, web app users).
  2. **Application Programmers**: Write application programs using DML
     calls embedded in host languages (Java, Python, C#).
  3. **Sophisticated Users**: Interact directly with the DBMS using SQL
     (analysts, data scientists).
  4. **Database Administrator (DBA)**: Has full control over the database;
     defines schemas, grants access, tunes performance, manages backups.

■ ROLE OF DATABASE ADMINISTRATOR (DBA)
───────────────────────────────────────
  • Schema definition and modification
  • Storage structure and access method definition
  • Granting/revoking authorization
  • Routine maintenance (backups, performance tuning, disk management)
  • Integrity constraint specification

────────────────────────────────────────────────
1.6.2  DATABASE APPLICATION ARCHITECTURE
────────────────────────────────────────────────

■ TWO-TIER ARCHITECTURE (Client-Server)
────────────────────────────────────────

  ┌──────────────────┐        ┌───────────────────────┐
  │   CLIENT TIER    │  SQL   │    SERVER TIER        │
  │                  │◄──────►│                       │
  │  - Application   │  ODBC/ │  - DBMS Engine        │
  │  - User Interface│  JDBC  │  - Query Processing   │
  │  - Business Logic│        │  - Storage Management │
  │                  │        │  - Database Files     │
  └──────────────────┘        └───────────────────────┘

**How it works:**
  • The CLIENT contains both the user interface AND business logic.
  • The client communicates DIRECTLY with the database server using
    APIs like ODBC (Open Database Connectivity) or JDBC (Java Database
    Connectivity).
  • The server processes SQL queries and returns results.

**Pros:**
  • Simple architecture, easy to set up.
  • Good for small-scale applications with few users.

**Cons:**
  • Business logic on the client → difficult to maintain and update.
  • Security risk: clients have direct DB access.
  • Poor scalability for many concurrent users.
  • Fat client: requires more resources on client machines.

**Example:** A desktop accounting application (like Tally) that connects
directly to a central database server.

■ THREE-TIER ARCHITECTURE
──────────────────────────

  ┌────────────────┐    ┌────────────────────┐    ┌─────────────────┐
  │ PRESENTATION   │    │  APPLICATION       │    │ DATA TIER       │
  │ TIER (Client)  │◄──►│  TIER (Server)     │◄──►│ (Database)      │
  │                │HTTP│                    │SQL │                 │
  │ - Web Browser  │    │ - Business Logic   │    │ - DBMS Engine   │
  │ - Mobile App   │    │ - Application      │    │ - Data Storage  │
  │ - UI rendering │    │   Server (API)     │    │ - Query Proc.   │
  │                │    │ - Authentication   │    │                 │
  └────────────────┘    └────────────────────┘    └─────────────────┘

**How it works:**
  1. The CLIENT (Presentation Tier) only handles the user interface
     (web browser, mobile app). It sends requests (HTTP/HTTPS) to the
     application server.
  2. The APPLICATION SERVER (Middle Tier) contains all business logic,
     processes requests, validates data, and communicates with the database.
  3. The DATABASE SERVER (Data Tier) stores and manages data. Only the
     application server communicates with it — clients NEVER directly
     access the database.

**Pros:**
  • **Security**: Clients never touch the database directly.
  • **Scalability**: Application servers can be scaled horizontally.
  • **Maintainability**: Business logic is centralized; updates don't
    require client-side changes.
  • **Flexibility**: Different clients (web, mobile, desktop) can share
    the same application server and database.

**Cons:**
  • More complex to design and deploy.
  • Additional network latency (extra tier).
  • Requires more infrastructure (app server + DB server).

**Example:** Modern web applications like **Facebook**, **Amazon**:
  - Client: React/Angular web app or mobile app
  - App Server: Node.js/Django/Spring Boot handling API requests
  - Database: PostgreSQL/MySQL/DynamoDB storing data

■ COMPARISON TABLE
──────────────────
  ┌──────────────────────┬─────────────────────┬────────────────────────┐
  │ Feature              │ Two-Tier            │ Three-Tier             │
  ├──────────────────────┼─────────────────────┼────────────────────────┤
  │ Client complexity    │ Fat (logic + UI)    │ Thin (UI only)         │
  │ Security             │ Low (direct DB)     │ High (no direct DB)    │
  │ Scalability          │ Limited             │ Highly scalable        │
  │ Maintenance          │ Harder              │ Easier (centralized)   │
  │ Network round-trips  │ Fewer               │ More (extra tier)      │
  │ Cost                 │ Lower               │ Higher                 │
  │ Use case             │ Small/desktop apps  │ Web/enterprise apps    │
  └──────────────────────┴─────────────────────┴────────────────────────┘

■ INTERVIEW ESSENTIALS
───────────────────────
  Q: What is the advantage of three-tier over two-tier architecture?
  A: Three-tier provides better security (no direct DB access from client),
     improved scalability (app server can be scaled independently),
     centralized business logic maintenance, and supports multiple client
     types (web, mobile) with the same backend.

  Q: What is the role of a DBA?
  A: The DBA is responsible for schema definition, access control, backup
     and recovery, performance tuning, and ensuring data integrity and
     security.
