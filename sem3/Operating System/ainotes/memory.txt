1.0  THE FOUNDATIONS (THE "WHY" AND "WHERE")
================================================================================

Before learning allocation, paging, and replacement algorithms, students must
first understand one central problem in computer architecture and operating
systems:

  Fast memory is expensive and small.
  Large memory is cheap and slow.

An operating system exists partly to hide this hardware contradiction and give
programs the illusion of a large, fast, safe, and private memory space.

Why this section exists:
  1. It builds the conceptual base used in all later units.
  2. It explains why abstractions like virtual address and page table exist.
  3. It connects hardware details (cache, MMU, DRAM) with OS policies.

Real-life analogy:
  Think of a hospital emergency system.

  - Doctor's hand tools      -> Registers (tiny, instant access)
  - Emergency room tray      -> Cache (small, very fast)
  - Nearby medicine cabinet  -> RAM (larger, moderate speed)
  - Main warehouse           -> Disk/SSD (very large, slower)

The doctor (CPU) cannot fetch from warehouse every second. The workflow only
works if frequently needed items stay near the doctor.

OS implementation perspective:
  The kernel memory subsystem, CPU cache hierarchy, and MMU collaborate to
  maintain performance, protection, and process isolation.

Advantages of studying foundations first:
  - Better understanding of exam numericals in paging and replacement.
  - Strong intuition for performance bottlenecks.
  - Easier debugging of memory-related behavior in real systems.

Limitations if ignored:
  - Students memorize algorithms without understanding why they exist.
  - Confusion between hardware address and software-visible address.
  - Weak understanding of page faults, TLB misses, and thrashing.

1.1  MEMORY HIERARCHY: WHY WE USE REGISTERS, CACHE, RAM, AND DISK
--------------------------------------------------------------------------------

Definition:
  Memory hierarchy is the layered arrangement of storage technologies ordered
  by speed, capacity, and cost per bit.

Why this concept exists:
  No single device can provide all three goals simultaneously:

  1. Ultra-fast access time
  2. Very large capacity
  3. Very low cost

  Therefore systems combine many levels and move data between them.

Internal working mechanism (step by step):
  1. CPU executes instructions using registers.
  2. If data is not in registers, CPU checks cache hierarchy (L1 -> L2 -> L3).
  3. On cache miss, controller fetches from DRAM.
  4. If page is not in DRAM (virtual memory case), OS fetches from disk.
  5. Data is brought upward and reused according to locality.

Core principle: Locality of reference
  1. Temporal locality: recently used data is likely used again soon.
  2. Spatial locality: nearby addresses are likely used soon.

ASCII flow diagram:

        CPU Registers
             │
             ▼
            L1
             │
             ▼
            L2
             │
             ▼
            L3
             │
             ▼
           DRAM
             │
             ▼
         SSD / HDD

Comparison table:

Memory Level         Speed           Cost/Bit         Capacity
---------------------------------------------------------------------
Registers            Fastest         Highest          Tiny
L1/L2/L3 Cache       Very Fast       Very High        Small to Medium
RAM (DRAM)           Fast            Moderate         Large
SSD                  Slower          Low              Very Large
HDD                  Slowest         Very Low         Very Large

Operating system implementation:
  - Scheduler and memory manager try to keep active process data hot in RAM.
  - Kernel uses page cache to reduce disk I/O.
  - Virtual memory subsystem decides when pages stay in RAM or are evicted.

Real-life analogy:
  Kitchen workflow:

  - Items in hand                  -> Registers
  - Items on kitchen counter       -> Cache
  - Items in kitchen cabinets      -> RAM
  - Items in basement storage      -> Disk

  Cooking is fastest when frequently used items stay near the counter.

Advantages:
  1. High average performance with affordable hardware cost.
  2. Scalable system design across laptops, servers, and mobiles.
  3. Enables abstraction that applications can use seamlessly.

Disadvantages:
  1. Complexity in data movement and coherence.
  2. Performance unpredictability due to misses (cache/TLB/page fault).
  3. Requires careful hardware-OS coordination.

    Micro-topic: Cache Hits, Misses, and Penalty
    ─────────────────────────────────────────────
    Definition:
      A cache hit occurs when requested data is found in cache.
      A cache miss occurs when data is absent and must be fetched below.

    Why important:
      CPU speed is orders of magnitude faster than DRAM and disk.
      Small changes in hit ratio can significantly affect runtime.

    Effective access intuition:
      Effective time = Hit probability × hit time + Miss probability × miss cost

      Even a 2% miss at high miss cost can dominate execution time.

    OS angle:
      Process scheduling, memory allocation patterns, and file caching strategy
      influence cache and memory behavior indirectly.

        Deeper: Multi-core Cache Coherence (MESI Preview)
        ──────────────────────────────────────────────────
        In a multi-core CPU, each core may cache the same memory line. If one
        core updates it, other copies become stale. Coherence protocols track
        line states so all cores eventually observe consistent values.


    Key Points
    ──────────
    • Memory hierarchy exists because speed, cost, and capacity conflict.
    • Locality is the mathematical reason caches work.
    • Average access time is dominated by miss penalties.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. Define temporal and spatial locality with examples.
      2. Why cannot we build a computer using only registers?

    Long Questions (8–10 marks)
      1. Explain memory hierarchy with diagram and practical implications.
      2. Compare register, cache, RAM, and disk in one coherent answer.

    Numerical Problems
      1. Compute effective access time using hit ratio and miss penalty.
      2. Compare performance after cache hit ratio increases from 90% to 95%.

1.2  STORAGE ORGANIZATION: VOLATILE VS NON-VOLATILE MEMORY
--------------------------------------------------------------------------------

Definition:
  Storage organization classifies memory by persistence, speed, and usage role.

Primary classification:
  1. Volatile memory:
     Data is lost when power is removed.
     Examples: registers, cache (SRAM), DRAM.

  2. Non-volatile memory:
     Data remains after power loss.
     Examples: SSD (flash), HDD (magnetic), ROM, NVRAM.

Why this concept exists:
  Programs need both temporary working area and permanent retention.

  - Temporary working area is optimized for speed (volatile).
  - Persistent storage is optimized for retention and capacity.

Internal working mechanism:
  1. Program executable is stored on non-volatile storage (SSD/HDD).
  2. Loader places program pages into volatile RAM during execution.
  3. CPU runs with volatile levels (cache/registers).
  4. On shutdown/power failure, RAM content vanishes.
  5. Persistent files remain safely in non-volatile storage.

ASCII architecture view:

      Persistent Layer (Non-Volatile)
      +-----------------------------+
      |  SSD / HDD / ROM / NVRAM    |
      +-----------------------------+
                   │ Load/Store
                   ▼
      Volatile Execution Layer
      +-----------------------------+
      |       RAM / Cache / Reg     |
      +-----------------------------+

Table: Volatile vs Non-Volatile

Property                 Volatile Memory                Non-Volatile Memory
-------------------------------------------------------------------------------
Power-off data           Lost                           Preserved
Speed                    High                           Lower (typically)
Capacity                 Lower to medium                Medium to very high
Cost per bit             Higher                         Lower
Primary usage            Active execution               Long-term storage
Typical examples         SRAM, DRAM, CPU registers      SSD, HDD, Flash, ROM

Operating system implementation:
  - Filesystem manages persistent data on non-volatile devices.
  - Virtual memory and page cache bridge persistent storage and RAM.
  - Journaling filesystems protect consistency after crashes.

Real-life analogy:
  Student study setup:

  - Open notebook on desk (currently used) -> volatile working memory.
  - Library shelf and hard-copy archive     -> non-volatile storage.

  If the table is cleared suddenly, open notes disappear; library books remain.

Advantages and disadvantages:

  Volatile memory
    Advantages:
      1. Very fast random access.
      2. Essential for active instruction/data processing.

    Disadvantages:
      1. Data loss on power failure.
      2. Higher cost per bit.

  Non-volatile memory
    Advantages:
      1. Persistent storage.
      2. Lower cost for large capacities.

    Disadvantages:
      1. Slower access than RAM.
      2. Some media have limited write endurance (flash).

    Micro-topic: Why RAM Is Not Used as Permanent Storage
    ──────────────────────────────────────────────────────
    1. Cost factor: storing terabytes in DRAM is expensive.
    2. Persistence factor: DRAM needs continuous refresh power.
    3. Reliability factor: power failures erase volatile content.

    OS consequence:
      Critical data is periodically flushed from page cache to disk to avoid
      loss and ensure durability guarantees.

        Deeper: Emerging NVRAM and Persistent Memory
        ─────────────────────────────────────────────
        Newer technologies aim to blend persistence with near-DRAM speed.
        Operating systems adapt by introducing byte-addressable persistent
        memory support, new filesystems, and modified crash-consistency logic.


    Key Points
    ──────────
    • Volatile memory is for speed; non-volatile memory is for persistence.
    • All executing programs must ultimately be in volatile layers.
    • OS acts as transfer manager between persistent and execution storage.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. Define volatile and non-volatile memory with two examples each.
      2. Why is SSD considered non-volatile but RAM not?

    Long Questions (8–10 marks)
      1. Explain storage organization and OS role in managing both types.
      2. Compare DRAM and SSD from OS memory-management perspective.

    Numerical Problems
      1. Estimate load time for a 500 MB process from SSD to RAM.
      2. Compare throughput effects between RAM and disk access scenarios.

1.3  LOGICAL VS PHYSICAL ADDRESS: CPU VIEW VS REAL RAM LOCATION
--------------------------------------------------------------------------------

Definition:
  Logical (virtual) address:
    Address generated by CPU during program execution.

  Physical address:
    Actual address location in main memory hardware.

Why this concept exists:
  1. Process isolation and security.
  2. Program relocation flexibility.
  3. Simplified programming model independent of actual RAM layout.

Internal working mechanism (base-level conceptual model):
  1. Program issues logical address LA.
  2. MMU translates LA into physical address PA.
  3. Memory controller accesses RAM at PA.
  4. Process never directly sees raw physical layout.

Basic equation (simple relocation model):

      PA = Base + LA

Bounds check condition:

      0 <= LA < Limit

If invalid:
  hardware trap is raised (protection fault / segmentation fault class).

ASCII translation path:

      Logical Address (CPU)
              │
              ▼
        +-----------+
        |   MMU     |
        +-----------+
              │
              ▼
      Physical Address (RAM)

Real-life analogy:
  Apartment mailbox system:

  - Resident writes flat number (logical address).
  - Building management maps flat number to physical delivery route.
  - Residents use simple numbering; they do not manage infrastructure paths.

OS implementation details:
  - Per-process address space: each process thinks it starts near address 0.
  - Kernel maps logical pages to different physical frames for each process.
  - Shared memory maps same physical frame into multiple process spaces.

Why students confuse this topic:
  1. Both addresses are numbers, but from different viewpoints.
  2. Same logical address in two processes can map to different physical pages.

Advantages of logical addressing:
  1. Security via isolation.
  2. Easier compilation/loading.
  3. Virtual memory support beyond physical RAM size.

Limitations / trade-offs:
  1. Translation overhead (MMU, TLB miss cost).
  2. Additional data structures (page tables).
  3. Complexity in kernel memory management.

Table: Logical vs Physical

Aspect                    Logical Address                  Physical Address
-------------------------------------------------------------------------------
Generated by              CPU execution unit              MMU translation output
Visible to process        Yes                             No (normally hidden)
Address space scope       Per-process                     System-wide RAM view
Security implication      Enables isolation               Must be protected
Flexibility               High (virtual mapping)          Low (real hardware map)

    Micro-topic: Address Space Isolation
    ────────────────────────────────────
    If Process A and Process B both access logical address 4096, they can still
    reach completely different physical locations.

    This is the foundation of process protection and multiprogramming.

        Deeper: Shared Libraries and Shared Memory
        ───────────────────────────────────────────
        Two processes may intentionally map a common physical page (for shared
        library code or IPC). Logical addresses may differ, physical frame can
        be same. This gives memory efficiency with controlled sharing.


    Key Points
    ──────────
    • Logical address is process perspective; physical is hardware perspective.
    • MMU performs translation and protection check.
    • Same logical value in different processes does not imply same RAM cell.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. Distinguish logical and physical addresses.
      2. Why is address translation necessary in multitasking OS?

    Long Questions (8–10 marks)
      1. Explain address translation path with base-limit model and diagram.
      2. Discuss process isolation using logical address spaces.

    Numerical Problems
      1. Given Base and Limit, determine valid/invalid logical addresses.
      2. Compute physical address for multiple logical requests.

1.4  THE MMU (MEMORY MANAGEMENT UNIT): HARDWARE ADDRESS TRANSLATION
--------------------------------------------------------------------------------

Definition:
  MMU is a hardware component between CPU and memory system that translates
  logical addresses into physical addresses and enforces protection rules.

Why MMU exists:
  1. To provide per-process private address spaces.
  2. To enforce memory protection in hardware (fast and secure).
  3. To support relocation, paging, segmentation, and virtual memory.

Internal working mechanism (page-based modern view):
  1. CPU emits virtual address VA.
  2. MMU extracts Virtual Page Number (VPN) and offset.
  3. MMU checks TLB for VPN -> PFN mapping.
  4. On TLB hit: compose physical address and continue.
  5. On TLB miss: walk page table (hardware or kernel-assisted).
  6. If page invalid/not present: raise page fault trap.
  7. After OS handles fault and updates mapping, instruction restarts.

ASCII diagram:

      CPU (Virtual Address)
              │
              ▼
        +----------------+
        |      MMU       |
        |  +----------+  |
        |  |   TLB    |  |
        |  +----------+  |
        +----------------+
              │
      +-------+--------+
      |                |
      ▼                ▼
  Page Table Walk    TLB Hit
      │                │
      +-------+--------+
              ▼
      Physical Address
              │
              ▼
             RAM

MMU responsibilities in OS context:
  1. Translation
  2. Protection (R/W/X, user/kernel)
  3. Fault generation for illegal access
  4. Support for context switching via page table base register changes

Real-life analogy:
  MMU is like a secure receptionist in a large office complex:

  - Employee asks for room number (virtual address).
  - Reception verifies access rights and maps to real building location.
  - Unauthorized request triggers alarm (fault/trap).

Advantages:
  1. Strong process isolation.
  2. Flexible virtual memory abstractions.
  3. Efficient sharing and memory overcommit strategies.

Disadvantages / costs:
  1. Translation overhead without TLB.
  2. Hardware complexity.
  3. Page-table memory overhead for large address spaces.

Table: MMU Without TLB vs With TLB

Scenario                     Translation Cost              Practical Impact
-------------------------------------------------------------------------------
Without TLB                  Frequent page-table access    Significant slowdown
With TLB (high hit rate)     Mostly cached translation     Near-RAM speed access
TLB miss path                Table walk + possible fault   Latency spike

    Micro-topic: Hardware Protection Bits
    ────────────────────────────────────
    Page table entries typically carry bits such as:
      - Present/Valid bit
      - Read/Write permission
      - Execute disable (NX)
      - User/Supervisor mode
      - Accessed and Dirty indicators

    Why these bits matter:
      They let hardware block illegal memory operations instantly, before data
      corruption or kernel compromise occurs.

        Deeper: MMU and Context Switching
        ─────────────────────────────────
        During context switch, kernel changes page-table root (for example,
        CR3 on x86). That instantly changes virtual->physical mapping context.
        The same virtual address can now refer to another process's data.

        This is the hardware foundation of multiprogramming isolation.


    Key Points
    ──────────
    • MMU is the hardware engine of virtual memory.
    • TLB is essential to keep translation overhead low.
    • Faults generated by MMU are handled by kernel trap handlers.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. What is MMU and why is it required?
      2. Differentiate TLB hit and TLB miss.

    Long Questions (8–10 marks)
      1. Explain modern address translation pipeline using MMU and page table.
      2. Describe MMU role in protection and context switching.

    Numerical Problems
      1. Compute effective access time for given TLB hit ratio.
      2. Calculate translation cost for mixed hit/miss workload.

2.0  CONTIGUOUS ALLOCATION (OLD SCHOOL: THE "BIG BLOCKS")
================================================================================

Contiguous allocation is the classical memory management method in which each
process receives one continuous (single-piece) region of physical memory.

Historical reason this model was used:
  1. Early systems had simpler hardware and no advanced paging support.
  2. Address translation was easier using base and limit registers.
  3. OS implementation complexity had to remain low.

Why this topic still matters today:
  - It teaches the origin of fragmentation problems.
  - It provides the conceptual bridge to paging and segmentation.
  - Many exam questions ask for comparison with modern methods.

Internal working idea:
  1. OS maintains a list of free holes in RAM.
  2. Process arrives with memory requirement S.
  3. OS selects a hole according to a placement algorithm.
  4. Process is loaded into one contiguous region.
  5. On termination, region becomes free hole again.

ASCII conceptual diagram:

      Physical Memory (Contiguous Allocation)

      +------------------------------------------------------------+
      |  OS  |   P1   |   Hole   |    P2    | Hole |     P3       |
      +------------------------------------------------------------+

Real-life analogy:
  Think of a hotel corridor where each guest group needs adjacent rooms only.
  Even if total empty rooms are enough, scattered single rooms cannot host a
  large group needing consecutive rooms.

OS implementation note:
  Many embedded and special-purpose systems still use simplified contiguous
  strategies due to deterministic behavior and low implementation overhead.

2.1  FIXED PARTITIONING: DIVIDING RAM INTO SET SIZES
--------------------------------------------------------------------------------

Definition:
  Fixed partitioning divides main memory into pre-defined partitions at boot
  time. Each partition can hold at most one process.

Why this concept exists:
  1. Extremely simple memory bookkeeping.
  2. Fast admission control.
  3. Suitable for early multiprogramming systems.

Internal working mechanism:
  1. OS creates fixed partitions (equal or unequal size).
  2. Incoming process is assigned to the first suitable free partition.
  3. If process size exceeds largest partition, process waits/rejected.
  4. On completion, whole partition becomes free.

Illustration:

      RAM = 1 GB

      +---------+---------+---------+---------+
      | 256 MB  | 256 MB  | 256 MB  | 256 MB  |
      |   P1    |   P2    |  Free   |   P3    |
      +---------+---------+---------+---------+

If P3 uses only 120 MB, remaining 136 MB inside that partition is unusable for
other processes. This unused-in-allocated-space is internal fragmentation.

Why internal fragmentation occurs here:
  Allocation granularity is partition size, not exact process size.

Table: Equal vs Unequal Fixed Partitioning

Partitioning Type        Description                     Effect
-------------------------------------------------------------------------------
Equal partitions         All same size                   Simple but rigid
Unequal partitions       Mix of small/medium/large       Better fit, still waste

Operating system implementation:
  - OS can maintain a partition descriptor table with status bits:
      Partition ID, Size, Occupied/Free, Process ID.
  - Scheduling and admission can be tightly coupled with partition availability.

Real-life analogy:
  Bus seats reserved in fixed clusters. A family of 2 in a cluster of 4 wastes
  2 seats, and those seats cannot be reassigned across cluster boundaries.

Advantages:
  1. Very easy to implement.
  2. Predictable allocation time.
  3. Low metadata overhead.

Disadvantages:
  1. Internal fragmentation can be severe.
  2. Number of concurrently resident processes is capped by partition count.
  3. Inflexible for mixed-size workloads.

    Micro-topic: Degree of Multiprogramming Limit
    ──────────────────────────────────────────────
    If there are N partitions, at most N processes can reside simultaneously,
    regardless of total free memory inside partially used partitions.

        Deeper: Why Fixed Partitioning Faded Out
        ─────────────────────────────────────────
        Modern workloads are dynamic and memory demands fluctuate rapidly.
        Fixed partitioning cannot adapt to this variability, so systems moved
        toward variable partitioning and then paging-based virtual memory.


    Key Points
    ──────────
    • Fixed partitioning is simple but memory-inefficient.
    • It mainly suffers from internal fragmentation.
    • Partition count limits multiprogramming.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. Define fixed partitioning and internal fragmentation.
      2. Why does equal partitioning waste memory?

    Long Questions (8–10 marks)
      1. Explain fixed partitioning with example and limitations.
      2. Compare equal and unequal partitioning.

    Numerical Problems
      1. Given process sizes and partition layout, compute unused memory.
      2. Determine number of admitted processes under fixed partitions.

2.2  VARIABLE PARTITIONING: DYNAMIC DIVISION AS PROCESSES ARRIVE
--------------------------------------------------------------------------------

Definition:
  Variable (dynamic) partitioning creates memory blocks according to process
  size at allocation time instead of using predefined fixed partitions.

Why this concept exists:
  1. Reduce internal fragmentation.
  2. Improve memory utilization for diverse process sizes.
  3. Increase flexibility in multiprogramming.

Internal working mechanism:
  1. OS starts with one large free hole.
  2. For each request S, OS finds hole of size >= S.
  3. Allocates exactly S (or with tiny alignment overhead).
  4. Leaves residual as smaller hole.
  5. On process termination, hole is created and adjacent holes may merge.

Dynamic view example:

Step 1: Initial
  +------------------------------------------------+
  |                    Free 1024 MB                |
  +------------------------------------------------+

Step 2: P1=200, P2=300, P3=100
  +------------------------------------------------+
  | P1 200 | P2 300 | P3 100 |      Free 424       |
  +------------------------------------------------+

Step 3: P2 exits
  +------------------------------------------------+
  | P1 200 | Hole 300 | P3 100 |    Free 424       |
  +------------------------------------------------+

Now a request of 500 MB cannot use hole 300, although total free = 724 MB.
This is external fragmentation.

OS implementation perspective:
  - Kernel maintains free-space data structure (linked list/tree/segregated
    lists) and applies a placement policy.
  - Coalescing and compaction policies determine long-term efficiency.

Real-life analogy:
  Warehouse floor where boxes of exact requested sizes are placed dynamically.
  Over time, odd gaps appear between boxes; large incoming boxes cannot fit
  despite total empty area being enough.

Advantages:
  1. Better fit for varying process sizes.
  2. Lower internal fragmentation than fixed partitions.
  3. Higher practical utilization initially.

Disadvantages:
  1. External fragmentation accumulates over time.
  2. Allocation search overhead can grow.
  3. May require expensive compaction.

    Micro-topic: Hole List Representation
    ─────────────────────────────────────
    Typical hole metadata:
      - Start address
      - Size
      - Free/allocated status
      - Next/previous pointer (if linked list)

    Allocation quality is tightly coupled to how efficiently this structure is
    searched and updated.

        Deeper: Why External Fragmentation Is Hard
        ──────────────────────────────────────────
        Fragmentation is not just "unused space"; it is "unusable shape" of
        free space. Even with high total free memory, large contiguous requests
        can fail due to geometric scattering of holes.


    Key Points
    ──────────
    • Variable partitioning reduces internal but introduces external
      fragmentation.
    • Free-space management policy strongly affects performance.
    • Long-running systems need coalescing/compaction strategies.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. Define variable partitioning.
      2. What is external fragmentation?

    Long Questions (8–10 marks)
      1. Explain variable partitioning with suitable memory map.
      2. Compare fixed and variable partitioning with pros/cons.

    Numerical Problems
      1. Track hole sizes after sequence of allocations and deallocations.
      2. Test whether a request can be satisfied contiguously.

2.3  PLACEMENT ALGORITHMS: FIRST FIT, BEST FIT, WORST FIT, NEXT FIT
--------------------------------------------------------------------------------

Definition:
  Placement algorithms decide which free hole should be used when allocating
  memory in variable partitioning systems.

Why placement policies exist:
  Multiple holes may satisfy one request. Choice affects:
  1. Allocation speed
  2. Future fragmentation pattern
  3. Overall throughput

Initial hole list for solved demonstration:

  H1=100 KB, H2=500 KB, H3=200 KB, H4=300 KB, H5=600 KB
  Process requests in order: P1=212 KB, P2=417 KB, P3=112 KB, P4=426 KB

Algorithm behavior summary:

Algorithm      Selection Rule
---------------------------------------------------------------
First Fit      First hole (from start) that is large enough
Best Fit       Smallest hole that is large enough
Worst Fit      Largest available hole
Next Fit       Like First Fit, but continue from last position

Solved allocation outcomes (exam style)

First Fit:

Step   Request   Chosen Hole      Result
---------------------------------------------------------------
1      212       H2=500           H2 becomes 288
2      417       H5=600           H5 becomes 183
3      112       H2=288           H2 becomes 176
4      426       No hole fits     Allocation fails

Best Fit:

Step   Request   Chosen Hole      Result
---------------------------------------------------------------
1      212       H4=300           H4 becomes 88
2      417       H2=500           H2 becomes 83
3      112       H3=200           H3 becomes 88
4      426       H5=600           H5 becomes 174

Worst Fit:

Step   Request   Chosen Hole      Result
---------------------------------------------------------------
1      212       H5=600           H5 becomes 388
2      417       H2=500           H2 becomes 83
3      112       H5=388           H5 becomes 276
4      426       No hole fits     Allocation fails

Next Fit (starting search at H1):

Step   Request   Search Start   Chosen Hole      Result
---------------------------------------------------------------
1      212       H1             H2=500           H2 becomes 288
2      417       after H2       H5=600           H5 becomes 183
3      112       after H5       H1=100 no, H2=288 yes   H2 becomes 176
4      426       after H2       no suitable hole         Allocation fails

Interpretation:
  - Best Fit succeeded for all four requests in this case.
  - First/Next/Worst failed at request P4 for this sequence.
  - No algorithm is universally best for all workloads.

Operating system implementation:
  - Practical allocators use segregated classes, buddy/slab hybrids, or
    approximate strategies instead of pure textbook first/best/worst scans.
  - Time complexity and cache behavior of metadata structures are critical.

Real-life analogy:
  Choosing parking spaces for vehicles:
  - First Fit: pick first available spot that fits.
  - Best Fit: choose tightest fit spot.
  - Worst Fit: choose biggest open spot.
  - Next Fit: resume search from last parked position.

Advantages and disadvantages table:

Algorithm      Advantages                              Disadvantages
-------------------------------------------------------------------------------
First Fit      Fast in practice                        Can leave small holes early
Best Fit       Minimizes immediate leftover            Creates many tiny fragments
Worst Fit      Leaves larger residual chunks           Often poor global behavior
Next Fit       Reduces restart-at-head overhead        Placement quality can degrade

    Micro-topic: Why "Best" Fit Is Not Always Best
    ───────────────────────────────────────────────
    Best Fit optimizes immediate local waste, not long-term global structure.
    It can create many tiny unusable holes, increasing external fragmentation.

        Deeper: Policy vs Mechanism
        ───────────────────────────
        Mechanism = ability to allocate/deallocate memory blocks.
        Policy = strategy deciding which block to choose.
        Good OS design separates both so policy can evolve without redesigning
        the entire allocator mechanism.


    Key Points
    ──────────
    • Placement policy affects both performance and fragmentation.
    • Exam numericals require strict stepwise table tracking.
    • No single policy is optimal for all request patterns.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. Define First Fit and Next Fit.
      2. Why can Best Fit cause many tiny holes?

    Long Questions (8–10 marks)
      1. Compare First, Best, Worst, and Next Fit.
      2. Discuss policy trade-offs with practical examples.

    Numerical Problems
      1. Solve allocation sequence under all four algorithms.
      2. Count failed allocations and remaining hole distribution.

2.4  FRAGMENTATION & SOLUTIONS: COALESCING AND COMPACTION
--------------------------------------------------------------------------------

Definition:
  Fragmentation is inefficient memory utilization caused by mismatch between
  requested allocation shape and available memory layout.

Types:
  1. Internal Fragmentation:
     Wasted space inside an allocated block.

  2. External Fragmentation:
     Free memory split into scattered holes between allocated blocks.

Why fragmentation is inevitable in contiguous schemes:
  Dynamic process arrivals/exits produce irregular memory maps over time.

Formula view:

  Internal waste for one allocation:
      Waste_internal = Allocated_Size - Requested_Size

  External feasibility check:
      Request fails when Max_Contiguous_Hole < Requested_Size
      even if Total_Free_Memory >= Requested_Size

Solved mini numerical:

Given hole sizes: 120 KB, 80 KB, 200 KB, 60 KB
Request = 250 KB

Total free = 460 KB (enough in total)
Largest hole = 200 KB (not enough contiguously)

Result: Allocation fails due to external fragmentation.

Solution 1: Coalescing
  Definition:
    Merge adjacent free holes into one larger hole.

  Mechanism:
    1. Process terminates; block marked free.
    2. Check left and right neighbors.
    3. If neighbor is free, merge metadata and sizes.

  ASCII example:

    Before free(P2):
      +-------------------------------+
      | P1 |  H1  | P2 |  H2  |  P3   |
      +-------------------------------+

    After free(P2) and coalescing:
      +-------------------------------+
      | P1 |       H(merged)    | P3  |
      +-------------------------------+

Solution 2: Compaction
  Definition:
    Relocate processes so all free holes combine into one large contiguous
    region.

  Mechanism:
    1. Temporarily pause/move processes.
    2. Shift allocated blocks toward one end.
    3. Create single large free block.
    4. Update relocation/address mappings.

  ASCII concept:

    Before compaction:
      | P1 | Hole | P2 | Hole | P3 | Hole |

    After compaction:
      | P1 | P2 | P3 |        One Large Hole        |

Why compaction is costly:
  - Requires copying large memory regions.
  - Needs relocation support and synchronization.
  - Can temporarily reduce CPU throughput.

Operating system implementation:
  - Coalescing is common and relatively cheap.
  - Full compaction is rare in modern paging systems because paging avoids the
    need for strict contiguous process allocation.

Real-life analogy:
  Bookshelf maintenance:
  - Coalescing: join neighboring empty gaps.
  - Compaction: shift all books left to create one big empty space right side.

Advantages and disadvantages:

Coalescing
  Advantages:
    1. Low overhead.
    2. Helps progressively reduce external fragmentation.
  Disadvantages:
    1. Only works when holes are adjacent.

Compaction
  Advantages:
    1. Can recover a large contiguous free block.
  Disadvantages:
    1. Expensive runtime overhead.
    2. Requires relocation support.

    Micro-topic: Why Paging Reduced Fragmentation Crisis
    ─────────────────────────────────────────────────────
    Paging allows non-contiguous physical placement of process pages, so large
    contiguous free regions are no longer mandatory for process execution.

        Deeper: Fragmentation in Modern Systems
        ───────────────────────────────────────
        Paging removes classic external fragmentation at process-allocation
        level, but systems can still face fragmentation-like issues in kernel
        allocators, huge pages, and storage layers.


    Key Points
    ──────────
    • Internal and external fragmentation are distinct failure modes.
    • Coalescing is local repair; compaction is global repair.
    • Compaction is powerful but expensive.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. Differentiate internal and external fragmentation.
      2. What is coalescing?

    Long Questions (8–10 marks)
      1. Explain compaction with diagram and limitations.
      2. Discuss why contiguous allocation suffers fragmentation inherently.

    Numerical Problems
      1. Identify fragmentation type from memory map.
      2. Check allocation feasibility using total free vs largest hole.

3.0  PAGING (THE MODERN STANDARD: THE "FIXED SLICES")
================================================================================

Paging is the dominant memory-management model in modern operating systems.
Instead of requiring one process-sized contiguous chunk, paging divides memory
into equal-size units and maps them flexibly.

Why paging became the standard:
  1. It eliminates classic external fragmentation in process allocation.
  2. It supports virtual memory naturally.
  3. It allows independent placement of process pieces in RAM.

Conceptual shift from contiguous allocation:
  - Old model: one large block per process.
  - Paging model: many fixed-size blocks per process.

Real-life analogy:
  Parcel shipping with standardized boxes.
  If every item must use one huge custom box, packing is hard.
  With standard cartons, pieces can be distributed efficiently.

OS implementation note:
  Paging is implemented by cooperation among CPU MMU, per-process page tables,
  TLB, and kernel page-fault handlers.


--------------------------------------------------------------------------------
3.1  BASIC CONCEPTS: PAGES (LOGICAL) AND FRAMES (PHYSICAL)
--------------------------------------------------------------------------------

Definition:
  Page:
    Fixed-size block of a process's logical (virtual) address space.

  Frame:
    Fixed-size block of physical memory (RAM).

Core rule:
  Page size = Frame size

Why this concept exists:
  1. Enables non-contiguous physical placement with simple arithmetic.
  2. Simplifies allocation by fixed unit size.
  3. Supports demand paging and page replacement.

Internal working mechanism (step by step):
  1. OS splits virtual address space into pages (e.g., 4 KB each).
  2. RAM is viewed as an array of equal-sized frames.
  3. Any virtual page can be loaded into any free frame.
  4. Page table records mapping: page number -> frame number.

Address breakdown:
  Virtual Address = (Page Number, Offset)
  Physical Address = (Frame Number, Offset)

If page size is $2^n$ bytes:
  - Lower n bits = offset
  - Upper bits = page number

ASCII diagram:

      Virtual Address Space (Process)
      +------+------+------+------+------+
      | Pg0  | Pg1  | Pg2  | Pg3  | Pg4  |
      +------+------+------+------+------+

                     mapped to

      Physical Memory (Frames)
      +------+------+------+------+------+
      | Fr5  | Fr1  | Fr9  | Fr2  | Fr7  |
      +------+------+------+------+------+

Note: Pages do not need neighboring frames.

Numerical example:

Given:
  - Virtual address size = 16 bits
  - Page size = 1 KB = $2^{10}$ bytes

Then:
  - Offset bits = 10
  - Page number bits = 6
  - Total pages per process space = $2^6 = 64$

Operating system implementation:
  - Kernel maintains free-frame list or bitmap.
  - Frame allocator gives frames to processes on page demand.
  - Zero-fill-on-demand prevents data leakage between processes.

Real-life analogy:
  Library books split into numbered pages.
  Physical shelves can store these pages in any order as long as index mapping
  exists. Reader still sees correct logical order using catalog.

Advantages:
  1. Removes need for large contiguous free region.
  2. Supports multiprogramming effectively.
  3. Works naturally with virtual memory and sharing.

Disadvantages:
  1. Requires translation metadata (page tables).
  2. Can cause internal fragmentation at last page of process region.
  3. Translation overhead must be managed with TLB.

    Micro-topic: Internal Fragmentation in Paging
    ─────────────────────────────────────────────
    Paging removes external fragmentation at process-placement level, but final
    page of each segment/region may be partially unused.

    Example:
      Process needs 10,100 bytes with 4,096-byte pages.
      Pages required = 3 (12,288 bytes allocated).
      Internal waste = 12,288 - 10,100 = 2,188 bytes.

        Deeper: Page Size Trade-off
        ───────────────────────────
        Small page size:
          + less internal waste
          - larger page tables, more TLB pressure

        Large page size:
          + smaller tables, improved sequential I/O behavior
          - more internal waste, larger transfer on fault


    Key Points
    ──────────
    • Paging splits virtual memory into pages and RAM into frames.
    • Page and frame sizes are equal by design.
    • Mapping flexibility removes classical contiguous-allocation problems.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. Define page and frame.
      2. Why must page size equal frame size?

    Long Questions (8–10 marks)
      1. Explain paging basics with diagram and address-bit split.
      2. Discuss page-size trade-offs in practical systems.

    Numerical Problems
      1. Given address width and page size, find page number/offset bits.
      2. Compute internal fragmentation in final page.

3.2  ADDRESS TRANSLATION: HOW THE PAGE TABLE WORKS
--------------------------------------------------------------------------------

Definition:
  A page table is a per-process data structure that maps virtual page numbers
  to physical frame numbers and stores status/protection bits.

Why page table exists:
  1. Decouples program-visible addresses from physical RAM layout.
  2. Enables protection and isolation.
  3. Supports demand paging and sharing.

Internal working mechanism:
  1. CPU generates virtual address VA.
  2. MMU extracts VPN and offset.
  3. MMU uses VPN to index page table.
  4. If entry valid/present, obtain PFN.
  5. Compose physical address: (PFN, offset).
  6. If invalid/not present, trigger page fault.

ASCII path:

      Virtual Address (VPN | Offset)
                    │
                    ▼
              +-----------+
              |   MMU     |
              +-----------+
                    │ index by VPN
                    ▼
              +-----------+
              | PageTable |
              +-----------+
                    │ gives PFN
                    ▼
      Physical Address (PFN | Offset)

Typical page table entry (PTE) fields:
  - Frame Number (PFN)
  - Present/Valid bit
  - Read/Write bit
  - User/Supervisor bit
  - Accessed (Reference) bit
  - Dirty (Modified) bit
  - Execute disable (NX) bit

Mini numerical translation:

Given:
  - Page size = 1 KB
  - VA = 3480
  - Page table: VPN 3 -> PFN 12

Step 1:
  VPN = floor(3480 / 1024) = 3
  Offset = 3480 mod 1024 = 408

Step 2:
  PFN = 12

Step 3:
  Physical Address = 12*1024 + 408 = 12,696

Operating system implementation:
  - On context switch, OS updates page-table base register to new process map.
  - Kernel updates PTE bits during page faults, protection events, and swapping.
  - Copy-on-Write uses read-only shared mappings until write occurs.

Real-life analogy:
  City map lookup:
  - Virtual page number = district code.
  - Page table = official mapping directory.
  - Physical frame = actual land block.

Advantages:
  1. Strong process isolation.
  2. Flexible mapping and sharing.
  3. Fine-grained protection.

Disadvantages:
  1. Memory overhead for tables.
  2. Additional memory references without TLB.
  3. Complexity for very large address spaces.

    Micro-topic: Single-Level Table Memory Cost
    ────────────────────────────────────────────
    Example (32-bit VA, 4 KB pages, 4-byte PTE):
      Number of pages per process = $2^{32}/2^{12} = 2^{20}$
      Page table size = $2^{20} * 4$ bytes = 4 MB per process.

    This motivates multi-level and alternative page table structures.

        Deeper: Protection Enforcement in Hardware
        ──────────────────────────────────────────
        The MMU checks permission bits before memory access completes. Illegal
        accesses trap immediately, giving the kernel control and preserving
        system integrity.


    Key Points
    ──────────
    • Page table maps VPN to PFN and stores control bits.
    • Translation also performs access validation.
    • Table size can become large for big virtual spaces.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. What is stored in a page table entry?
      2. What happens when Present bit is 0?

    Long Questions (8–10 marks)
      1. Explain page-table-based address translation with neat diagram.
      2. Discuss PTE fields and their role in protection.

    Numerical Problems
      1. Perform virtual-to-physical translation with given table.
      2. Compute page table memory overhead for given architecture.


--------------------------------------------------------------------------------
3.3  SPEEDING UP PAGING: TLB (TRANSLATION LOOKASIDE BUFFER)
--------------------------------------------------------------------------------

Definition:
  TLB is a small, fast associative cache inside/near MMU that stores recent
  virtual-page to physical-frame translations.

Why TLB exists:
  Without TLB, each memory access may require extra page-table memory access,
  significantly increasing effective memory latency.

Internal working mechanism:
  1. CPU issues VA.
  2. MMU searches TLB for VPN.
  3. If TLB hit, PFN is obtained immediately.
  4. If TLB miss, page table walk is performed.
  5. Found mapping inserted into TLB.
  6. If page absent, page fault handling occurs.

ASCII pipeline:

      VA
      │
      ▼
  +--------+
  |  TLB   |
  +--------+
   │    │
 hit    miss
   │    │
   ▼    ▼
   PFN  Page Table Walk
    │      │
    +--+---+
       ▼
   Physical Address

Effective Access Time (EAT) model:

Let:
  - $h$ = TLB hit ratio
  - $\epsilon$ = TLB lookup time
  - $m$ = memory access time

Then (single-level page table assumption):

      EAT = h(ε + m) + (1-h)(ε + 2m)

Solved numerical:

Given:
  $h = 0.95$, $\epsilon = 10$ ns, $m = 100$ ns

Compute:
  Hit path = 10 + 100 = 110 ns
  Miss path = 10 + 200 = 210 ns

  EAT = 0.95(110) + 0.05(210)
      = 104.5 + 10.5
      = 115 ns

Interpretation:
  A high hit ratio keeps EAT close to RAM access time.

Operating system implementation:
  - Context switch may require TLB flush or ASID-based tagging.
  - Kernel updates invalidate stale entries after mapping changes.
  - Huge pages can increase TLB reach (more memory covered per entry).

Real-life analogy:
  Reception desk shortcut list:
  Frequently requested room mappings are kept on a quick-reference card;
  uncommon requests require searching full registry.

Advantages:
  1. Major reduction in average translation overhead.
  2. Essential for high-performance virtual memory systems.

Disadvantages:
  1. Misses still expensive.
  2. Adds hardware complexity and replacement policy challenges.

    Micro-topic: TLB Reach
    ──────────────────────
    TLB reach = (Number of TLB entries) × (Page size)

    Larger reach means larger working set can be translated without misses.

        Deeper: ASID and Shootdown
        ──────────────────────────
        ASID (Address Space Identifier) tags TLB entries per process to reduce
        full flushes on context switch. In multiprocessors, when mappings
        change, kernels perform TLB shootdown to invalidate stale remote-core
        entries safely.


    Key Points
    ──────────
    • TLB is a translation cache, not a data cache.
    • EAT strongly depends on hit ratio.
    • OS and CPU coordinate to maintain TLB correctness.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. What is TLB and why is it needed?
      2. Define TLB hit and TLB miss.

    Long Questions (8–10 marks)
      1. Derive and explain EAT with TLB.
      2. Discuss TLB maintenance during context switch.

    Numerical Problems
      1. Compute EAT for given $h$, $\epsilon$, and $m$.
      2. Evaluate performance change when hit ratio drops.

3.4  PAGE TABLE STRUCTURES: HIERARCHICAL, HASHED, AND INVERTED
--------------------------------------------------------------------------------

As virtual address spaces grew (32-bit to 64-bit), flat single-level page
tables became memory-expensive. OSes use structured designs to reduce overhead.

3.4.1  Hierarchical (Multi-level) Page Tables
──────────────────────────────────────────────

Definition:
  Multi-level paging splits page table into levels. Upper-level entries point
  to lower-level tables, created only when needed.

Why it exists:
  1. Saves memory for sparse address spaces.
  2. Avoids allocating huge contiguous page table blocks.

Working mechanism:
  1. Virtual address is divided into multiple indices + offset.
  2. First index selects top-level entry.
  3. Next index selects second-level entry, and so on.
  4. Final level gives PFN.

ASCII view:

  VA -> [L1 idx][L2 idx][L3 idx][Offset]
            │
            ▼
        L1 Table
            │
            ▼
        L2 Table
            │
            ▼
        L3 Table -> PFN

Advantages:
  - Excellent for sparse virtual spaces.
  - Practical and widely deployed (x86-64, ARM).

Disadvantages:
  - More levels increase miss-path walk cost.


3.4.2  Hashed Page Tables
─────────────────────────

Definition:
  VPNs are hashed into buckets containing mapping chains/entries.

Why it exists:
  Useful for very large and sparse address spaces where direct indexing is
  costly.

Working mechanism:
  1. Compute hash(VPN).
  2. Follow bucket chain to find matching VPN and process context.
  3. Return PFN if found.

Advantages:
  - Memory-efficient for sparse mappings.

Disadvantages:
  - Collision handling adds lookup variability.


3.4.3  Inverted Page Tables
───────────────────────────

Definition:
  One global table entry per physical frame (not per virtual page per process).

Why it exists:
  Greatly reduces table size in systems with huge virtual address spaces.

Working mechanism:
  1. Entry stores (PID, VPN) currently mapped into that frame.
  2. Lookup uses hashing/search to locate matching (PID, VPN).
  3. Found entry provides frame index directly.

Table comparison:

Structure            Key Idea                          Main Trade-off
-------------------------------------------------------------------------------
Hierarchical         Allocate lower levels on demand   More walk steps
Hashed               Hash VPN to mapping bucket         Collision overhead
Inverted             One entry per physical frame       Complex lookup logic

Operating system implementation:
  - Modern Linux on x86-64 uses multi-level paging.
  - Different architectures adopt variants optimized for hardware MMU design.
  - Kernel must maintain consistency during map/unmap, fork, and page reclaim.

Real-life analogy:
  Directory systems:
  - Hierarchical: country -> state -> city -> house.
  - Hashed: quick lookup by hashed identifier bucket.
  - Inverted: one record per existing house, showing who occupies it.

Advantages and disadvantages (overall):
  Advantages:
    1. Scalable memory mapping for large modern address spaces.
    2. Better metadata efficiency than flat tables in sparse cases.

  Disadvantages:
    1. Greater implementation complexity.
    2. Non-trivial lookup paths on misses.

    Micro-topic: Shared Pages and Multi-level Tables
    ────────────────────────────────────────────────
    Shared libraries can map same physical frames into many processes while
    each process keeps its own virtual mapping entries. This boosts memory
    efficiency without breaking isolation semantics.

        Deeper: Why 64-bit Needed Structured Tables
        ───────────────────────────────────────────
        A naive flat table for full 64-bit virtual space is impractical. Multi-
        level sparse allocation is essential for real systems where only a tiny
        fraction of virtual space is actively mapped.


    Key Points
    ──────────
    • Single-level tables are simple but can be memory-heavy.
    • Multi-level, hashed, and inverted designs target scalability.
    • Structure choice balances memory overhead and lookup complexity.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. Why are hierarchical page tables needed?
      2. Define inverted page table.

    Long Questions (8–10 marks)
      1. Compare hierarchical, hashed, and inverted page tables.
      2. Explain multi-level address translation process.

    Numerical Problems
      1. Compute table size for flat vs multi-level assumptions.
      2. Determine bit split across levels for given architecture.

4.0  SEGMENTATION (THE "LOGICAL SLICES")
================================================================================

Segmentation is a memory-management scheme that divides a process address space
by logical meaning (for example code, data, stack, heap) rather than by fixed
size blocks. It reflects how programmers naturally think about programs.

Why this model exists:
  1. Programs are logically organized into distinct functional regions.
  2. Different regions need different permissions and growth behavior.
  3. Logical separation improves protection and modularity.

Core conceptual contrast:
  Paging:
    Divides memory into equal-size units for allocation convenience.

  Segmentation:
    Divides memory into variable-size logical units for semantic clarity.

OS relevance today:
  Even though pure segmentation is uncommon in modern 64-bit systems, the
  concepts of region-based protection and logical memory organization remain
  central in executable layout, stack growth, and process memory maps.

Real-life analogy:
  A university campus layout:
  - Academic block (code)
  - Administration block (data)
  - Hostel block (stack-like dynamic usage)
  - Playground / future expansion (heap)

Each area has different purpose and access policies.


--------------------------------------------------------------------------------
4.1  SEGMENTED ADDRESSING: CODE, DATA, STACK DIVISION
--------------------------------------------------------------------------------

Definition:
  Segmented addressing uses a logical address of the form:

      <Segment Number, Offset>

where each segment represents a logical program unit with independent base,
limit, and protection attributes.

Why segmented addressing exists:
  1. Matches programmer mental model (functions, globals, stack frames).
  2. Allows per-segment protection (e.g., code read/execute, data read/write).
  3. Allows independent segment growth (especially stack and heap).

Internal working mechanism (step by step):
  1. CPU generates logical address (s, d), where s=segment id, d=offset.
  2. MMU indexes segment table using s.
  3. Fetch segment descriptor containing Base, Limit, and permission bits.
  4. Check offset validity: if d >= Limit, trap.
  5. Check access rights (read/write/execute).
  6. Physical address = Base + d.

Mathematical rule:

      If d < Limit_s, then PA = Base_s + d
      Else trap (segmentation fault)

ASCII translation diagram:

      Logical Address (s, d)
               │
               ▼
      +-------------------+
      |   Segment Table   |  <- indexed by s
      +-------------------+
               │
               ▼
      Descriptor: Base, Limit, Perm
               │
     check d < Limit and permission
               │
               ▼
         Physical Address

Segment table example:

Seg No.   Base      Limit     Perm       Meaning
---------------------------------------------------------------------
0         4000      1200      R-X        Code/Text
1         9000      2000      RW-        Data/BSS
2        15000      3000      RW-        Heap
3        25000      1500      RW-        Stack

Numerical example:

Given logical reference (s=1, d=1500):
  Segment 1 has Base=9000, Limit=2000
  Since 1500 < 2000, valid
  PA = 9000 + 1500 = 10500

Given logical reference (s=0, d=1300):
  Segment 0 Limit=1200
  Since 1300 >= 1200, invalid -> trap

Operating system implementation:
  - OS loader creates segment descriptors for each process image region.
  - Protection can be enforced per region (text non-writable, stack non-exec,
    etc.).
  - Segment table pointer is switched on context switch (in segmented systems).

Real-life analogy:
  Office file cabinets:
  - Cabinet label = segment number
  - Drawer position = offset
  - Security pass determines who can read/write a cabinet

Advantages:
  1. Natural program-structure representation.
  2. Fine-grained region-based protection.
  3. Supports sharing of specific segments (for example shared code).

Disadvantages:
  1. Variable-sized segments cause external fragmentation in physical memory.
  2. Allocation complexity grows with long-running workloads.
  3. Compaction/relocation overhead may be required.

    Micro-topic: Sharing Code Segment Across Processes
    ──────────────────────────────────────────────────
    Common executable code can be mapped as read-only shared segment across
    many processes, reducing memory usage while preserving safety.

    Example:
      Multiple shell instances can share the same text segment of binary code.

        Deeper: Why Segmentation Helps Protection Reasoning
        ───────────────────────────────────────────────────
        Segment boundaries create explicit security domains. It is easier to
        enforce "code must not be writable" and "stack must not be executable"
        when regions are logically named and independently permissioned.


    Key Points
    ──────────
    • Segmentation uses logical units, not fixed-size blocks.
    • Address form is (segment, offset).
    • Bound and permission checks happen before physical access.

4.2  SEGMENTATION WITH PAGING: MODERN X86 COMBINATION
--------------------------------------------------------------------------------

Definition:
  Segmentation with paging is a hybrid model in which a logical segmented
  address is first converted to a linear address, and then paging converts the
  linear address to physical address.

Why this hybrid exists:
  1. Segmentation provides logical/protection structure.
  2. Paging provides efficient physical-memory management and virtual memory.
  3. Combination balances semantic clarity and allocation scalability.

Classical x86 conceptual flow:
  1. CPU instruction references selector:offset.
  2. Selector indexes descriptor table (GDT/LDT).
  3. Descriptor yields segment base, limit, privilege.
  4. Linear address = segment base + offset (after checks).
  5. Paging translates linear address via page tables to physical address.

ASCII pipeline:

      Logical Addr (Selector:Offset)
                   │
                   ▼
            +---------------+
            | Segmentation  |
            |  (GDT/LDT)    |
            +---------------+
                   │  -> Linear Address
                   ▼
            +---------------+
            |    Paging     |
            |  (PageTable)  |
            +---------------+
                   │
                   ▼
            Physical Address

Why modern 64-bit OSes appear "paging-dominant":
  - In x86-64 long mode, most segmentation bases are effectively flattened
    (base treated as 0 for common code/data segments).
  - Paging remains the primary mechanism for translation and protection.
  - Certain segmentation constructs remain for compatibility and privilege
    transitions, but not as general-purpose memory partitioning for user code.

Operating system implementation perspective:
  - Kernel configures descriptor tables during boot and per-CPU setup.
  - User-space memory protection and isolation are mainly enforced by paging
    PTE bits and privilege levels.
  - Thread-local storage on some architectures historically uses segment-based
    facilities or analogous mechanisms.

Real-life analogy:
  Two-stage postal routing:
  1. City-level sorting center chooses district route (segmentation stage).
  2. District center chooses exact street-house path (paging stage).

Comparison table: Pure Segmentation vs Segmentation+Paging

Aspect                    Pure Segmentation               Hybrid with Paging
-------------------------------------------------------------------------------
Unit of allocation        Variable segments               Fixed pages in segments
External fragmentation    Significant                     Greatly reduced
Logical grouping          Strong                          Strong
Physical flexibility      Moderate                        High
Modern usage              Limited                         Common conceptual model

Numerical conceptual example:

Given:
  Segment Base = 400000
  Offset = 8192
  Linear Address = 408192

If page size = 4096:
  VPN = 408192 / 4096 = 99
  Offset within page = 408192 mod 4096 = 2688

If page table maps VPN 99 -> PFN 550:
  Physical Address = 550*4096 + 2688 = 2,255,488

Advantages:
  1. Retains logical protection abstractions.
  2. Uses paging benefits for efficient memory placement.
  3. Scales better than pure segmentation.

Disadvantages:
  1. Two-stage translation complexity.
  2. Additional hardware/software coordination.
  3. Debugging address interpretation can be conceptually harder.

    Micro-topic: Privilege and Descriptor Checks
    ─────────────────────────────────────────────
    In segmented architectures, descriptors include privilege constraints. CPU
    checks these before allowing access, enforcing user-vs-kernel boundaries.

        Deeper: Why This Topic Still Matters in Exams
        ──────────────────────────────────────────────
        Many curricula retain segmentation+paging because it teaches layered
        translation design and architecture evolution from older systems to
        current paging-centric models.


    Key Points
    ──────────
    • Hybrid flow: logical -> linear (segment) -> physical (paging).
    • Modern x86-64 uses mostly flat segmentation + full paging.
    • Concept is important for understanding architecture history and design.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. What is linear address in x86 translation?
      2. Why is paging dominant in modern 64-bit OS?

    Long Questions (8–10 marks)
      1. Explain segmentation with paging using neat block diagram.
      2. Compare pure segmentation and hybrid approach.

    Numerical Problems

5.0  VIRTUAL MEMORY (THE "MAGIC TRICK")
================================================================================

Virtual memory is the operating system technique that gives each process the
illusion of a large, private, contiguous address space, even when physical RAM
is limited and shared among many processes.

Why this concept is called a "magic trick":
  - Programs believe they own a huge memory space.
  - Only actively needed parts are kept in RAM.
  - Inactive parts stay on secondary storage until required.

Why virtual memory exists:
  1. Physical RAM is finite and expensive.
  2. Multiprogramming requires isolation and sharing simultaneously.
  3. Modern software needs memory footprints larger than available RAM.

Internal big-picture mechanism:
  1. CPU generates virtual addresses.
  2. MMU + page tables translate to physical frames.
  3. If page not resident, page fault occurs.
  4. Kernel fetches page from backing store and resumes process.

ASCII conceptual flow:

      Process Virtual Space
      +----------------------------------------------+
      | Pg0 | Pg1 | Pg2 | Pg3 | ... | PgN           |
      +----------------------------------------------+
           │ mapped partially
           ▼
      +---------------------+
      |      Physical RAM   |
      +---------------------+
           │ missing pages
           ▼
      +---------------------+
      |  Disk / Swap Area   |
      +---------------------+

Operating system implementation note:
  Virtual memory is implemented through the combined work of page-fault
  handlers, frame allocator, replacement policy, swap subsystem, and TLB
  management logic.

Real-life analogy:
  A student keeps only currently needed books on desk (RAM), while the rest
  remain in a nearby bookshelf/store room (disk). When a new chapter is needed,
  the student brings that specific book to desk.


--------------------------------------------------------------------------------
5.1  DEMAND PAGING: LOAD ONLY WHEN REQUESTED
--------------------------------------------------------------------------------

Definition:
  Demand paging is a virtual memory strategy where pages are loaded into RAM
  only when the CPU actually references them.

Why demand paging exists:
  1. Avoids loading entire process image upfront.
  2. Reduces startup latency and RAM pressure.
  3. Exploits locality: many pages are never touched.

Internal working mechanism (step by step):
  1. Process starts with some pages marked not-present.
  2. CPU references a page with Present bit = 0.
  3. MMU raises page-fault trap.
  4. OS validates access and locates page on disk/executable/swap.
  5. OS allocates free frame (or replaces victim if none free).
  6. Page is read into frame.
  7. Page table/TLB updated; instruction restarted.

ASCII sequence:

      CPU Reference
          │
          ▼
      Present bit = 0 ? ---- No ----> Continue
          │
         Yes
          │
          ▼
      Page Fault Trap
          │
          ▼
      OS loads page from disk
          │
          ▼
      Update mapping + restart instruction

Important demand-paging terms:
  - Lazy loading: postpone load until first access.
  - Page-in: bringing page from disk to RAM.
  - Page-out: writing victim page to disk when needed.

Performance model:

Let:
  - $p$ = page fault probability
  - $m$ = memory access time
  - $f$ = average page fault service time

Then:

      EAT = (1-p)m + p(f)

Since $f \gg m$, even small $p$ can significantly hurt performance.

Solved numerical:

Given:
  $m = 100$ ns
  $f = 8$ ms = 8,000,000 ns
  $p = 0.0005$

EAT:
  = (1-0.0005)(100) + 0.0005(8,000,000)
  = 99.95 + 4,000
  = 4,099.95 ns

Interpretation:
  Very low fault rate still increases effective time ~41x over pure memory hit.

Operating system implementation:
  - Executable pages may be demand-loaded from binary file.
  - Anonymous memory (heap/stack) may be zero-filled on first use.
  - Swap daemon/page reclaim subsystem maintains free-frame availability.

Real-life analogy:
  Online video buffering: only watched segment is fetched now; future parts are
  loaded on demand, not all at once.

Advantages:
  1. Lower initial memory and I/O cost.
  2. Better RAM utilization.
  3. Enables larger logical processes than RAM size.

Disadvantages:
  1. First-touch latency due to faults.
  2. Excessive faults degrade throughput.
  3. Requires sophisticated kernel policies.

    Micro-topic: Pure Demand Paging vs Pre-paging
    ─────────────────────────────────────────────
    Pure demand paging loads exactly on first access.
    Pre-paging predicts near-future pages and loads ahead to reduce faults.

    Trade-off:
      Pre-paging can reduce fault bursts but may waste I/O if prediction wrong.

        Deeper: Locality and Working Set Entry
        ──────────────────────────────────────
        Demand paging performs well when active working set fits in RAM. If
        working set exceeds available frames, page-fault frequency increases
        rapidly and leads to thrashing (Section 5.3).


    Key Points
    ──────────
    • Demand paging loads pages at first use.
    • Page fault handling is central to virtual memory.
    • Tiny page-fault probabilities can dominate EAT.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. Define demand paging.
      2. Why is demand paging called lazy loading?

    Long Questions (8–10 marks)
      1. Explain demand paging workflow with neat diagram.
      2. Discuss performance impact of page fault rate.

    Numerical Problems
      1. Compute EAT using given $p$, $m$, and $f$.
      2. Compare EAT before and after reducing page-fault probability.

5.2  PAGE FAULTS: WHAT HAPPENS WHEN PAGE IS NOT IN RAM
--------------------------------------------------------------------------------

Definition:
  A page fault is a hardware trap raised when a process references a virtual
  page whose page table entry is not currently marked present in physical RAM
  (or violates protection constraints).

Types of page faults (teaching perspective):
  1. Minor (soft) fault:
     Page is not mapped in current process context but can be resolved without
     expensive disk I/O in some cases.

  2. Major (hard) fault:
     Page must be fetched from disk/swap; high latency event.

  3. Invalid access fault:
     Address/protection violation; process may receive fault signal/termination.

Why fault handling exists:
  Faults are the control handoff from hardware to OS so the kernel can enforce
  correctness, protection, and lazy loading.

Detailed page-fault handling steps:
  1. Hardware trap to kernel mode, saving process state.
  2. Validate address and permission against VMA/page metadata.
  3. If invalid, generate protection exception and handle accordingly.
  4. Locate required page source (file-backed, swap-backed, or zero page).
  5. Obtain frame:
       a) Use free list if available, or
       b) Select victim via replacement policy.
  6. If victim dirty, write back to disk/swap.
  7. Read demanded page into selected frame.
  8. Update page table entry, set present/protection bits.
  9. Invalidate/update relevant TLB entries.
 10. Restart interrupted instruction.

ASCII fault-service path:

      CPU Access
         │
         ▼
      PTE Present=0 ?
         │
        Yes
         │
         ▼
      Trap to Kernel
         │
         ▼
   Validate -> Fetch -> Map -> Resume

Time components of major page fault:
  1. Trap and context save overhead
  2. Replacement decision time
  3. Disk queue + seek/transfer + completion interrupt
  4. Page table and TLB update
  5. Restart overhead

Numerical mini-analysis:

Given:
  Fault service components
    Trap+kernel overhead = 5 µs
    Disk read = 7 ms
    Mapping updates = 10 µs

Total fault time:
  = 5 µs + 7000 µs + 10 µs
  = 7015 µs = 7.015 ms

Operating system implementation:
  - Linux uses per-process virtual memory areas, page cache, swap subsystem,
    and per-architecture fault handlers.
  - Fault path is highly optimized but still many orders slower than RAM hit.

Real-life analogy:
  You ask for a file at your desk drawer. If missing, office staff must go to
  archive room, fetch it, update index, and return. The request eventually
  succeeds, but with significant delay.

Advantages of fault-driven design:
  1. Supports lazy allocation and demand loading.
  2. Enables sparse large virtual spaces efficiently.
  3. Integrates protection with memory management.

Disadvantages:
  1. High latency on major faults.
  2. Fault storms can collapse throughput.
  3. Complex kernel path with concurrency concerns.

    Micro-topic: Copy-on-Write Faults
    ─────────────────────────────────
    During `fork()`, parent and child may share read-only pages. On first write
    attempt, fault occurs, kernel allocates new frame, copies data, and updates
    writer mapping. This preserves correctness and saves memory.

        Deeper: Fault Frequency as Health Metric
        ────────────────────────────────────────
        OSes monitor page-fault trends to detect pressure. Persistently high
        major fault rate indicates insufficient RAM or poor replacement tuning.


    Key Points
    ──────────
    • Page fault is a hardware-to-kernel control transfer.
    • Major faults are expensive due to disk I/O.
    • Correct fault handling is essential for VM correctness and security.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. Define page fault.
      2. Differentiate minor and major page faults.

    Long Questions (8–10 marks)
      1. Explain page-fault handling sequence in detail.
      2. Discuss role of page replacement during fault servicing.

    Numerical Problems
      1. Compute total fault handling time from component latencies.
      2. Estimate overall slowdown for given fault rate.

5.3  THRASHING: WHEN OS SWAPS MORE THAN IT WORKS
--------------------------------------------------------------------------------

Definition:
  Thrashing is a pathological state in which the system spends most of its time
  handling page faults and disk transfers rather than executing user code.

Why thrashing happens:
  1. Total active working sets of processes exceed available RAM.
  2. Degree of multiprogramming is too high under memory pressure.
  3. Poor page replacement decisions increase refault frequency.

Internal mechanism (cause-effect chain):
  1. Memory pressure rises.
  2. Replacement evicts pages still needed soon.
  3. Processes fault repeatedly to reload evicted pages.
  4. Disk I/O increases sharply.
  5. CPU utilization drops (waiting on I/O).
  6. Throughput collapses despite high system activity.

ASCII symptom loop:

      Low Free RAM
          │
          ▼
      More Evictions
          │
          ▼
      More Page Faults
          │
          ▼
      More Disk I/O Wait
          │
          ▼
      Lower CPU Useful Work
          │
          └───────────────┐
                          ▼
                      Thrashing

Working Set Model:
  Let $W_i(\Delta)$ be pages process i referenced in recent window $\Delta$.
  Total demand:

      D = Σ W_i(Δ)

If $D >$ available frames, system is at high risk of thrashing.

Page Fault Frequency (PFF) control idea:
  - If process fault rate too high -> allocate more frames or suspend process.
  - If very low fault rate -> frames may be reclaimed safely.

Detecting thrashing in practice:
  1. High sustained major page-fault rate
  2. High disk utilization with low productive CPU usage
  3. Increased response time for all processes

Operating system mitigation strategies:
  1. Reduce multiprogramming degree (temporarily swap/suspend processes).
  2. Use working-set-aware replacement.
  3. Prefer local replacement for stability in some workloads.
  4. Add RAM or tune memory overcommit and reclaim behavior.
  5. Use huge pages carefully when beneficial to reduce TLB/fault pressure.

Real-life analogy:
  A crowded kitchen with too few work surfaces. Chefs keep moving utensils in
  and out of storage instead of cooking. Activity is high, meals output is low.

Advantages/disadvantages framing:
  Thrashing itself has no benefit; it is a failure mode. However, studying it
  reveals design limits and motivates adaptive memory-control policies.

Numerical illustration:

Given 3 processes working sets:
  P1=20 pages, P2=18 pages, P3=25 pages
  Total demand $D = 63$ pages
  Available frames = 48 pages

Since $63 > 48$, system likely thrashes unless one process is suspended or more
frames become available.

    Micro-topic: Global vs Local Replacement and Thrashing
    ──────────────────────────────────────────────────────
    Global replacement lets one process steal frames from another, which can
    spread instability. Local replacement confines victim choices to process's
    own allocation, often improving isolation under pressure.

        Deeper: Linux OOM and Last-Resort Recovery
        ───────────────────────────────────────────
        If memory reclaim and swapping cannot satisfy allocations, Linux may
        invoke OOM killer to terminate selected processes and recover the
        system. This is a last resort, not normal operating state.


    Key Points
    ──────────
    • Thrashing means paging overhead dominates useful execution.
    • Working set excess over frames is a primary root cause.
    • Control policies (PFF/working set) are essential to stability.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. Define thrashing.
      2. State two symptoms of thrashing.

    Long Questions (8–10 marks)
      1. Explain causes and control of thrashing.
      2. Discuss working set model with equation and interpretation.

    Numerical Problems
      1. Determine thrashing risk using total working set and available frames.
      2. Analyze effect of reducing multiprogramming on fault frequency.

6.0  PAGE REPLACEMENT ALGORITHMS (THE NUMERICAL SECTION)
================================================================================

When a page fault occurs and no free frame is available, the operating system
must choose a resident page to evict. This decision is made by a page
replacement algorithm.

Why replacement algorithms exist:
  1. Physical RAM is finite.
  2. Demand paging needs victim selection under pressure.
  3. Choice of victim strongly affects page-fault rate and performance.

Core optimization objective:
  Minimize future page faults while keeping algorithm overhead practical.

General replacement workflow:
  1. Page fault occurs.
  2. If free frame exists, load page directly.
  3. Else choose victim by policy.
  4. If victim dirty, write to disk.
  5. Load demanded page and update metadata.

ASCII control path:

      Page Fault
          │
          ▼
   Free Frame Available?
      │             │
     Yes           No
      │             │
      ▼             ▼
   Load page     Select victim
                      │
                      ▼
              Evict -> Load -> Resume

Reference string used for main solved sets:

      7 0 1 2 0 3 0 4 2 3 0 3 2

Frames considered: 3 (unless explicitly stated otherwise)

6.1  FIFO: FIRST-IN-FIRST-OUT (AND BÉLÁDY'S ANOMALY)
--------------------------------------------------------------------------------

Definition:
  FIFO evicts the page that has been in memory the longest (oldest arrival).

Why FIFO exists:
  1. Very simple queue-based implementation.
  2. Low bookkeeping overhead.

Internal working mechanism:
  1. Keep frames in queue order of insertion.
  2. On hit: no queue reorder.
  3. On fault with full frames: evict queue front and append new page.

Real-life analogy:
  People standing in a line at a service counter. The person who arrived first
  leaves first, regardless of current urgency.

Solved numerical (3 frames):

Step   Page   Frame1   Frame2   Frame3   Fault
----------------------------------------------------------
1      7      7        -        -        Yes
2      0      7        0        -        Yes
3      1      7        0        1        Yes
4      2      2        0        1        Yes
5      0      2        0        1        No
6      3      2        3        1        Yes
7      0      2        3        0        Yes
8      4      4        3        0        Yes
9      2      4        2        0        Yes
10     3      4        2        3        Yes
11     0      0        2        3        Yes
12     3      0        2        3        No
13     2      0        2        3        No

Total Page Faults (FIFO, 3 frames) = 10

Bélády's Anomaly:
  In FIFO, increasing frame count can sometimes increase page faults.

Demonstration reference string:
  1 2 3 4 1 2 5 1 2 3 4 5

FIFO with 3 frames:

Step   Page   F1   F2   F3   Fault
--------------------------------------
1      1      1    -    -    Yes
2      2      1    2    -    Yes
3      3      1    2    3    Yes
4      4      4    2    3    Yes
5      1      4    1    3    Yes
6      2      4    1    2    Yes
7      5      5    1    2    Yes
8      1      5    1    2    No
9      2      5    1    2    No
10     3      5    3    2    Yes
11     4      5    3    4    Yes

--------------------------------------------

2      2      1    2    -    -    Yes

Anomaly observed: more frames (4) produced more faults than 3.

Operating system implementation note:
  Pure FIFO is rarely used alone in modern kernels due to poor locality
  awareness.

Advantages:
  1. Very simple implementation.
  2. Low per-reference overhead.

Disadvantages:
  1. Ignores usage recency/frequency.
  2. Suffers Bélády's anomaly.
  3. Can evict heavily used pages.

    ──────────────────────────────────────────────────────
    Stack algorithms (for example LRU, OPT) guarantee that pages in memory with

    FIFO is not a stack algorithm.

        Deeper: Why FIFO Still Taught
        ─────────────────────────────
        FIFO is pedagogically important because it exposes the difference
        between easy implementation and good performance characteristics.


    Key Points
    ──────────
    • FIFO replaces oldest loaded page.
    • It is simple but can perform poorly.
    • Bélády's anomaly is a classic FIFO weakness.

6.2  OPTIMAL (OPT): THEORETICAL BEST (BUT IMPOSSIBLE ONLINE)
--------------------------------------------------------------------------------

Definition:
  OPT (Belady's optimal algorithm) replaces the page whose next use is farthest
  in the future.

Why OPT exists:
  1. Provides theoretical lower bound on page faults.
  2. Serves as benchmark for evaluating practical algorithms.

Internal mechanism:
  1. On fault with full frames, inspect future reference stream.
  2. For each resident page, find next-use index.
  3. Evict page with farthest next use (or never used again).

Why impossible in real-time systems:
  Future references are unknown at runtime.

Real-life analogy:
  Packing travel bag while knowing exact future schedule. You remove the item
  you will need farthest in future. Perfect if future is known.

Solved numerical (same string, 3 frames):

Step   Page   Frame1   Frame2   Frame3   Fault
----------------------------------------------------------
1      7      7        -        -        Yes
2      0      7        0        -        Yes
3      1      7        0        1        Yes
4      2      2        0        1        Yes   (7 replaced)
5      0      2        0        1        No
6      3      2        0        3        Yes   (1 replaced)
7      0      2        0        3        No
8      4      2        4        3        Yes   (0 replaced)
9      2      2        4        3        No
10     3      2        4        3        No
11     0      2        0        3        Yes   (4 replaced)
12     3      2        0        3        No
13     2      2        0        3        No

Total Page Faults (OPT, 3 frames) = 7

Operating system implementation:
  - Not directly implementable for live systems.
  - Used in simulators, research, and exam comparisons.

Advantages:
  1. Minimum possible faults for any given string.
  2. Useful theoretical benchmark.

Disadvantages:
  1. Requires future knowledge.
  2. Not feasible as online policy.

    Micro-topic: Competitive Evaluation
    ───────────────────────────────────
    In exams, compare practical algorithm fault count to OPT to discuss
    closeness-to-optimal behavior.

        Deeper: Offline Oracle Perspective
        ─────────────────────────────────
        OPT acts like an oracle with future insight. Real systems cannot access
        this information, so practical algorithms approximate recency/frequency
        patterns as a substitute.


    Key Points
    ──────────
    • OPT gives theoretical minimum page faults.
    • It is offline, not implementable in real-time OS.
    • Used as benchmark baseline.

    Typical Exam Questions
    ──────────────────────
    Short Questions (2–4 marks)
      1. Define OPT replacement.
      2. Why is OPT impossible in practice?

    Long Questions (8–10 marks)
      1. Solve OPT for a given reference string.
      2. Compare FIFO/LRU results against OPT.

    Numerical Problems
      1. Compute OPT fault count for given frames.

6.3  LRU (LEAST RECENTLY USED): MOST PRACTICAL CLASSICAL POLICY
--------------------------------------------------------------------------------

Definition:
  LRU evicts the page that has not been used for the longest time in the past.

Why LRU exists:
  1. Approximates temporal locality effectively.
  2. Generally performs much better than FIFO.

Internal mechanism:
  1. Track recency of page accesses.
  2. On hit, mark page as most recently used.
  3. On fault with full frames, evict least recently used page.

Implementation approaches:
  1. Counter/timestamp method
  2. Stack/list ordering method

Operating system implementation reality:
  Exact LRU is expensive at scale. Real kernels use approximations based on
  reference bits, active/inactive lists, and aging heuristics.

Real-life analogy:
  Desk cleanup: remove the document not touched for the longest time because it
  is least likely to be needed immediately.

Advantages:
  1. Uses recency principle aligned with program behavior.
  2. Usually better than FIFO.
  3. Stack algorithm property (no Bélády anomaly).

Disadvantages:
  1. Exact implementation overhead can be high.
  2. Can still perform poorly on cyclic patterns larger than frame count.

    Micro-topic: LRU as Stack Algorithm
    ───────────────────────────────────
    With more frames, LRU page-fault count does not increase for same reference
    string. This monotonic property avoids FIFO-style anomaly.

        Deeper: Why OSes Approximate LRU
        ────────────────────────────────
        Maintaining exact global recency order for millions of pages is costly.
        Systems approximate LRU with hardware accessed bits and periodic aging
        scans to balance accuracy and overhead.


    Key Points
    ──────────
    • LRU evicts least recently used page.
    • Better locality awareness than FIFO.
    • Exact LRU is expensive; approximations are common.

6.4  SECOND CHANCE / CLOCK: PRACTICAL LRU APPROXIMATION
--------------------------------------------------------------------------------

Definition:
  Second Chance (Clock) is a FIFO-based policy enhanced with reference bit R.
  Pages with R=1 receive a "second chance" before eviction.

Why it exists:
  1. Approximates LRU with low overhead.
  2. Uses hardware-maintained reference bits effectively.
  3. Practical for large systems.

Internal mechanism:
  1. Frames arranged conceptually in a circle with a clock hand pointer.
  2. On access, page's R bit becomes 1.
  3. On replacement:
       - If candidate has R=0, evict it.
       - If R=1, set R=0 and move hand forward.
  4. Continue until an R=0 victim found.

ASCII clock idea:

            [F0,R]
          /        \
     [F3,R]      [F1,R]
          \        /
            [F2,R]

      Clock hand rotates searching for R=0 victim

Operating system implementation:
  - Practical kernels use clock-like aging mechanisms and active/inactive page
    lists to approximate recency while keeping overhead manageable.
  - Linux memory reclaim is more sophisticated than textbook one-bit clock but
    conceptually related to "give recently used pages another chance".

Real-life analogy:
  Library return shelf check:
  - If a book was recently touched (R=1), librarian gives it one more round.
  - Untouched books (R=0) are moved out first.

Advantages:
  1. Near-LRU behavior with much lower cost.
  2. Scales better than exact LRU.
  3. Good practical compromise.

Disadvantages:
  1. Not exact recency ordering.
  2. Quality depends on reference-bit update behavior.
  3. Edge workloads can still perform suboptimally.

    Micro-topic: Clock vs Second Chance Naming
    ───────────────────────────────────────────
    "Second Chance" describes the policy idea; "Clock" describes common data
    structure implementation using circular list and rotating pointer.

        Deeper: From Clock to WSClock
        ─────────────────────────────
        WSClock adds working-set age and dirty-page handling to clock logic,
        improving decision quality under memory pressure.


    Key Points
    ──────────
    • Clock gives recently referenced pages one extra chance.
    • It is a practical approximation to LRU.
    • Widely relevant to real-world kernel reclaim designs.
