1.1  CONCEPT AND FUNCTION OF OPERATING SYSTEMS
================================================================================

An operating system (OS) is a sophisticated layer of system software that sits
between the raw hardware of a computer and the application programs that users
interact with. Its primary purpose is twofold: first, to provide an abstraction
layer that hides the ugly, complex details of hardware management from
application programmers and users; and second, to act as a resource manager
that allocates and controls access to the CPU, memory, I/O devices, and files
in an orderly and controlled fashion.

To understand the concept deeply, consider that a modern computer system is
composed of one or more processors, main memory (RAM), disks, printers,
a keyboard, a mouse, a display, network interfaces, and various other I/O
devices. Writing programs that keep track of all these components and use them
correctly—let alone optimally—is an extremely difficult job. For this reason,
computers are equipped with an operating system whose job is to manage all
these devices and provide user programs with a simpler, cleaner model of the
computer.

──────────────────────────────────────────
1.1.1  The OS as an Extended Machine (Top-Down View)
──────────────────────────────────────────

From the top-down (or user-centric) perspective, the operating system exists to
present the programmer with the equivalent of an "extended machine" or "virtual
machine" that is easier to program than the underlying hardware. Consider disk
I/O as an example: to read a block from a SATA hard disk, a programmer would
need to know about the disk controller's register layout, how to issue ATA
commands, handle DMA transfers, manage interrupts from the disk controller, and
deal with error conditions—all at the register level. The OS abstracts this
away into a simple read() system call.

The abstraction principle is one of the keys to managing complexity. Good
abstractions turn a nearly impossible task into two manageable ones. The first
is defining and implementing the abstractions (this is what the OS does). The
second is using these abstractions to solve the problem at hand (this is what
application programmers do).

    Micro-topic: Hardware Abstraction Layer (HAL)
    ─────────────────────────────────────────────
    Modern operating systems like Linux implement a Hardware Abstraction Layer
    that sits between the kernel proper and the hardware. In the Linux kernel,
    arch/-specific directories contain architecture-dependent code (e.g.,
    arch/x86/, arch/arm64/) that abstracts the CPU, interrupt controllers
    (APIC, GIC), timer hardware, and memory management units (MMUs). This
    allows the rest of the kernel to be largely hardware-independent.

    Inside the HAL, you find critical structures such as:
    - Interrupt Descriptor Table (IDT): Maps interrupt vectors to handler
      routines. On x86-64 Linux, this is set up during boot in
      arch/x86/kernel/idt.c.
    - Global Descriptor Table (GDT): Defines memory segments. Though modern
      Linux uses a flat memory model (base=0, limit=max), the GDT is still
      required by x86 architecture for defining kernel/user code and data
      segments, as well as the Task State Segment (TSS).

──────────────────────────────────────────
1.1.2  The OS as a Resource Manager (Bottom-Up View)
──────────────────────────────────────────

From the bottom-up (or resource-management) perspective, the operating system
is there to manage all the pieces of a complex system. Modern computers
consist of processors, memories, timers, disks, mice, network interfaces,
printers, and a wide variety of other devices. The OS must keep track of who is
using which resource, granting resource requests, accounting for usage, and
mediating conflicting requests from different programs and users.

Resource management includes multiplexing (sharing) resources in two different
ways:

  (a) Time Multiplexing: Different programs or users take turns using the
      resource. For example, the CPU is time-multiplexed among processes using
      scheduling algorithms. The OS determines who runs next and for how long.

  (b) Space Multiplexing: Instead of taking turns, each entity gets part of
      the resource. Main memory is space-multiplexed: it is divided among
      several running programs so that each can be resident at the same time.
      Disk space is similarly space-multiplexed, with each file occupying a
      portion of the disk.

    Micro-topic: Resource Accounting and cgroups
    ─────────────────────────────────────────────
    In modern Linux, resource management goes far beyond simple CPU and memory
    allocation. The kernel provides Control Groups (cgroups), a mechanism to
    organize processes hierarchically and distribute resources (CPU time,
    system memory, network bandwidth, disk I/O) among those groups. cgroups v2
    (unified hierarchy, default in modern kernels including Arch Linux) allows
    fine-grained control:

      - cpu.max: Limits CPU bandwidth (e.g., "200000 1000000" means 200ms
        per 1000ms period, effectively 20% of one CPU).
      - memory.max: Hard memory limit for a cgroup.
      - io.max: Limits disk I/O rates (rbps, wbps, riops, wiops).

    These cgroups underpin container technologies (Docker, Podman, systemd-
    nspawn) and are managed by systemd on Arch Linux through "slices" and
    "scopes".

──────────────────────────────────────────
1.1.3  Core Functions of an Operating System
──────────────────────────────────────────

The major functions that an operating system performs can be enumerated as
follows:

  1. Process Management: The OS creates and deletes processes, suspends and
     resumes processes, provides mechanisms for process synchronization,
     provides mechanisms for process communication, and provides mechanisms
     for deadlock handling.

  2. Memory Management: The OS keeps track of which parts of memory are
     currently being used and by whom, decides which processes and data to
     move into and out of memory, and allocates and deallocates memory space
     as needed.

  3. File System Management: The OS creates and deletes files and directories,
     provides primitives to manipulate files and directories, maps files onto
     secondary storage, and backs up files onto stable (non-volatile) storage
     media.

  4. I/O System Management: The OS manages the memory management component
     of I/O (buffering, caching, spooling), provides a general device-driver
     interface, and provides drivers for specific hardware devices.

  5. Protection and Security: The OS ensures that all access to system
     resources is controlled, provides user authentication, and defends
     external I/O devices from invalid access attempts.

  6. Networking: Modern operating systems provide TCP/IP stack implementation,
     socket APIs, and support for various network protocols.

  7. Command Interpretation: Through shells and graphical interfaces, the OS
     interprets and executes user commands.

1.2  OPERATING SYSTEMS CONCEPT AND FUNCTIONALITY
================================================================================

The interface between the operating system and the user programs is defined by
the set of "extended instructions" that the operating system provides. These
extended instructions are traditionally known as system calls, and they form
the boundary between user space and kernel space. To truly understand what
operating systems do, we need to examine the key concepts that they manage:
processes, files, and the system call interface, along with the shell that
provides interactive access.

────────────────────────────────────────────────────
1.2.1  Processes
────────────────────────────────────────────────────

A process is the fundamental concept in any operating system. Informally, a
process is a program in execution. Associated with each process is its address
space—a list of memory locations from 0 to some maximum, which the process can
read and write. The address space contains the executable program, the
program's data, and its stack. Also associated with each process is a set of
registers, including the program counter (PC), stack pointer (SP), and other
hardware registers, as well as all the other information needed to run the
program.

Conceptually, each process has its own virtual CPU. In reality, the actual CPU
switches back and forth from process to process (this is called
multiprogramming), but to understand the system, it is much easier to think
about a collection of processes running in (pseudo) parallel than to try to
keep track of how the CPU switches from program to program.

    Micro-topic: The task_struct in Linux
    ─────────────────────────────────────
    In the Linux kernel, every process is represented by a data structure
    called task_struct, defined in include/linux/sched.h. This is one of the
    largest data structures in the kernel, containing hundreds of fields. Key
    fields include:

      - pid (Process ID): A unique integer identifier.
      - state: The current state of the process (TASK_RUNNING,
        TASK_INTERRUPTIBLE, TASK_UNINTERRUPTIBLE, TASK_STOPPED, TASK_ZOMBIE).
      - mm (struct mm_struct *): Pointer to the memory descriptor, which
        contains the process's virtual address space information, including
        the page tables.
      - fs (struct fs_struct *): Filesystem information (root directory,
        current working directory).
      - files (struct files_struct *): Open file table.
      - signal (struct signal_struct *): Signal handlers.
      - parent / children: Pointers forming the process tree.
      - sched_entity: The scheduling entity used by the CFS scheduler to
        track virtual runtime (vruntime).

        Deeper: The sched_entity and vruntime
        ──────────────────────────────────────
        The sched_entity is a sub-structure embedded in task_struct that the
        Completely Fair Scheduler (CFS) uses to track how much CPU time a
        process has received. The key field is vruntime (virtual runtime),
        which is the weighted sum of actual CPU time consumed. Processes with
        smaller vruntime values are given priority by CFS, as they have
        received less than their fair share. The CFS maintains all runnable
        tasks in a red-black tree, ordered by vruntime, allowing O(log n)
        insertion and O(1) selection of the next task (it's always the
        leftmost node).

All processes in the system form a tree structure. When an operating system
boots on Linux, the first user-space process is init (PID 1), which on Arch
Linux is systemd. Every subsequent process is created by a parent process
using the fork() system call, forming a hierarchy.

    Micro-topic: Process Creation — fork(), exec(), clone()
    ───────────────────────────────────────────────────────
    In UNIX/Linux, process creation is achieved through the fork() system call,
    which creates a near-exact duplicate of the calling process. The new
    (child) process gets a copy of the parent's address space, open files,
    and other resources. However, modern Linux uses Copy-on-Write (CoW) to
    avoid actually copying the entire address space: the parent and child
    share the same physical pages, which are marked read-only. When either
    process tries to write to a shared page, a page fault occurs, and the
    kernel then makes a private copy of that page for the writing process.

    After fork(), the child typically calls exec() (one of the execve family)
    to replace its memory image with a new program. This two-step process
    (fork + exec) is fundamental to UNIX process creation.

    Under the hood, both fork() and the creation of threads in Linux are
    implemented via the clone() system call, which allows fine-grained control
    over what is shared between the parent and child (address space, file
    descriptor table, signal handlers, etc.).

────────────────────────────────────────────────────
1.2.2  Files
────────────────────────────────────────────────────

Another key concept supported by virtually all operating systems is the file
system. A major function of the operating system is to hide the peculiarities
of the disks and other I/O devices and present the programmer with a nice,
clean abstract model of device-independent files.

System calls are needed to create files, remove files, read files, and write
files. Before a file can be read, it must be located on the disk and opened,
and after being read it should be closed, so calls are provided for these
things too.

To provide a place to keep files, most operating systems have the concept of
a directory as a way of grouping files together. A directory hierarchy, or
directory tree, forms the logical organization of the file system. In UNIX and
Linux, the file system forms a single unified tree starting from the root
directory (/), regardless of how many physical disks are attached.

    Micro-topic: The Virtual File System (VFS) Layer
    ─────────────────────────────────────────────────
    Linux implements a Virtual File System (VFS) layer that provides a common
    interface to different file system implementations (ext4, XFS, Btrfs,
    FAT32, NTFS, tmpfs, procfs, sysfs, etc.). The VFS defines a set of
    operations that every file system must implement:

      - struct super_operations: Operations on the superblock (e.g., alloc_
        inode, destroy_inode, write_super).
      - struct inode_operations: Operations on inodes (e.g., create, lookup,
        link, unlink, mkdir, rmdir, rename).
      - struct file_operations: Operations on open files (e.g., read, write,
        llseek, mmap, ioctl, open, release).
      - struct dentry_operations: Operations on directory entries (dentries).

    This abstraction means that a user-space program calling read() doesn't
    need to know whether the file resides on an ext4 partition, a Btrfs
    subvolume, or a remote NFS share—the VFS dispatches to the appropriate
    driver.

        Deeper: The inode Structure
        ───────────────────────────
        Every file in a UNIX file system is represented by an inode (index
        node), which is a data structure that contains all metadata about the
        file except its name and its actual data. The inode stores:
          - File type and permissions (mode)
          - Owner (uid) and group (gid)
          - File size in bytes
          - Timestamps (atime, mtime, ctime)
          - Number of hard links
          - Pointers to data blocks (direct, single-indirect, double-indirect,
            triple-indirect blocks)
        In ext4, each inode is 256 bytes by default. The total number of
        inodes is determined at filesystem creation time (mkfs.ext4) and
        limits the maximum number of files.

    Micro-topic: Special Files and the /proc & /sys Filesystems
    ───────────────────────────────────────────────────────────
    UNIX systems make I/O devices look like files. Special files come in two
    flavors:
      - Block special files: Model devices that consist of randomly
        addressable blocks (disks).
      - Character special files: Model devices that accept or output a
        character stream (terminals, printers).

    Beyond device files, Linux provides two pseudo-filesystems:
      - /proc: A virtual filesystem that exposes kernel and process
        information as files. For example, /proc/cpuinfo contains CPU
        details, /proc/meminfo shows memory statistics, and /proc/[pid]/
        directories contain per-process information.
      - /sys (sysfs): Exposes the kernel's device model—a structured view of
        buses, devices, and drivers. It's used by udev (on Arch, systemd-
        udevd) to discover and manage hardware.

────────────────────────────────────────────────────
1.2.3  System Calls
────────────────────────────────────────────────────

If processes want to interact with the hardware, communicate with each other,
create or destroy processes, or do anything that involves the kernel's
services, they must make a system call. A system call is the programmatic way
in which a computer program requests a service from the kernel of the
operating system. System calls provide the interface between a process and the
operating system.

When a user-space program invokes a system call (e.g., read()), the following
sequence occurs on a modern x86-64 Linux system:

  1. The C library function (glibc wrapper) places the system call number in
     the RAX register and the arguments in RDI, RSI, RDX, R10, R8, R9.

  2. The SYSCALL instruction is executed, which:
     a. Saves the user-space RIP (return address) in RCX.
     b. Saves the user-space RFLAGS in R11.
     c. Loads the kernel's code segment selector and instruction pointer
        from the MSR (Model Specific Register) IA32_LSTAR.
     d. Switches to Ring 0 (kernel mode).

  3. The kernel's system call entry point (entry_SYSCALL_64 in
     arch/x86/entry/entry_64.S) saves the user-space register state onto
     the kernel stack, looks up the system call number in the sys_call_table,
     and dispatches to the appropriate kernel function.

  4. After the kernel function completes, the return value is placed in RAX,
     and the SYSRET instruction restores user-space execution.

    Micro-topic: Categories of System Calls
    ────────────────────────────────────────
    System calls can be broadly categorized as:

      (a) Process Control: fork(), exec(), wait(), exit(), kill(), getpid()
      (b) File Management: open(), close(), read(), write(), lseek(), stat()
      (c) Device Management: ioctl(), read(), write() on device files
      (d) Information Maintenance: time(), gettimeofday(), getuid(), uname()
      (e) Communication: pipe(), shmget(), mmap(), socket(), send(), recv()
      (f) Protection: chmod(), chown(), umask(), setuid()

    In Linux, there are over 450 system calls (as of kernel 6.x). The
    complete list can be found in the kernel source at
    arch/x86/entry/syscalls/syscall_64.tbl.

        Deeper: The vDSO (Virtual Dynamic Shared Object)
        ─────────────────────────────────────────────────
        Not every "system call" actually needs to trap into the kernel. The
        Linux kernel provides a mechanism called the vDSO, a small shared
        library that the kernel automatically maps into every process's
        address space. It provides user-space implementations of certain
        frequently-called functions (like gettimeofday() and clock_gettime())
        that can read kernel-exported data structures directly from user
        space without a context switch. This dramatically improves
        performance for time-sensitive applications. On x86-64, the vDSO
        reads a shared page (vvar) that the kernel updates on every timer
        tick.

────────────────────────────────────────────────────
1.2.4  The Shell
────────────────────────────────────────────────────

The shell is the operating system's command-line interpreter. It is the primary
interface between a user sitting at a terminal and the operating system. When a
user logs in, a shell is started. The shell has the terminal as standard input
and standard output. It displays a prompt (e.g., $ or #), the user types a
command, and the shell carries it out.

The shell is not part of the operating system itself; it is a user-space
program. This is an important distinction. On UNIX and Linux systems, there
are many shells available:

  - sh (Bourne Shell): The original UNIX shell by Stephen Bourne.
  - bash (Bourne Again Shell): The most widely used shell, default on many
    Linux distributions. It extends sh with features like command-line
    editing, history, and job control.
  - zsh (Z Shell): An extended shell with powerful features like better tab
    completion, globbing, theming (Oh My Zsh), and scripting capabilities.
    This is the default shell on macOS and is very popular on Arch Linux.
  - fish (Friendly Interactive Shell): A user-friendly shell with syntax
    highlighting and auto-suggestions.
  - dash: A minimal POSIX-compliant shell, often used as /bin/sh for speed
    in script execution.

When a user types a command like:

    $ ls -la /tmp

The shell performs the following steps:
  1. Reads the command from standard input.
  2. Parses the command line into the program name ("ls") and arguments
     ("-la", "/tmp").
  3. Calls fork() to create a child process.
  4. In the child, calls execvp("ls", ["ls", "-la", "/tmp"]) to replace the
     child's image with the ls program.
  5. The parent (shell) calls waitpid() to wait for the child to finish.
  6. When ls exits, the shell regains control and prints a new prompt.

    Micro-topic: Shell I/O Redirection and Pipes
    ─────────────────────────────────────────────
    One of the most powerful features of the UNIX shell is the ability to
    redirect I/O and connect processes together using pipes:

      - Output Redirection: ls > file.txt redirects stdout to a file.
        The shell opens file.txt (or creates it), then uses dup2() to
        replace the child's file descriptor 1 (stdout) with the file's fd
        before calling exec().

      - Input Redirection: sort < data.txt redirects stdin from a file.

      - Pipes: ls | grep ".c" connects the stdout of ls to the stdin of
        grep. The shell calls pipe() to create a pipe (two file descriptors),
        forks twice, and uses dup2() to wire them together.

        Deeper: Named Pipes (FIFOs) and Here Documents
        ───────────────────────────────────────────────
        Beyond anonymous pipes, UNIX provides named pipes (FIFOs) that exist
        as entries in the file system and allow unrelated processes to
        communicate. They are created with mkfifo and can be opened like
        regular files.

        Here documents (<<) allow the shell to feed multi-line input to a
        command directly from the script:

            cat << EOF
            This is line one.
            This is line two.
            EOF

1.3  OPERATING SYSTEM STRUCTURE
================================================================================

The internal organization of an operating system is a critical design decision
that affects its reliability, performance, extensibility, and security. Over
the decades, several structural models have been proposed and implemented. Each
model represents a different trade-off between these factors.

────────────────────────────────────────────────────
1.3.1  Monolithic System
────────────────────────────────────────────────────

A monolithic operating system is structured as a single large program running
in kernel mode. The entire operating system runs as a single program in kernel
space. The structure is essentially "no structure"—the operating system is
written as a collection of procedures, each of which can call any other one.

In a monolithic system, every component of the operating system—process
management, memory management, file system, device drivers, networking stack—
all runs in the same address space with full access to all hardware. When a
user program makes a system call, the hardware traps to the kernel, the
parameters are checked, and the appropriate service procedure is called
directly.

    Structure of a typical monolithic OS:
    ┌──────────────────────────────────────┐
    │           User Programs              │  (User Space)
    ├──────────────────────────────────────┤
    │  ┌──────────────────────────────┐    │
    │  │   System Call Interface      │    │
    │  ├──────────────────────────────┤    │
    │  │   Service Procedures         │    │  (Kernel Space)
    │  ├──────────────────────────────┤    │
    │  │   Utility Procedures         │    │
    │  └──────────────────────────────┘    │
    └──────────────────────────────────────┘

Advantages:
  - High performance: No overhead from message passing; procedure calls are
    fast within a single address space.
  - Simple to implement for small systems.

Disadvantages:
  - Poor reliability: A bug in any part of the kernel can crash the entire
    system (a faulty device driver can corrupt kernel memory).
  - Difficult to maintain and extend: All code is intertwined.
  - Large attack surface: Any vulnerability in any component gives an attacker
    full kernel access.

Real-World Context: Linux is technically a monolithic kernel, although it
mitigates many of the disadvantages through loadable kernel modules (LKMs).
Modules allow device drivers, file systems, and other components to be loaded
and unloaded at runtime without rebooting. This gives Linux some of the
flexibility of a microkernel while retaining the performance advantages of
a monolithic architecture. The term for this design is "modular monolithic."

    Micro-topic: Loadable Kernel Modules (LKMs) in Linux
    ─────────────────────────────────────────────────────
    A loadable kernel module is an object file (*.ko) that contains code to
    extend the running kernel. Modules can be loaded with insmod or modprobe
    and removed with rmmod. The module system uses symbol tables to resolve
    dependencies between modules.

    Key commands:
      lsmod              — List currently loaded modules
      modprobe <module>  — Load a module (resolving dependencies)
      modinfo <module>   — Show module information
      rmmod <module>     — Unload a module

        Deeper: Module Initialization and Cleanup
        ──────────────────────────────────────────
        Every kernel module must define at least two functions:
          - init_module() (or a function registered via module_init()):
            Called when the module is loaded. It registers the module's
            functionality with the kernel (e.g., registers a character
            device, sets up a network driver).
          - cleanup_module() (or a function registered via module_exit()):
            Called when the module is unloaded. It deregisters everything
            and frees allocated resources.

        The module is compiled against the kernel headers and must match
        the running kernel version. Arch Linux's linux package provides
        headers in /usr/lib/modules/$(uname -r)/build/.

────────────────────────────────────────────────────
1.3.2  Layered System
────────────────────────────────────────────────────

The layered approach to operating system design organizes the OS as a hierarchy
of layers. Each layer is built on top of the one below it. The bottom layer
(layer 0) is the hardware. The highest layer (layer N) is the user interface.
Each layer uses only the functions and services of the layer directly below it.

The original layered system was THE (Technische Hogeschool Eindhoven) system
designed by E.W. Dijkstra in the Netherlands in 1968. It had six layers:

  Layer 5: The operator (user interface)
  Layer 4: User programs
  Layer 3: I/O management
  Layer 2: Operator-process communication
  Layer 1: Memory and drum management
  Layer 0: Processor allocation and multiprogramming

Advantages:
  - Modularity: Each layer can be debugged independently.
  - Abstraction: Each layer only needs to know the interface of the layer
    below.
  - Security: Each layer can enforce access controls.

Disadvantages:
  - Performance: Each layer adds overhead. A request from a user program may
    need to pass through many layers to reach the hardware.
  - Difficulty of correct layering: Defining the exact boundaries and
    ordering of layers is challenging. For example, should the memory manager
    be above or below the process scheduler? The memory manager needs to
    page processes out, but the scheduler needs memory information.

    Micro-topic: The OSI Model as a Layered Architecture
    ────────────────────────────────────────────────────
    The layered design principle extends beyond OS kernels. The OSI
    (Open Systems Interconnection) model for networking uses seven layers
    (Physical, Data Link, Network, Transport, Session, Presentation,
    Application), each providing services to the layer above. The TCP/IP
    stack in the Linux kernel is itself layered: the socket layer sits above
    the transport layer (TCP/UDP), which sits above the network layer (IP),
    which sits above the link layer (Ethernet driver).

        Deeper: The Networking Stack Layers in the Linux Kernel
        ───────────────────────────────────────────────────────
        When a packet arrives at a Linux network interface:
          1. The NIC (Network Interface Card) driver receives the packet via
             an interrupt or NAPI polling and creates an sk_buff structure.
          2. The packet is passed up to the network layer (net/ipv4/ip_input.c
             for IPv4), where routing decisions are made.
          3. If destined locally, it's passed to the transport layer (TCP in
             net/ipv4/tcp_input.c), where sequence numbers are checked and
             the data is placed in the socket's receive buffer.
          4. The user-space application retrieves the data via recv() or
             read().

────────────────────────────────────────────────────
1.3.3  Virtual Machines
────────────────────────────────────────────────────

The virtual machine concept takes the layered approach to its logical
conclusion. A virtual machine monitor (VMM), also called a hypervisor, runs on
the bare hardware and provides an exact copy of the bare hardware to each
virtual machine running above it. Each virtual machine can run a different
operating system.

The original VM system was IBM's VM/370, which ran on IBM mainframes. Each user
got their own virtual machine that was an exact replica of the underlying
hardware (including kernel/user mode, I/O, interrupts, everything).

There are two types of hypervisors:

  Type 1 (Bare-Metal): The hypervisor runs directly on the hardware.
    Examples: VMware ESXi, Xen, Microsoft Hyper-V, KVM (Linux itself becomes
    the hypervisor).

  Type 2 (Hosted): The hypervisor runs as a program on top of a host OS.
    Examples: VirtualBox, VMware Workstation, QEMU (without KVM).

Real-World Context: KVM (Kernel-based Virtual Machine) is built into the
Linux kernel. When the kvm module is loaded, the Linux kernel itself becomes
a Type 1 hypervisor. Each virtual machine is a regular Linux process (managed
by QEMU), and the virtual CPUs are threads within that process. The host
kernel's scheduler schedules VM threads alongside normal processes.

    Micro-topic: Hardware Virtualization Extensions
    ────────────────────────────────────────────────
    Modern CPUs provide hardware support for virtualization:
      - Intel VT-x: Introduces VMX (Virtual Machine Extensions) with two
        new CPU modes: VMX root (for the hypervisor) and VMX non-root (for
        guest OS). The VMCS (Virtual Machine Control Structure) stores the
        state of both the host and guest.
      - AMD-V (SVM): AMD's equivalent, with VMCB (Virtual Machine Control
        Block).

    These extensions allow the hypervisor to run guest OS code directly on
    the CPU with near-native performance, only trapping to the hypervisor
    for privileged instructions.

        Deeper: VMCS and VM-Exit / VM-Entry
        ────────────────────────────────────
        A VM-Entry transitions from the hypervisor to the guest, loading the
        guest state from the VMCS. A VM-Exit transitions from the guest to
        the hypervisor when the guest executes a privileged instruction,
        accesses certain hardware, or when an external interrupt occurs. The
        VMCS contains fields for:
          - Guest state area (registers, IDTR, GDTR, CR0, CR3, CR4, etc.)
          - Host state area (hypervisor's register values to restore)
          - VM-execution control fields (which events cause VM-exits)
          - VM-exit information fields (reason for the exit)

────────────────────────────────────────────────────
1.3.4  Client-Server Model
────────────────────────────────────────────────────

The client-server model, when applied to operating system design, moves as
much functionality as possible out of the kernel and into user-space server
processes. The kernel's job is reduced to handling communication between
clients and servers and to managing basic hardware access.

In this model:
  - Server processes provide services: file server, memory server, process
    server, network server.
  - Client processes request services by sending messages to the appropriate
    server.
  - The kernel (often a microkernel) provides only the message-passing
    mechanism and basic scheduling.

When a user program wants to read a file, it sends a message to the file
server. The file server does the work and sends back the response. This
clear separation provides:

  - Better reliability: If the file server crashes, it can be restarted
    without rebooting. The rest of the system continues to function.
  - Better security: Each server runs with minimal privileges.
  - Easier extensibility: New servers can be added without modifying the
    kernel.

The disadvantage is performance: message passing between processes is slower
than direct function calls within a monolithic kernel.

    Micro-topic: The Distributed Client-Server Model
    ─────────────────────────────────────────────────
    The client-server model adapts naturally to distributed systems. The
    servers can run on different machines from the clients. For example,
    NFS (Network File System) implements a client-server file system where
    the NFS server runs on one machine and clients on others mount the
    remote filesystem transparently.

        Deeper: RPC (Remote Procedure Call) in Client-Server OS
        ───────────────────────────────────────────────────────
        Communication between clients and servers in distributed systems
        typically uses Remote Procedure Calls (RPC). An RPC allows a
        program on one machine to call a procedure on another machine. The
        client stub marshals the arguments into a network message, sends
        it to the server, the server stub unmarshals the arguments, calls
        the actual procedure, marshals the result, and sends it back. The
        caller is unaware that the call was executed remotely.

────────────────────────────────────────────────────
1.3.5  Microkernel and Exokernel
────────────────────────────────────────────────────

MICROKERNEL

A microkernel is a minimalist kernel that contains only the most essential
operating system functions:

  1. Inter-process communication (IPC) mechanism (message passing)
  2. Basic scheduling
  3. Low-level address space management

Everything else—device drivers, file systems, network protocols, even
traditional kernel services—runs in user space as separate server processes.

The key idea is to minimize the amount of code running in kernel mode to
reduce the number of potential bugs that can cause system crashes.

Notable microkernel systems:
  - Mach: Developed at Carnegie Mellon University. macOS and iOS run on
    XNU, which has a Mach microkernel at its core (though it also includes
    a BSD layer in kernel space, making it a hybrid).
  - MINIX 3: Andrew S. Tanenbaum's educational OS, designed for extreme
    reliability. All drivers run in user space; if a driver crashes, the
    reincarnation server restarts it automatically.
  - QNX: A real-time microkernel OS used in automotive (BlackBerry QNX),
    medical devices, and nuclear power plants.
  - seL4: A formally verified microkernel—proven mathematically to be
    free of implementation bugs.
  - GNU Hurd: A microkernel OS based on Mach, still in development.

    The Tanenbaum-Torvalds Debate (1992):
    ─────────────────────────────────────
    One of the most famous debates in OS history occurred between Andrew S.
    Tanenbaum (creator of MINIX) and Linus Torvalds (creator of Linux) on
    the comp.os.minix Usenet group. Tanenbaum argued that monolithic kernels
    were obsolete and that microkernels were the future. Torvalds argued
    that the performance advantages and practical results of Linux's
    monolithic design spoke for themselves. Decades later, both approaches
    survive: Linux dominates servers and embedded, while microkernels
    dominate safety-critical systems.

EXOKERNEL

The exokernel takes a radically different approach. Instead of providing
high-level abstractions, the exokernel exposes the hardware directly to
application programs, giving them almost complete control over physical
resources. The exokernel's only job is to ensure that no process interferes
with another—it handles only resource protection, not abstraction.

The idea is that operating system abstractions (like virtual memory pages,
file systems, etc.) are "one size fits all" and may not be optimal for
every application. By giving applications direct access to hardware resources,
each application can implement its own abstractions (via "library operating
systems" or libOS) optimized for its specific needs.

    Micro-topic: Library Operating Systems (LibOS)
    ───────────────────────────────────────────────
    In an exokernel system, each application links against a library OS
    that provides traditional OS abstractions (file system, networking,
    etc.) in user space. Different applications can use different libOS
    implementations optimized for their workload. For example, a database
    could use a libOS with a file system optimized for B-tree operations,
    while a web server could use one optimized for small random reads.

    Modern relevance: The concept of exokernels lives on in unikernels
    (like MirageOS, IncludeOS) where a single application is compiled
    directly with the OS library into a single-purpose virtual machine
    image. This eliminates multi-process overhead and is used in cloud
    environments for lightweight, fast-booting microservices.

        Deeper: Unikernels and Their Relationship to Exokernels
        ────────────────────────────────────────────────────────
        A unikernel is a specialized, single-address-space machine image
        constructed by using library operating systems. The application code
        is compiled together with the minimum OS functionality it needs into
        a bootable image that runs directly on a hypervisor. Benefits:
          - Tiny attack surface (no shell, no unnecessary services)
          - Sub-second boot times
          - Minimal memory footprint
        Examples: MirageOS (OCaml), IncludeOS (C++), Unik (Go).

1.4  TYPES AND EVOLUTION OF OPERATING SYSTEMS
================================================================================

Operating systems have evolved dramatically since the first computers in the
1940s. Understanding this evolution provides context for why modern operating
systems are designed the way they are.

────────────────────────────────────────────────────
1.4.1  Generations of Operating Systems
────────────────────────────────────────────────────

FIRST GENERATION (1945–1955): Vacuum Tubes and Plugboards
  - No operating system. Programmers had direct access to the hardware.
  - Programs were written in machine language and entered via plugboards
    or punch cards.
  - One program ran at a time (no multiprogramming).
  - Machines were enormous (ENIAC: 30 tons, 18,000 vacuum tubes).

SECOND GENERATION (1955–1965): Transistors and Batch Systems
  - Transistors replaced vacuum tubes, making computers more reliable.
  - Introduction of batch processing: Jobs were submitted on punch cards,
    collected into batches, and run sequentially.
  - The operator loaded a batch of jobs, and the computer ran them one
    after another.
  - Early batch monitors (e.g., IBM's FMS — Fortran Monitor System) were
    primitive operating systems.
  - No interaction between user and computer during job execution.

THIRD GENERATION (1965–1980): ICs and Multiprogramming
  - Integrated circuits (ICs) enabled smaller, cheaper, more powerful
    computers.
  - Introduction of multiprogramming: Multiple jobs kept in memory
    simultaneously. When one job was waiting for I/O, the CPU switched to
    another job, keeping the CPU busy.
  - Time-sharing (multitasking): A variant of multiprogramming where the
    CPU switches between users rapidly, giving each user the illusion of
    having the computer to themselves.
  - Key systems: IBM OS/360 (the first OS to span a product line), MULTICS
    (Multiplexed Information and Computing Service, the precursor to UNIX),
    and UNIX (developed by Ken Thompson and Dennis Ritchie at Bell Labs).
  - Spooling (Simultaneous Peripheral Operations On-Line): Overlapping I/O
    with computation.

FOURTH GENERATION (1980–Present): Personal Computers and Beyond
  - LSI (Large Scale Integration) and VLSI circuits led to personal computers.
  - Key operating systems: MS-DOS, Windows, macOS, Linux, iOS, Android.
  - Graphical User Interfaces (GUIs) became standard.
  - Networking became integral to the OS (TCP/IP stack).
  - Multi-core processors necessitated parallel and concurrent OS design.
  - Cloud computing, virtualization, and containerization.

────────────────────────────────────────────────────
1.4.2  Types of Operating Systems
────────────────────────────────────────────────────

1. Batch Operating Systems
   - Jobs are collected, grouped, and processed in batches.
   - No user interaction during execution.
   - Advantage: Efficient for large, repetitive jobs.
   - Disadvantage: No interactivity; long turnaround times.
   - Modern relevance: Batch processing still exists in job scheduling
     systems like SLURM (used in HPC clusters) and cloud batch services
     (AWS Batch).

2. Multiprogramming Operating Systems
   - Multiple programs loaded in memory simultaneously.
   - CPU switches between programs when one is waiting for I/O.
   - Improves CPU utilization.
   - Requires memory protection and management.

3. Time-Sharing (Multitasking) Operating Systems
   - Extension of multiprogramming with rapid CPU switching.
   - Each user gets a time slice (quantum) of CPU time.
   - Provides interactive computing: users can interact with programs
     during execution.
   - Examples: UNIX, Linux, modern Windows, macOS.

4. Real-Time Operating Systems (RTOS)
   - Must guarantee that operations complete within strict time constraints.
   - Hard real-time: Missing a deadline is catastrophic (aircraft flight
     control, nuclear plant control).
   - Soft real-time: Missing a deadline degrades performance but is not
     catastrophic (multimedia streaming, video games).
   - Examples: VxWorks, QNX, FreeRTOS, RTEMS.
   - [Deep-dived in Chapter 7]

5. Distributed Operating Systems
   - Manages a collection of independent, networked computers and makes
     them appear as a single system to users.
   - Provides location transparency, migration transparency, and
     replication transparency.
   - [Deep-dived in Chapter 7]

6. Embedded Operating Systems
   - Designed for embedded systems (IoT devices, routers, smart TVs,
     washing machines).
   - Typically small, efficient, and deterministic.
   - Examples: Embedded Linux, FreeRTOS, Zephyr, Contiki.

7. Mobile Operating Systems
   - Designed for smartphones and tablets.
   - Focus on touch interfaces, power management, connectivity.
   - Examples: Android (Linux kernel), iOS (XNU kernel).
   - [Deep-dived in Chapter 7]

8. Network Operating Systems
   - Provide networking capabilities: file sharing, printer sharing,
     user management across a network.
   - Examples: Novell NetWare, Windows Server.

    Micro-topic: The UNIX Family Tree
    ──────────────────────────────────
    UNIX was created in 1969 at Bell Labs by Ken Thompson and Dennis Ritchie.
    It spawned an enormous family tree:

      UNIX (1969)
        ├── BSD (Berkeley Software Distribution)
        │     ├── FreeBSD → basis for PlayStation OS
        │     ├── OpenBSD → focus on security
        │     ├── NetBSD → focus on portability
        │     └── macOS / iOS (via NeXTSTEP → Mach + BSD)
        ├── System V (AT&T)
        │     ├── Solaris (Sun/Oracle)
        │     ├── HP-UX
        │     └── AIX (IBM)
        └── Linux (1991, Linus Torvalds)
              ├── Debian → Ubuntu
              ├── Red Hat → Fedora, CentOS
              ├── Slackware
              ├── Arch Linux (2002) → Manjaro
              ├── Gentoo
              └── Android (Google, Linux kernel)

        Deeper: Arch Linux — A Rolling-Release Philosophy
        ─────────────────────────────────────────────────
        Arch Linux, founded by Judd Vinet in 2002 and now maintained by
        Levente Polyák and the Arch Linux team, follows a rolling-release
        model: there are no "versions." The user always has the latest
        software by running `pacman -Syu`. This contrasts with point-release
        distributions like Ubuntu (which has 22.04, 24.04, etc.).

        Arch follows the KISS principle (Keep It Simple, Stupid):
          - Minimalist base installation (no GUI by default)
          - User-centric: The user makes all decisions
          - The Arch Wiki is considered one of the best Linux documentation
            resources and is useful even for non-Arch users.

  ARCH LINUX: HANDS-ON IMPLEMENTATION
================================================================================

The following exercises allow you to observe the OS concepts from Unit 1 on
your Arch Linux system.

────────────────────────────────────────
Lab 1.1: Exploring the OS as a Resource Manager
────────────────────────────────────────

# View basic OS information
    $ uname -a
    # Output: Linux <hostname> <kernel-version> ... x86_64 GNU/Linux

# Detailed OS release information
    $ cat /etc/os-release
    # Shows NAME="Arch Linux", ID=arch, etc.

# View CPU information (resource the OS manages)
    $ cat /proc/cpuinfo | head -30
    # Shows processor model, cores, cache size, flags (including vmx/svm)

# View memory information (another managed resource)
    $ cat /proc/meminfo | head -20
    # Shows MemTotal, MemFree, MemAvailable, Buffers, Cached, etc.

# View all block devices (disk resources)
    $ lsblk
    # Shows disk partitions, sizes, mount points

# View cgroups hierarchy (modern resource management)
    $ systemctl status
    # Shows the systemd cgroup tree

# Inspect a specific cgroup (e.g., user slice)
    $ cat /sys/fs/cgroup/user.slice/cpu.max
    # Shows CPU bandwidth limit (or "max 100000" for unlimited)

────────────────────────────────────────
Lab 1.2: Examining Processes
────────────────────────────────────────

# View the process tree (the hierarchy from PID 1)
    $ pstree -p
    # Shows systemd(1) as root, with all children

# View all processes with details
    $ ps aux
    # USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND

# View process states in real-time
    $ top
    # Press '1' to see per-CPU utilization
    # Press 'H' to show individual threads

# Inspect a specific process's task_struct info via /proc
    $ cat /proc/self/status
    # Shows Name, State, Tgid, Pid, PPid, Threads, VmSize, etc.

# View the process's memory map
    $ cat /proc/self/maps
    # Shows virtual memory regions: code, heap, stack, vDSO, libraries

# View the vDSO mapping
    $ cat /proc/self/maps | grep vdso
    # Shows the virtual dynamic shared object mapped into the process

────────────────────────────────────────
Lab 1.3: System Calls in Action
────────────────────────────────────────

# Use strace to watch system calls made by a simple command
    $ strace ls /tmp 2>&1 | head -50
    # Shows: execve(), brk(), openat(), fstat(), read(), write(), close()...

# Count system calls used by a command
    $ strace -c ls /tmp 2>&1
    # Outputs a table showing % time, seconds, calls, errors, syscall name

# Trace only specific system calls
    $ strace -e trace=open,read,write ls /tmp 2>&1
    # Filters to show only open(), read(), write() calls

# View the number of system calls supported by your kernel
    $ wc -l /usr/include/asm/unistd_64.h
    # Or check the kernel source:
    # $ grep -c "^[0-9]" /usr/src/linux/arch/x86/entry/syscalls/syscall_64.tbl

────────────────────────────────────────
Lab 1.4: The Shell
────────────────────────────────────────

# Check your current shell
    $ echo $SHELL
    # /bin/bash or /bin/zsh etc.

# List available shells
    $ cat /etc/shells

# See how the shell forks to execute a command
    $ strace -f -e trace=clone,execve bash -c "ls /tmp" 2>&1
    # Shows clone() (fork) followed by execve() in the child

# Demonstrate I/O redirection at the system call level
    $ strace -e trace=dup2,openat bash -c "echo hello > /tmp/test.txt" 2>&1
    # Shows openat() to open the file, then dup2() to redirect fd 1

────────────────────────────────────────
Lab 1.5: OS Structure — Kernel Modules
────────────────────────────────────────

# List all currently loaded kernel modules
    $ lsmod
    # Shows Module, Size, Used by

# Get detailed info about a module (e.g., the ext4 filesystem)
    $ modinfo ext4

# Check if KVM (virtualization) is available
    $ lsmod | grep kvm
    # Shows kvm_intel or kvm_amd if hardware virtualization is loaded

# View kernel configuration (monolithic + modules)
    $ zcat /proc/config.gz | grep CONFIG_MODULES
    # CONFIG_MODULES=y  (modules are enabled)

# Write and compile a simple kernel module (save as hello.c):
# ─────────────────────────────────────────────────────────────
#   #include <linux/init.h>
#   #include <linux/module.h>
#   #include <linux/kernel.h>
#
#   MODULE_LICENSE("GPL");
#   MODULE_AUTHOR("Student");
#   MODULE_DESCRIPTION("A simple hello world kernel module");
#
#   static int __init hello_init(void) {
#       printk(KERN_INFO "Hello from kernel module!\n");
#       return 0;
#   }
#
#   static void __exit hello_exit(void) {
#       printk(KERN_INFO "Goodbye from kernel module!\n");
#   }
#
#   module_init(hello_init);
#   module_exit(hello_exit);
# ─────────────────────────────────────────────────────────────
#
# Create a Makefile:
#   obj-m += hello.o
#   all:
#       make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules
#   clean:
#       make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean
#
# Build and load:
#   $ make
#   $ sudo insmod hello.ko
#   $ dmesg | tail -1        # "Hello from kernel module!"
#   $ sudo rmmod hello
#   $ dmesg | tail -1        # "Goodbye from kernel module!"

────────────────────────────────────────
Lab 1.6: Virtual File Systems — /proc and /sys
────────────────────────────────────────

# Explore /proc
    $ ls /proc | head -30
    # Shows numbered directories (one per process) + kernel info files

# View kernel version
    $ cat /proc/version

# View system uptime
    $ cat /proc/uptime
    # First number: seconds since boot. Second: idle time.

# Explore /sys (sysfs — device model)
    $ ls /sys/class/net/
    # Shows network interfaces (e.g., enp0s3, wlan0, lo)

    $ cat /sys/class/net/*/address
    # Shows MAC addresses of all network interfaces

# View block device info
    $ ls /sys/block/
    $ cat /sys/block/sda/size    # Size in 512-byte sectors
